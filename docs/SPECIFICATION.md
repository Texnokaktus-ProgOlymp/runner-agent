# Техническая спецификация RunnerAgent

Дата: 2 октября 2026 года. Статус: спецификация согласованной части MVP с открытыми вопросами для детализации перед реализацией.

Документ предназначен для разработчиков агента, мастера проверяющей системы и интеграционных тестов. Он задаёт поведение RunnerAgent, границы компонентов, обмен данными и критерии приёмки на основе существующей документации. В репозитории пока нет приложения, проектов .NET, Dockerfile и CI workflow; требования ниже описывают будущую реализацию.

Источники: [архитектура](../ARCHITECTURE.md), [структура репозитория и сборка](REPOSITORY.md), [обзор проекта](../README.md). Архитектура хранит согласованные решения и их обоснование; эта спецификация переводит их в проверяемые требования. Детали, обозначенные в источниках как предложения, сохраняют этот статус. Новые протокольные решения этим документом не утверждаются.

Слова «должен» и «требуется» обозначают согласованные требования. Предложения помечены непосредственно в соответствующих разделах. Имена полей, состояний и категорий, кроме явно согласованных, служат для описания семантики и не заменяют окончательный `.proto`. Реестр открытых вопросов находится в разделе 13; критерии приёмки — в разделе 12.

## 1. Назначение и границы MVP

**REQ-01.** RunnerAgent должен принимать от мастера одно задание с одним исходным файлом C++23 и набором из N тестов, подготавливать файлы, один раз компилировать исходный код через g++, выполнять тесты и возвращать структурированный результат со ссылками на артефакты.

**REQ-02.** Компиляция и каждое исполнение должны запускаться в отдельных sandbox isolate. Тесты выполняются последовательно в порядке запроса, с независимым применением общего профиля execution limits к каждому запуску. Исполняемый артефакт компиляции используется для всего набора.

**REQ-03.** Агент отвечает за выполнение, ограничение ресурсов, метрики, диагностику и артефакты. Мастер отвечает за инициирование задания, получение результата, сравнение stdout с эталоном или запуск checker и вынесение AC/WA. Успешное исполнение в агенте не означает Accepted.

Запуск инициирует член жюри после ручного просмотра кода; участники не запускают программы в этой среде самостоятельно. Ручной просмотр не является технической границей изоляции.

В текущий MVP не входят дополнительные языки, несколько исходных файлов в задании, произвольные команды и compiler flags от мастера, проверка правильности ответа, отмена задания через API, сохранение задания на диск и автоматическое восстановление после перезапуска. Аутентификация gRPC, TLS и автоматический деплой также не входят в согласованный объём MVP.

Native AOT и отдельная Judge VM/host относятся к целевому развитию. Они не являются условиями готовности первой JIT-реализации.

## 2. Среда исполнения и внешние границы

**REQ-04.** MVP должен работать в Linux Docker-контейнере с `--privileged`, содержащем .NET 10 Runner Agent, isolate, g++, compiler/runtime libraries и локальную временную рабочую область. Первый образ условно называется `judge-cpp`; имя пакета registry ещё не утверждено. Для JIT-образа требуется .NET runtime.

```text
Мастер -- gRPC HTTP/2 --> RunnerAgent
                             |
                             +-- MinIO: исходный код, входные данные, артефакты
                             +-- isolate: одна компиляция
                             +-- isolate: отдельный запуск каждого теста
Мастер <-- результат и ссылки на S3 --+
```

**REQ-05.** gRPC используется для управления и небольших структурированных результатов. Исходный код, stdin, stdout, stderr и журнал компиляции передаются через S3, а не через gRPC. В MVP gRPC работает по HTTP/2 без HTTPS/TLS и аутентификации в доверенной внутренней сети.

**REQ-06.** Файловое хранилище — MinIO. Агент обращается к нему через `AWSSDK.S3` за интерфейсом `IObjectStorage`; endpoint берётся из конфигурации. Credentials принадлежат только агенту и получаются через credential provider, который предстоит выбрать.

Privileged Docker служит упаковкой и способом запуска, но не самостоятельной security boundary. Основная техническая граница для кода решения — isolate. Существенный риск компрометации judge-host принят для первого этапа. Контейнер дополнительно ограничивается по CPU, RAM и числу процессов там, где это совместимо с isolate и cgroups.

Целевое развёртывание — отдельная заменяемая Judge VM либо выделенный host с native isolate, cgroup delegation, минимальными привилегиями и изолированными toolchain/rootfs. Переход должен сохранять внешний gRPC/S3-контракт и логику orchestration. Подбор capabilities, user namespaces и cgroup delegation внутри Docker не входит в MVP.

## 3. Контракт задания и gRPC

### 3.1. Данные задания

**REQ-07.** Задание должно содержать следующие данные. Названия полей предварительные; номера protobuf-полей, wire types остальных значений и правила валидации ещё не определены.

| Данные | Смысл и ограничения |
| --- | --- |
| `job_id` | Знаковый `int64`, задаётся мастером и возвращается без изменения |
| `language`, `language_version` | Выбор заранее зарегистрированного профиля; для MVP — C++23 |
| `source` | Одна ссылка на исходный код: ключ S3 и ожидаемый SHA-256 |
| `tests[]` | Упорядоченный набор тестов; каждый содержит заданный мастером `test_id` типа `int64` и ссылку на входные данные по ключу и SHA-256 |
| `result_prefix` | Префикс выходных объектов, задаётся мастером |
| Compilation limits | Самостоятельные ограничения компиляции |
| Execution limits | Единый профиль ограничений, применяемый независимо к каждому тесту |

Bucket, команды запуска, compiler flags и `version_id` S3 в задании не выбираются. Допустимые значения ID, уникальность `test_id`, допустимость пустого набора, максимальное число тестов и размеры запроса требуют решения в Q-03.

### 3.2. Принятие задания

**REQ-08.** API должен быть асинхронным. Предварительное имя RPC запуска — `StartJob`. Агент проверяет структуру нового задания, фиксирует его принятие и занятость ресурса и сразу возвращает подтверждение. Подтверждение не означает успешной компиляции или исполнения. После принятия работа продолжается независимо от завершения RPC и разрыва соединения.

Для долгоживущей ветки действуют правила:

| Ситуация | Поведение |
| --- | --- |
| Ресурс свободен и новое задание прошло проверку | Принять задание и начать обработку |
| Выполняется задание с тем же `job_id` | Ответить «задание уже принято», повторно не исполнять |
| Готовый результат того же `job_id` ожидает чтения | Ответить «задание уже принято», повторно не исполнять |
| Ресурс занят другим `job_id`, включая ожидание чтения | Ответить «ресурс занят» |
| Начата штатная остановка | Не принимать новые задания |

Повтор с тем же ID и изменённым содержимым, повторное использование ID после выдачи результата, точные ответы и gRPC status codes остаются открытыми. Приведённые правила не задают постоянный реестр выполненных заданий.

### 3.3. Получение результата

**REQ-09.** Операция `GetResult` должна выдавать результат соответствующего задания. До готовности она сразу отвечает «не завершено», не ожидает окончания внутри RPC и не освобождает ресурс. Запрос результата другого задания также не освобождает ресурс.

При выдаче готового результата `GetResult` освобождает ресурс и сразу удаляет сохранённый результат из памяти агента. Отдельного подтверждения мастера нет; повторное чтение выданного результата невозможно. S3-артефакты остаются. Точный ответ для отсутствующего, чужого или уже выданного результата ещё не выбран.

**REQ-10.** Принятие задания и переход при `GetResult` должны быть согласованы при конкурентных запросах: нельзя принять два задания одновременно или повторно выдать один сохранённый результат. Точная точка удаления относительно отправки RPC-ответа и поведение при обрыве передачи требуют решения в Q-02.

Следствие согласованного удаления без подтверждения: протокол не гарантирует повторную доставку результата после потери ответа. Мастер не должен рассчитывать на повторное чтение уже выданного результата.

## 4. Состояние агента и жизненный цикл

### 4.1. Обработка задания

**REQ-11.** Orchestration должно выполнять следующий порядок действий:

1. Проверить запрос и атомарно зафиксировать принятие задания.
2. Создать workspace, получить исходный код и необходимые входные данные, проверить SHA-256 до использования файлов в sandbox.
3. Выполнить одну компиляцию с compilation limits в отдельном isolate box.
4. При успешной компиляции выполнить тесты по порядку, создавая отдельный execution sandbox для каждого запуска. Ошибка отдельного теста не прерывает обработку остальных.
5. Собрать результаты и загрузить доступные артефакты в S3, вычислив их SHA-256.
6. Сохранить структурированный результат отдельно от workspace и очистить временные файлы и isolate boxes. При ошибках также выполнить очистку и сформировать соответствующий результат.
7. Ожидать `GetResult`, сохраняя ресурс занятым.
8. Выдать готовый результат, удалить его из памяти и освободить ресурс; при остановке завершить процесс после обслуживания RPC.

Порядок предварительного скачивания всех входов либо их получения перед каждым тестом не зафиксирован. Выбранная реализация должна сохранять продолжение набора при сбое загрузки входа отдельного теста.

Для описания долгоживущей ветки используются следующие логические состояния; это не утверждённый transport enum:

| Состояние | Что хранится и выполняется | Переход |
| --- | --- | --- |
| Свободен | Нет текущего задания и непрочитанного результата | Принятие задания → обработка |
| Обработка | Задание принято; выполняются подготовка, компиляция, тесты, публикация и очистка | Готовность результата → ожидание чтения |
| Ожидание чтения | Результат хранится в памяти отдельно от очищенной рабочей области | Выдача через `GetResult` → свободен либо завершение при остановке |
| Завершён | Процесс остановлен; состояние в памяти утрачено | При новом запуске восстановление задания не выполняется |

Штатная остановка — отдельный режим, запрещающий принятие новых заданий в состояниях обработки и ожидания. Он описан ниже.

**REQ-12.** Во время обычной работы долгоживущего агента ожидание `GetResult` не ограничено таймаутом. Непрочитанный результат не истекает и удерживает ресурс независимо от длительности отсутствия мастера. Завершение вычислений или очистка sandbox сами по себе ресурс не освобождают.

**REQ-13.** Для MVP задание и непрочитанный результат хранятся в памяти. Их потеря при перезапуске допустима; сохранение на диск, восстановление и возобновление не требуются. Решение о повторном запуске принимает мастер. Опубликованные S3-артефакты не зависят от памяти процесса.

### 4.2. Штатная остановка

**REQ-14.** При запросе штатной остановки агент должен прекратить принятие новых заданий, завершить текущий набор, опубликовать доступные артефакты, очистить sandbox/workspace и сохранить готовый результат для `GetResult`.

Ожидание получения результата при остановке настраивается; значение по умолчанию — **30 секунд**. Отсчёт начинается после готовности результата, публикации артефактов и очистки. Если результат уже готов, отсчёт начинается при запросе остановки. Выполнение задания не расходует этот таймаут.

В течение ожидания gRPC остаётся доступным для `GetResult`. Если результат забран, агент завершает обслуживание RPC, затем останавливает сервер и процесс. Если таймаут истёк, агент выходит с потерей непрочитанного результата в памяти, сохраняя опубликованные S3-артефакты. При отсутствии задания и результата агент может завершиться сразу.

Настройки остановки приложения и контейнера должны позволять завершить задание и затем выдержать ожидание результата. Принудительное или аварийное завершение может привести к допустимой потере состояния. Внутренний `CancellationToken` не означает наличие `CancelJob`; отключение клиента и начало штатной остановки сами по себе не отменяют принятое задание.

### 4.3. Не выбранный вариант жизненного цикла

Окончательный выбор между долгоживущим агентом и контейнером на один набор тестов не сделан. В альтернативной ветке агент выполняет одно задание, ожидает получения результата в пределах того же настраиваемого таймаута и завершается после выдачи результата либо истечения ожидания. Контейнер затем останавливается и удаляется внешним управляющим компонентом. Владелец создания и удаления контейнеров не определён. Это runtime orchestration, а не автоматический CI-деплой.

## 5. S3 и целостность файлов

**REQ-15.** Конфигурация агента должна задавать два bucket:

| Роль | Bucket | Ссылка во входном задании или результате |
| --- | --- | --- |
| Исходный код | Отдельный bucket исходного кода | Входные `key` и ожидаемый `sha256` |
| Вход теста | Общий bucket данных и артефактов | Входные `key` и ожидаемый `sha256` |
| Журнал компиляции | Общий bucket данных и артефактов | Фактические выходные `key` и вычисленный `sha256` |
| Stdout и stderr тестов | Общий bucket данных и артефактов | Фактические выходные `key` и вычисленный `sha256` |

Bucket выбирается агентом по роли объекта. Для выходных файлов ключи формируются внутри `result_prefix` мастера; точные суффиксы и правила уникальности ещё не определены. Агент возвращает фактические ссылки на опубликованные объекты.

**REQ-16.** После скачивания входного объекта агент должен проверить SHA-256 до помещения файла в sandbox. Несовпадение hash — ошибка подготовки; такой файл не запускается и не используется при компиляции. ETag не заменяет SHA-256. Контракт не использует `version_id` и не требует включения S3 versioning. Для выходных артефактов агент вычисляет и возвращает SHA-256.

**REQ-17.** Скачивание и загрузка MinIO должны повторяться при временных ошибках: не более трёх попыток всего, включая первую, с небольшой задержкой между ними. Вложенные повторы `AWSSDK.S3` должны укладываться в этот общий бюджет. Отсутствие объекта и несовпадение SHA-256 повторов не вызывают.

После исчерпания попыток фиксируется инфраструктурная ошибка соответствующей стадии. Ошибка отдельного теста не останавливает остальные тесты. Точные задержки, перечень временных ошибок и реализация policy не выбраны.

Выходной объект с неуспешной публикацией нельзя обозначать как успешно доступный. Подробная модель частичной публикации, формат hash, ограничения размеров, credential provider и политика хранения объектов требуют детализации.

## 6. Sandbox и профиль языка

**REQ-18.** Компилятор обрабатывает недоверенный исходный код и должен запускаться в собственном sandbox с отдельными лимитами. В execution sandbox каждого теста передаются только необходимый исполняемый артефакт и разрешённые файлы. Рабочие файлы одного теста не должны передаваться следующему.

**REQ-19.** Для обеих стадий должны соблюдаться следующие ограничения:

- Нет доступа к сети, управляющим endpoint и S3/AWS credentials.
- Окружение формируется по allowlist: `PATH`, при необходимости `LANG` и согласованные переменные языка. Секреты не наследуются процессом isolate, компилятором или решением.
- Доступны только необходимые локальные файлы и разрешённые mounts. Рабочая область агента и другие задания недоступны.
- Исходный код, stdin, stdout/stderr и журнал компиляции передаются через локальные файлы под управлением агента.
- Workspace и isolate box привязаны к заданию/стадии и очищаются после завершения, ошибки или управляемой остановки. Ожидание чтения результата не требует сохранять sandbox.

**REQ-20.** Учёт compilation и execution должен быть раздельным. Память и процессы агента не должны включаться в потребление решения.

**REQ-21.** Профиль C++23 должен определяться агентом: версия toolchain, команды компиляции/запуска, все флаги, файлы и окружение. Мастер выбирает поддерживаемый профиль и передаёт resource limits, но не задаёт произвольные команды или дополнительные compiler flags. Language providers регистрируются заранее; первый provider использует g++.

Версии g++ и isolate, compiler flags, rootfs, mounts, права, идентификаторы box, детали cgroups, ограничения записи файлов и очистка после падения пока не специфицированы. Их нельзя считать обеспеченными одним фактом использования isolate.

## 7. Лимиты и измерения

**REQ-22.** Агент должен различать следующие ограничения; имена полей предварительные:

| Лимит | Поле | Единица и смысл |
| --- | --- | --- |
| CPU time | `cpu_time_ms` | Миллисекунды процессорного времени |
| Wall time | `wall_time_ms` | Миллисекунды реального времени |
| Memory | `memory_bytes` | Байты памяти sandbox; точная метрика требует выбора |
| Stdout | `stdout_bytes` | Отдельный максимальный размер stdout в байтах |
| Stderr | `stderr_bytes` | Отдельный максимальный размер stderr в байтах |
| Processes | `processes` | Допустимое число процессов/задач; учёт потоков и дочерних процессов требует уточнения |

Compilation и execution имеют самостоятельные наборы лимитов. Журнал компиляции также должен быть ограничен; форма и семантика его лимита ещё не определены. CPU time не заменяет wall time: ожидание и блокировка могут расходовать реальное время без значительного CPU time.

Execution limits применяются отдельно к каждому тесту, не к сумме потребления набора. Необходимость общего предела длительности задания не определена. Допустимые диапазоны, значения по умолчанию, преобразования единиц для isolate, точный учёт памяти и приоритет одновременно нарушенных лимитов остаются открытыми.

**REQ-23.** При превышении отдельного лимита stdout или stderr агент должен остановить процесс с `OutputLimitExceeded`. Уже полученная часть каждого потока сохраняется и публикуется в пределах собственного лимита. Сумма размеров потоков не заменяет проверку каждого из них. После этого обработка остальных тестов продолжается.

## 8. Результат и обработка ошибок

### 8.1. Состав результата

**REQ-24.** Структурированный результат должен содержать:

| Уровень | Данные |
| --- | --- |
| Задание | Исходный `job_id`, итоговый статус, стадия возникновения ошибки, результат единственной компиляции, коллекция результатов тестов |
| Компиляция | Статус/причина прекращения, CPU time, wall time, peak memory, exit code и signal при наличии, ссылка на журнал компиляции, доступная инфраструктурная диагностика |
| Тест | Исходный `test_id`, статус/причина прекращения, CPU time, wall time, peak memory, exit code и signal при наличии, ссылки на stdout/stderr, доступная инфраструктурная диагностика |
| Артефакт | Фактическая ссылка на опубликованный объект и вычисленный SHA-256 |

Отсутствующие exit code/signal должны представляться явно отсутствующими, а не фиктивным нулём. Для инфраструктурных ошибок сохраняются известные метрики и доступные артефакты; отсутствующие данные не подменяются успешным результатом.

Полный enum статусов и mapping isolate metadata не утверждены. Предварительные категории: успешное исполнение, compilation error, runtime error, CPU/wall time limit exceeded, memory limit exceeded, output limit exceeded, process limit exceeded и infrastructure error. Согласованы имена `CompilationError` и `OutputLimitExceeded`; `InfrastructureError` — предварительное имя отдельного статуса инфраструктурной ошибки теста.

### 8.2. Поведение при ошибках

**REQ-25.** Ошибки должны обрабатываться согласно следующей таблице:

| Событие | Требуемое поведение |
| --- | --- |
| Ошибка компиляции | Итоговый статус `CompilationError`, данные компиляции и журнал компиляции; тесты не запускаются, коллекция результатов тестов пуста |
| Ошибка публикации журнала компиляции | Отдельно отразить инфраструктурную ошибку; не представлять журнал компиляции опубликованным |
| Runtime error или превышение лимита теста | Сохранить verdict, метрики и доступные артефакты; продолжить остальные тесты |
| Сбой скачивания входа, запуска isolate или публикации артефактов отдельного теста | Отдельный инфраструктурный статус этого теста; сохранить известные данные, продолжить набор |
| Общая ошибка подготовки исходного кода или невозможность компиляции из-за инфраструктуры | Сформировать ошибку соответствующей стадии; общая классификация и представление невыполненных тестов ещё не определены |
| Перезапуск или падение процесса до выдачи результата | Потеря состояния допустима для MVP; опубликованные S3-артефакты сохраняются |

Сбой storage не должен маскироваться под ошибку программы участника. Правила общего статуса задания при смешанных результатах, совместное представление ошибки исполнения и публикации, а также приоритет причин при нескольких нарушениях требуют детализации.

Финальный результат, включая ошибку компиляции или инфраструктуры, выдаётся через `GetResult` и освобождает ресурс по общим правилам, если процесс агента сохранился до выдачи.

## 9. Компоненты и внутренние контракты

**REQ-26.** Реализация должна сохранять следующие логические границы. Они не требуют отдельного assembly на каждый компонент.

| Компонент | Ответственность |
| --- | --- |
| `Grpc` / `JudgeRunnerService` | Принятие запросов, преобразование transport models, выдача результата |
| Orchestration | Состояние задания в памяти, занятость до чтения, независимая от RPC обработка, координация storage/workspace/runner и публикации |
| `Storage` / `IObjectStorage`, `S3ObjectStorage` | Получение и публикация S3-объектов, метаданные хранилища |
| `Execution` / `ISubmissionRunner`, `IsolateSubmissionRunner` | Локальная компиляция и execution pipeline, преобразование isolate metadata |
| `Languages` / `ILanguageProvider`, `CppLanguageProvider` | Поддерживаемые версии, toolchain, команды, файлы и окружение |
| `Workspace` / `WorkspaceManager` | Создание рабочих областей, размещение локальных файлов и очистка |

`IsolateSubmissionRunner` не должен зависеть от gRPC или S3. Он получает локальное задание с одним файлом исходного кода и набором тестов и возвращает локальные результаты и пути артефактов. Финальный внутренний контракт должен явно представлять отдельные compilation/execution limits. Точная сигнатура и распределение операций получения входов между orchestration и runner пока не определены.

Выделение низкоуровневого `ISandboxRunner` возможно как деталь реализации. Дополнительные языки должны добавляться без переноса логики gRPC/S3 в runner.

**REQ-27.** Разработка начинается с .NET 10 JIT. Код должен учитывать целевую Native AOT publication: статически известные типы, сгенерированные protobuf-модели, явная регистрация providers, `System.Text.Json` source generation при необходимости JSON; без runtime plugins, dynamic loading и ненужной reflection-heavy сериализации.

Проверка `PublishAot=true` и trimming/AOT warnings планируется при появлении реализации. Совместимость конкретных gRPC-библиотек и `AWSSDK.S3` с AOT не доказана. Переход production-образа на AOT требует проверки gRPC, S3, isolate и результатов на целевой Linux-платформе. AOT не заменяет sandbox; compiler/runtime поддерживаемого языка остаётся самостоятельной частью образа.

## 10. Конфигурация и эксплуатация

Точные имена параметров, переменных окружения и схема конфигурации не выбраны. Из согласованных требований следуют следующие категории настроек:

| Настройка | Зафиксированная семантика |
| --- | --- |
| gRPC endpoint и порт | HTTP/2 без TLS и аутентификации в доверенной внутренней сети; адрес и порт не выбраны |
| MinIO endpoint | Задаётся конфигурацией агента |
| Bucket исходного кода | Отдельный от данных тестов и результатов |
| Общий bucket | Входы тестов и выходные артефакты |
| Credential provider | Только на стороне агента; механизм получения не выбран |
| Workspace и isolate | Локальные рабочие области; пути, mounts, box IDs и cgroups требуют выбора |
| Профиль C++23 | Контролируемые агентом команды, флаги и окружение; конкретное содержимое требует выбора |
| Таймаут получения результата при завершении | Настраиваемый, по умолчанию 30 секунд; не действует при обычной работе долгоживущего агента |

Resource limits задания поступают от мастера; это не разрешение менять профиль toolchain. Способ задания host/container limits и их согласования с isolate ещё требует проработки.

**REQ-28.** Runtime credentials должны задаваться при развёртывании агента. Токены registry и S3 credentials не записываются в Dockerfile, build args или слои образа. При необходимости приватного NuGet используются BuildKit secret mounts; наличие такой зависимости пока не установлено.

Ручной деплой предполагает выбор проверенного образа по тегу версии, подготовку Linux judge-host, конфигурации, credentials и workspace, запуск выбранной ветки контейнера и контрольное задание C++ с получением результата. Точная команда запуска, проверка готовности сервиса, логирование, метрики, эксплуатационные лимиты и аварийная очистка должны быть описаны после выбора среды. Численные требования к пропускной способности, доступности и задержке API в источниках отсутствуют.

## 11. Репозиторий и поставка

**REQ-29.** Согласованы solution `.slnx`, production-код в `src/`, тесты в `tests/`, workflows в `.github/workflows/`, корневой `Directory.Build.props` и CPM в `Directory.Packages.props`. Вложенные `Directory.Build.props` должны явно импортировать родительские настройки. Общие тестовые зависимости относятся к `tests/`, а `InternalsVisibleTo` для соответствующего `.Tests` и `DynamicProxyGenAssembly2` задаётся в `src/Directory.Build.props`.

**REQ-30.** Тесты должны использовать NUnit на Microsoft.Testing.Platform с нативным MTP-режимом `dotnet test` в .NET 10. Версия SDK и `test.runner=Microsoft.Testing.Platform` задаются через `global.json`; настройки NUnit runner и MTP-расширения coverage/TRX — через `tests/Directory.Build.props`. Общие зависимости включают NUnit и NSubstitute. Версии пакетов и SDK patch ещё не выбраны.

**REQ-31.** GitHub Actions должен собирать и тестировать приложение, упаковывать Docker image и публиковать его в GHCR. Формат версии — `YYYY.M.D.<run_number>` с датой исходного коммита в Europe/Moscow; повтор workflow сохраняет версию. Образ выбирается для ручного деплоя по тегу версии. Pipeline заканчивается публикацией; автоматический деплой не планируется.

Следующие детали остаются **предложениями** из [REPOSITORY.md](REPOSITORY.md), а не утверждёнными ограничениями продукта:

- Один production-проект и два тестовых проекта: `.Tests` для локальной логики и `.IntegrationTests` для реальных внешних границ.
- Общие `net10.0`, C# 14.0, nullable/implicit usings, deterministic build и анализаторы; ReportGenerator как local tool; конкретные наборы настроек и версии проверяются при создании каркаса.
- Multi-stage Dockerfile рядом с production `.csproj`, build context в корне, `.dockerignore` для локальных и секретных файлов.
- PR-проверки без production secrets; публикация только после успешного доверенного push в выбранную основную ветку.
- Сначала `linux/amd64`; arm64 после проверки isolate/toolchain. Linux CI runner с рабочими privileged Docker/cgroups и интеграционным запуском C++ в собранном образе.
- Публикация уже проверенного image без пересборки, передача между jobs через `docker save/load`, OCI revision и версия в metadata, TRX/coverage artifacts.
- Имя образа `ghcr.io/texnokaktus-progolym/runner-agent`; отдельная проверка AOT с ещё не выбранной обязательностью.

Подробное предлагаемое дерево, MSBuild/CPM-настройки и план pipeline сохраняются в `REPOSITORY.md`. Создание Git-тега описано там как свойство изученного workflow и не является самостоятельным согласованным требованием RunnerAgent.

## 12. Критерии приёмки

Ниже приведён план проверок, выведенный из согласованных требований. Он не означает наличия или успешного выполнения тестов в текущем репозитории. Проверки условной долгоживущей ветки применяются при выборе этой ветки; детали альтернативы дополняются после Q-01. Проверки точных кодов протокола, mapping метаданных и диапазонов входных значений требуют закрытия соответствующих открытых вопросов.

| Проверка | Ожидаемый результат | Требования |
| --- | --- | --- |
| AT-01. Один файл исходного кода и несколько тестов | Компиляция выполняется один раз; тесты идут в порядке запроса, каждый в отдельном sandbox | REQ-01, REQ-02, REQ-11, REQ-18 |
| AT-02. Подтверждение и отключение клиента | Подтверждение приходит до завершения обработки; принятое задание продолжает работу после завершения RPC/соединения | REQ-08 |
| AT-03. Повторы `StartJob` во время работы и ожидания чтения | Текущий ID не запускается повторно; другой ID получает «ресурс занят» | REQ-08, REQ-12 |
| AT-04. Конкурентное принятие и чтение | Два задания одновременно не принимаются; готовый результат не выдаётся двум читателям | REQ-10 |
| AT-05. Ранний `GetResult` и запрос другого задания | Ответ не ожидает окончания обработки; ресурс остаётся занят | REQ-09 |
| AT-06. Выдача готового результата | Ресурс освобождён, результат в памяти удалён, повторно не читается; S3-артефакты сохранены | REQ-09 |
| AT-07. Очистка и длительное отсутствие мастера | Workspace/boxes очищены; в обычном режиме результат сохраняется и ресурс занят без таймаута | REQ-11, REQ-12, REQ-19 |
| AT-08. Ошибка компиляции | `CompilationError`, данные компиляции и опубликованный журнал компиляции, пустая коллекция тестов, ни одного исполнения | REQ-25 |
| AT-09. Ошибки решения на тестах | Runtime error или превышение лимита не препятствуют обработке следующих тестов; возвращаются результаты набора | REQ-02, REQ-25 |
| AT-10. Инфраструктурный сбой отдельного теста | Сбой загрузки входа, isolate или публикации даёт отдельную инфраструктурную ошибку; последующие тесты обрабатываются | REQ-17, REQ-25 |
| AT-11. Лимиты стадий и тестов | Компиляция ограничена отдельно; execution budget применяется заново к каждому тесту, а не ко всему набору | REQ-20, REQ-22 |
| AT-12. CPU и wall time | CPU-нагрузка и ожидание проверяют независимые ограничения согласно утверждённому mapping | REQ-22 |
| AT-13. Вывод | Превышение отдельно stdout и отдельно stderr останавливает процесс с `OutputLimitExceeded`; оба частичных потока не превышают собственные лимиты, набор продолжается | REQ-23 |
| AT-14. Сумма потоков | Если каждый поток укладывается в свой лимит, превышение их суммой одного из отдельных лимитов не даёт `OutputLimitExceeded` | REQ-23 |
| AT-15. Sandbox | Код не получает сеть, credentials, управляющие endpoint или чужие файлы; файлы одного теста не переходят в другой | REQ-18, REQ-19 |
| AT-16. Профиль языка | Команды/флаги определяет агент; применяются выбранный C++23-профиль и resource limits задания | REQ-07, REQ-21 |
| AT-17. S3-контракт | Используются два настроенных bucket по ролям; выходные ключи находятся внутри префикса мастера, возвращаются фактические ссылки и hash | REQ-06, REQ-15, REQ-16 |
| AT-18. Целостность | Неверный SHA-256 блокирует использование файла; ETag не подменяет hash; versioning не требуется | REQ-16 |
| AT-19. Повторы MinIO | Успешное восстановление и исчерпание временных ошибок укладываются в три попытки с учётом SDK; отсутствие объекта и неверный hash не повторяются | REQ-17 |
| AT-20. Данные результата | ID типа `int64` из допустимого диапазона сохраняются без изменения; неизвестные exit code/signal не превращаются в ноль; успешное исполнение не объявляется AC | REQ-03, REQ-07, REQ-24 |
| AT-21. Ошибка публикации | Недоступный артефакт не заявляется опубликованным; сбой не маскируется под ошибку решения, в том числе для журнала компиляции | REQ-25 |
| AT-22. Штатная остановка при обработке | Новые задания не принимаются; набор завершается, артефакты публикуются, sandbox очищаются, `GetResult` доступен | REQ-14 |
| AT-23. Таймаут остановки | По умолчанию 30 секунд, значение настраивается; отсчёт после готовности/очистки либо с запроса остановки при уже готовом результате; выполнение задания не расходует таймаут | REQ-14 |
| AT-24. Выход при остановке | После обслуживания `GetResult` процесс выходит; по таймауту теряет только результат в памяти; незанятый агент может завершиться сразу | REQ-14 |
| AT-25. Перезапуск | Текущее задание и непрочитанный результат не восстанавливаются; опубликованные S3-артефакты доступны | REQ-13 |
| AT-26. Внешние границы | HTTP/2 gRPC без TLS/auth передаёт управление; файлы идут через MinIO с production-реализацией `IObjectStorage`; runner работает с локальными файлами | REQ-05, REQ-06, REQ-26 |
| AT-27. Сборка и поставка | Общие настройки/CPM наследуются, тесты используют NUnit/MTP, pipeline выдаёт проверенный Docker image в GHCR с согласованным форматом версии | REQ-29, REQ-30, REQ-31 |
| AT-28. Образ и секреты | Linux-образ содержит agent/isolate/toolchain; секреты не записаны в build args/слои и не попадают в sandbox | REQ-04, REQ-19, REQ-28 |

Предлагаемое разделение проверок: unit-тесты для состояния, orchestration, классификации и storage policy без реального Docker/S3/isolate; интеграционные — для gRPC, MinIO, isolate, лимитов, очистки и остановки реального процесса. Точное устройство fixtures ещё не утверждено. AOT отдельно проверяется после появления реализации; его успешность не заявляется в этой спецификации.

| Q-05 | Диапазоны/значения лимитов, учёт дочерних процессов и потоков, точная метрика памяти, преобразование единиц, приоритет нарушений и поведение журнала компиляции при превышении лимита | Настройка isolate/cgroups и воспроизводимость verdict |
| Q-06 | Нужен ли общий предел длительности задания | Верхняя граница занятости и настройки остановки контейнера |
| Q-07 | Кодирование SHA-256, размеры входных объектов, суффиксы ключей, проверка префикса и его уникальность, перезапись объектов, частичная публикация, lifecycle S3 | Контракт storage и повторный запуск задания |
| Q-08 | Credential provider MinIO, версия/настройки `AWSSDK.S3`, перечень временных ошибок, задержки и реализация policy в рамках трёх попыток | Доступ к storage и интеграционные тесты |
| Q-09 | Linux/base image, версии isolate/g++, compiler flags, архитектуры, cgroups, rootfs/mounts, права, box IDs и ограничения записи файлов | Воспроизводимая сборка и фактическая изоляция |
| Q-10 | Очистка после падения, поведение при ошибке очистки, безопасное повторное использование workspace/boxes | Эксплуатация и готовность к следующему заданию |
| Q-11 | Схема конфигурации, логирование, диагностика/метрики, readiness, host/container limits и параметры остановки | Развёртывание и сопровождение |
| Q-12 | Состав проектов, SDK patch, версии packages/tools/actions, основная ветка, имя image, CI runner/fixtures и политика прерывания публикаций | Создание рабочего каркаса и pipeline |
| Q-13 | AOT-совместимые зависимости, размещение gRPC service, обязательность AOT check и критерии перехода production-образа | Целевой Native AOT |
| Q-14 | Рассмотреть брокер сообщений, например Kafka, для приёма заданий и публикации результатов тестирования; определить, заменяет ли он gRPC или дополняет его, правила доставки, подтверждений, повторов и освобождения ресурса | Возможное развитие транспорта и жизненного цикла задания |

Q-14 — вариант для обсуждения, не принятое требование MVP. При его оценке нужно определить обработку дубликатов по `job_id`, поведение при недоступности брокера и перезапуске агента, момент подтверждения задания и публикации результата, а также связь этих событий с освобождением ресурса. Отдельно следует уточнить роль S3 для файлов и артефактов. Пока действуют согласованные gRPC/S3-контракт и правила `StartJob`/`GetResult`; внедрение брокера требует отдельного решения.

## 14. Порядок дальнейшей детализации

Предлагаемая последовательность работ, а не новый согласованный план поставки:

1. Закрыть lifecycle, wire-контракт и модель результатов: Q-01–Q-04. Зафиксировать совместимые ожидания мастера и агента.
2. Определить лимиты, sandbox, storage и очистку: Q-05–Q-10; проверить возможности выбранной Linux-среды и isolate.
3. Выбрать конфигурацию, состав каркаса, версии и CI: Q-11–Q-12. Создать реальные проекты вместе с проверяемым минимальным приложением.
4. Реализовать и проверить вертикальный сценарий: принятие задания → MinIO → компиляция → тесты → публикация → очистка → `GetResult`, затем сценарии отказов и остановки из раздела 12.
5. Подтвердить критерии приёмки для выбранной ветки, описать проверенные команды сборки и ручного деплоя, опубликовать MVP-образ. Совместимость AOT и переход к целевому размещению вести отдельно.

По мере принятия решений обновляются эта спецификация, соответствующие разделы `ARCHITECTURE.md` и затронутые инструкции `REPOSITORY.md`/`README.md`. Закрытие вопроса должно менять конкретный контракт или требование, а не только удалять строку из реестра.

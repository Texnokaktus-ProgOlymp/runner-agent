## 1. Назначение и границы MVP

**REQ-01.** RunnerAgent должен принимать от мастера одно задание с одним исходным файлом C++23 и набором из N тестов, подготавливать файлы, один раз компилировать исходный код через g++, выполнять тесты и возвращать структурированный результат со ссылками на артефакты.

**REQ-02.** Компиляция и каждое исполнение должны запускаться в отдельных sandbox isolate. Тесты выполняются последовательно в порядке запроса, с независимым применением общего профиля execution limits к каждому запуску. Исполняемый артефакт компиляции используется для всего набора.

**REQ-03.** Агент отвечает за выполнение, ограничение ресурсов, метрики, диагностику и артефакты. Мастер отвечает за инициирование задания, получение результата, сравнение stdout с эталоном или запуск checker и вынесение AC/WA. Успешное исполнение в агенте не означает Accepted.

Запуск инициирует член жюри после ручного просмотра кода; участники не запускают программы в этой среде самостоятельно. Ручной просмотр не является технической границей изоляции.

В текущий MVP не входят дополнительные языки, несколько исходных файлов в задании, произвольные команды и compiler flags от мастера, проверка правильности ответа, отмена задания через API, сохранение задания на диск и автоматическое восстановление после перезапуска. Аутентификация gRPC, TLS и автоматический деплой также не входят в согласованный объём MVP.

Native AOT и отдельная Judge VM/host относятся к целевому развитию. Они не являются условиями готовности первой JIT-реализации.

## 2. Среда исполнения и внешние границы

**REQ-04.** MVP должен работать в Linux Docker-контейнере с `--privileged`, содержащем .NET 10 Runner Agent, isolate, g++, compiler/runtime libraries и локальную временную рабочую область. Первый образ условно называется `judge-cpp`; имя пакета registry ещё не утверждено. Для JIT-образа требуется .NET runtime.

```text
Мастер -- gRPC HTTP/2 --> RunnerAgent
                             |
                             +-- MinIO: исходный код, входные данные, артефакты
                             +-- isolate: одна компиляция
                             +-- isolate: отдельный запуск каждого теста
Мастер <-- результат и ссылки на S3 --+
```

**REQ-05.** gRPC используется для управления и небольших структурированных результатов. Исходный код, stdin, stdout, stderr и вывод компилятора передаются через S3, а не через gRPC. В MVP gRPC работает по HTTP/2 без HTTPS/TLS и аутентификации в доверенной внутренней сети. По умолчанию агент слушает `0.0.0.0:8080` внутри контейнера; адрес прослушивания и порт должны настраиваться.

**REQ-06.** Файловое хранилище — MinIO. Агент обращается к нему через `AWSSDK.S3` за интерфейсом `IObjectStorage`; endpoint берётся из конфигурации, используется `ForcePathStyle = true`. Credentials принадлежат только агенту: provider читает `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` и необязательный `AWS_SESSION_TOKEN` из окружения агента, без поиска в профилях или metadata-сервисах. Отсутствие обязательных значений — ошибка конфигурации при запуске. Выбор environment credentials принят при обязательной изоляции секретов по REQ-19.

Регион подписи клиента по умолчанию — `us-east-1`, с возможностью переопределения в конфигурации агента. В текущем развёртывании пользователя регион на сервере MinIO явно не задан; перенастройка сервера для работы агента не требуется. Совместимость выбранных версий MinIO/SDK проверяется интеграционно, в том числе на сервере без явно заданного региона. Версия SDK и оставшиеся настройки относятся к Q-08.

При запуске проверяется локальная конфигурация storage, включая обязательные credentials. Сетевая доступность MinIO, существование bucket и права доступа проверяются рабочими операциями по согласованной политике повторов. Обязательных сетевых проверок storage при запуске нет; временная недоступность MinIO сама по себе не препятствует запуску агента. Проверка локальной sandbox-среды по разделу 6 остаётся обязательной.

Privileged Docker служит упаковкой и способом запуска, но не самостоятельной security boundary. Основная техническая граница для кода решения — isolate. Существенный риск компрометации judge-host принят для первого этапа. Контейнер дополнительно ограничивается по CPU, RAM и числу процессов там, где это совместимо с isolate и cgroups.

Целевое развёртывание — отдельная заменяемая Judge VM либо выделенный host с native isolate, cgroup delegation, минимальными привилегиями и изолированными toolchain/rootfs. Переход должен сохранять внешний gRPC/S3-контракт и логику orchestration. Подбор capabilities, user namespaces и cgroup delegation внутри Docker не входит в MVP.

## 3. Контракт задания и gRPC

### 3.1. Данные задания

**REQ-07.** Задание должно содержать следующие данные. Названия полей предварительные; номера protobuf-полей, wire types остальных значений и правила валидации ещё не определены.

| Данные | Смысл и ограничения |
| --- | --- |
| `job_id` | Положительный `int64`: от `1` до `9223372036854775807`, задаётся мастером и возвращается без изменения |
| `language`, `language_version` | Проверка совместимости задания с единственным профилем агента; для MVP — строго `"cpp"` и `"23"` |
| `source` | Одна ссылка на исходный код: ключ S3 и ожидаемый SHA-256 |
| `tests[]` | Непустой упорядоченный набор тестов; каждый содержит заданный мастером `test_id` типа `int32` — порядковый номер теста в группе — и ссылку на входные данные по ключу и SHA-256 |
| `result_prefix` | Префикс выходных объектов, задаётся мастером |
| Compilation limits | Самостоятельные ограничения компиляции |
| Execution limits | Единый профиль ограничений, применяемый независимо к каждому тесту |

`test_id` должен быть положительным: от `1` до `2147483647`. Номера тестов должны быть уникальны внутри задания; в разных заданиях они могут повторяться. Задание должно содержать хотя бы один тест. Нулевые или отрицательные ID, повторяющиеся `test_id` и пустой набор тестов вызывают `INVALID_ARGUMENT`; задание не принимается. Агент возвращает `job_id` и `test_id` без изменения и не перенумеровывает тесты.

Агент обрабатывает именно переданный список тестов в порядке запроса. Полноту группы, отсутствие пропусков в номерах и их возрастание агент не проверяет; поднаборы и произвольный порядок положительных уникальных номеров допустимы. Агент не добавляет отсутствующие тесты, не сортирует и не перенумеровывает переданные. Например, список `8, 2, 5` обрабатывается в этом порядке с сохранением этих `test_id`. Правила ошибки компиляции и продолжения после ошибки отдельного теста сохраняются.

Один экземпляр агента обслуживает один конкретный компилятор. Поля `language` и `language_version` проверяют совместимость задания с его фиксированным профилем, а не выбирают компилятор внутри агента. Для MVP принимаются только `language = "cpp"` и `language_version = "23"`, с точным сравнением без алиасов и изменения регистра. Пустые и неподдерживаемые значения дают `INVALID_ARGUMENT` до принятия задания. `"23"` обозначает стандарт C++23; конкретная версия g++ определяется образом агента и ещё должна быть выбрана в Q-09. Версия g++ — внутренняя деталь образа агента: мастер не должен её знать или передавать. Отдельное поле версии компилятора в контракт задания не входит; валидация совместимости опирается на `language` и `language_version`.

Отдельные верхние пределы числа тестов и размера gRPC-запроса задания не вводятся: агент не должен отклонять корректный запрос по таким порогам. Настройки транспорта должны соответствовать этому решению. Непустой набор, положительные уникальные номера тестов и остальные согласованные правила валидации сохраняются. Это решение не отменяет resource limits компиляции и исполнения и согласуется с отсутствием отдельных лимитов размеров входных S3-объектов в разделе 5.

Bucket, команды запуска, compiler flags и `version_id` S3 в задании не выбираются. Оставшиеся правила валидации полей уточняются вместе с окончательным `.proto`, контрактом S3 (Q-07) и диапазонами resource limits (Q-05).

### 3.2. Принятие задания

**REQ-08.** API должен быть асинхронным. Имя RPC запуска — `StartJob`. Агент проверяет структуру нового задания, фиксирует его принятие и занятость ресурса и сразу возвращает подтверждение. Подтверждение не означает успешной компиляции или исполнения. После принятия работа продолжается независимо от завершения RPC и разрыва соединения.

Для долгоживущего агента действуют правила:

| Ситуация | Поведение |
| --- | --- |
| Ресурс свободен и новое задание прошло проверку | Принять задание и начать обработку |
| Выполняется задание с тем же `job_id` и одинаковым содержимым | Ответить «задание уже принято», повторно не исполнять |
| Готовый результат того же `job_id` ожидает чтения, содержимое запроса одинаково | Ответить «задание уже принято», повторно не исполнять |
| Тот же текущий `job_id`, но содержимое запроса изменено | Вернуть ошибку конфликта; принятое задание и его результат не изменять |
| Ресурс занят другим `job_id`, включая ожидание чтения | Ответить «ресурс занят» |
| Начата штатная остановка | Не принимать новые задания |

После выдачи результата или перезапуска агент не должен хранить историю ID. Когда ресурс свободен и приём заданий разрешён, запрос с ранее использованным `job_id` проходит обычную проверку и может запустить задание заново. Мастер должен выдавать новый `job_id` для каждого нового запуска. Защита от повторного исполнения действует только пока задание или его непрочитанный результат находятся у агента; постоянного реестра выполненных заданий нет.

Для повторного `StartJob` с текущим `job_id` агент должен сравнивать значения всех полей задания:

- `language` и `language_version`;
- ключ S3 и ожидаемый SHA-256 исходного файла;
- список `tests[]` с учётом количества и порядка тестов, включая `test_id`, ключ S3 и ожидаемый SHA-256 каждого входного файла;
- `result_prefix`;
- все лимиты компиляции и исполнения.

Для запроса, прошедшего проверку корректности согласно разделу 3.5, любое различие этих значений означает конфликт (`ALREADY_EXISTS`). Сравниваются разобранные значения полей, а не байты protobuf-сообщения. Для сравнения агент не должен повторно скачивать файлы из S3: используются ссылки и заявленные хеши принятого и повторного запросов. Эти правила действуют как во время выполнения, так и при ожидании чтения готового результата.

Семантика повторов, правила сравнения содержимого и ответы согласованы как часть Q-02; коды gRPC приведены в разделе 3.4. Окончательные типы полей и их представление определяются вместе с `.proto`.

### 3.3. Получение результата

**REQ-09.** Операция `GetResult` должна выдавать результат соответствующего задания. Если текущее задание с запрошенным ID ещё выполняется, она сразу отвечает «не завершено», не ожидает окончания внутри RPC и не меняет состояние или занятость ресурса. Если запрошенного задания нет, включая чужой ID или уже выданный результат, агент должен отвечать одинаково: «не найдено», не меняя состояние текущего задания.

При выдаче готового результата обработчик `GetResult` должен атомарно забрать результат из состояния агента и освободить ресурс **до отправки RPC-ответа**. Обработчик использует извлечённый результат для формирования ответа; в состоянии агента результата больше нет. Отдельного подтверждения мастера нет; повторное чтение выданного результата невозможно. S3-артефакты остаются. Коды gRPC приведены в разделе 3.4.

**REQ-10.** Принятие задания и переход при `GetResult` должны быть согласованы при конкурентных запросах: нельзя принять два задания одновременно или повторно выдать один сохранённый результат. При двух одновременных запросах готовый результат забирает только один обработчик; другой получает «не найдено», если задание с этим ID не было принято заново.

Обрыв соединения или потеря ответа после атомарного извлечения не должны восстанавливать результат или занятость ресурса. Повторный `GetResult` отвечает «не найдено», если задание с этим ID не было принято заново. Протокол не гарантирует доставку извлечённого результата мастеру; опубликованные S3-артефакты сохраняются. Это согласованная часть Q-02.

### 3.4. Имена RPC, ответы и коды gRPC

Согласованы имена `StartJob` и `GetResult` и следующее соответствие ситуаций ответам. Имена состояний в успешных ответах закрепляют семантику; окончательное protobuf-представление и номера полей ещё предстоит определить.

| RPC / ситуация | Код gRPC | Содержимое ответа |
| --- | --- | --- |
| `StartJob`: задание принято | `OK` | `Accepted` |
| `StartJob`: точный повтор текущего задания | `OK` | `AlreadyAccepted` |
| `StartJob`: текущий ID с изменённым содержимым | `ALREADY_EXISTS` | Описание конфликта |
| `StartJob`: агент занят другим заданием | `RESOURCE_EXHAUSTED` | «Агент занят» |
| `StartJob`: новое задание при остановке | `UNAVAILABLE` | «Агент останавливается» |
| Любой RPC: некорректный запрос | `INVALID_ARGUMENT` | Описание ошибки |
| `GetResult`: результат ещё не готов | `OK` | `NotReady` |
| `GetResult`: результат готов | `OK` | `Completed` и результат |
| `GetResult`: запрошенное задание отсутствует | `NOT_FOUND` | «Задание не найдено» |

`Completed` означает завершение обработки задания, включая ошибки компиляции или исполнения. Они отражаются внутри структурированного результата, а не меняют успешный код получения готового результата. `Accepted` и `AlreadyAccepted` также не означают успешности компиляции или тестов.

Соответствие использует [стандартные коды gRPC](https://grpc.io/docs/guides/status-codes/). При нескольких применимых условиях действует порядок из раздела 3.5.

### 3.5. Приоритет проверок RPC

`StartJob` должен выполнять проверки в следующем порядке, возвращая ответ по первому применимому условию:

1. Проверить корректность запроса; при ошибке вернуть `INVALID_ARGUMENT` независимо от занятости или остановки агента.
2. Если `job_id` совпадает с текущим, сравнить содержимое по разделу 3.2: вернуть `OK` с `AlreadyAccepted` либо `ALREADY_EXISTS`. Это правило действует и во время штатной остановки.
3. Если агент останавливается, вернуть `UNAVAILABLE`.
4. Если ресурс занят другим заданием, вернуть `RESOURCE_EXHAUSTED`.
5. Иначе атомарно принять задание и вернуть `OK` с `Accepted`.

Проверки текущего ID, остановки и занятости должны быть согласованы с фиксацией принятия и конкурентными переходами состояния согласно REQ-10. Между проверкой свободного ресурса и принятием нельзя допустить принятие второго задания или обойти начавшуюся штатную остановку.

Для `GetResult` сначала проверяется корректность запроса (`INVALID_ARGUMENT` при ошибке), затем наличие запрошенного задания (`NOT_FOUND` при отсутствии) и готовность результата (`OK` с `NotReady` либо атомарное извлечение и `OK` с `Completed`). Режим остановки не препятствует получению результата, пока gRPC-сервер работает.

Проверка корректности здесь относится к данным RPC-запроса. Скачивание файлов и проверка их содержимого по SHA-256 выполняются после принятия задания согласно REQ-11; правила валидации полей уточняются в Q-03.

### 3.6. Ответственность за deadlines RPC

Deadline исходящего RPC задаёт мастер. Конкретная длительность и её настройка относятся к мастеру и не задаются этой спецификацией или конфигурацией RunnerAgent. Значение по умолчанию для deadline на стороне агента не устанавливается.

Агент должен сохранять согласованное поведение при отмене RPC или истечении переданного deadline: уже принятое через `StartJob` задание продолжает выполняться, а уже извлечённый через `GetResult` результат не восстанавливается. Deadline RPC не является лимитом длительности задания и не заменяет таймаут ожидания результата при штатной остановке.

## 4. Состояние агента и жизненный цикл

### 4.1. Обработка задания

**REQ-11.** Orchestration должно выполнять следующий порядок действий:

1. Проверить запрос и состояние агента в порядке из раздела 3.5; если задание может быть принято, атомарно зафиксировать его принятие.
2. Создать workspace, получить исходный код и необходимые входные данные, проверить SHA-256 до использования файлов в sandbox.
3. Выполнить одну компиляцию с compilation limits в отдельном isolate box.
4. При успешной компиляции выполнить тесты по порядку, создавая отдельный execution sandbox для каждого запуска. Ошибка отдельного теста не прерывает обработку остальных.
5. Собрать результаты и загрузить доступные артефакты в S3, вычислив их SHA-256.
6. Сохранить структурированный результат отдельно от workspace и очистить временные файлы и isolate boxes. При ошибках также выполнить очистку; если сама очистка не удалась, сохранить результаты и их статусы, добавить инфраструктурную диагностику задания и перейти к завершению по разделу 4.4.
7. Ожидать `GetResult`, сохраняя ресурс занятым.
8. Атомарно забрать готовый результат из состояния агента и освободить ресурс до отправки RPC-ответа, затем отправить ответ; при остановке завершить процесс после обслуживания RPC. Обрыв соединения после извлечения не восстанавливает результат.

Порядок предварительного скачивания всех входов либо их получения перед каждым тестом не зафиксирован. Выбранная реализация должна сохранять продолжение набора при сбое загрузки входа отдельного теста.

Для описания долгоживущего агента используются следующие логические состояния; это не утверждённый transport enum:

| Состояние | Что хранится и выполняется | Переход |
| --- | --- | --- |
| Свободен | Нет текущего задания и непрочитанного результата | Принятие задания → обработка |
| Обработка | Задание принято; выполняются подготовка, компиляция, тесты, публикация и очистка | Готовность результата → ожидание чтения |
| Ожидание чтения | Результат хранится отдельно от workspace после успешной очистки либо её ошибки с переходом к завершению | Выдача через `GetResult` → свободен либо завершение при остановке |
| Завершён | Процесс остановлен; состояние в памяти утрачено | При новом запуске восстановление задания не выполняется |

Штатная остановка — отдельный режим, запрещающий принятие новых заданий в состояниях обработки и ожидания. Он описан ниже.

**REQ-12.** Во время обычной работы долгоживущего агента ожидание `GetResult` не ограничено таймаутом. Непрочитанный результат не истекает и удерживает ресурс независимо от длительности отсутствия мастера. Завершение вычислений или очистка sandbox сами по себе ресурс не освобождают.

**REQ-13.** Для MVP задание и непрочитанный результат хранятся в памяти. Их потеря при перезапуске допустима; сохранение на диск, восстановление и возобновление не требуются. Решение о повторном запуске принимает мастер. Опубликованные S3-артефакты не зависят от памяти процесса.

### 4.2. Штатная остановка

**REQ-14.** При запросе штатной остановки агент должен прекратить принятие новых заданий, завершить текущий набор, опубликовать доступные артефакты, очистить sandbox/workspace и сохранить готовый результат для `GetResult`.

Ожидание получения результата при остановке настраивается; значение по умолчанию — **30 секунд**. Отсчёт начинается после готовности результата, публикации артефактов и очистки; при ошибке очистки действует раздел 4.4. Если результат уже готов, отсчёт начинается при запросе остановки. Выполнение задания не расходует этот таймаут.

В течение ожидания gRPC остаётся доступным для `GetResult`. Если результат забран, агент завершает обслуживание RPC, затем останавливает сервер и процесс. Если таймаут истёк, агент выходит с потерей непрочитанного результата в памяти, сохраняя опубликованные S3-артефакты. При отсутствии задания и результата агент может завершиться сразу.

Настройки остановки приложения и контейнера должны позволять завершить задание и затем выдержать ожидание результата. Принудительное или аварийное завершение может привести к допустимой потере состояния. Внутренний `CancellationToken` не означает наличие `CancelJob`; отключение клиента и начало штатной остановки сами по себе не отменяют принятое задание.

### 4.3. Выбранный жизненный цикл (Q-01 закрыт)

Для MVP выбран долгоживущий агент, обрабатывающий одно задание за раз. Контейнер запускается при развёртывании и используется для нескольких заданий. После выдачи результата через `GetResult` агент должен оставаться запущенным и быть готовым принять следующее задание, если не начата штатная остановка. Завершение одного задания не требует пересоздания контейнера или процесса агента. Отдельные sandbox и очистка после обработки сохраняются согласно REQ-02 и REQ-11. Контейнер на один набор тестов в MVP не входит; компонент управления контейнерами для отдельных заданий не требуется. Автоматический CI-деплой по-прежнему не планируется.

### 4.4. Очистка при запуске и после задания (Q-10 закрыт)

До приёма заданий агент должен очистить оставшиеся собственные workspace и isolate boxes, включая остатки после падения. Чужие рабочие области и boxes очистке не подлежат. Если начальная очистка не удалась, агент завершает запуск с ошибкой и не принимает задания. Очистка не восстанавливает потерянные задания и результаты.

Если очистка после задания не удалась, агент сохраняет результаты компиляции и тестов, их статусы и общий статус задания, добавляя инфраструктурную диагностику очистки на уровне задания. Он прекращает приём новых заданий и переходит в режим завершения. `GetResult` остаётся доступным в пределах таймаута ожидания результата из REQ-14, по умолчанию 30 секунд. В этом случае отсчёт начинается после подготовки готового результата с диагностикой и завершения попыток публикации и очистки, включая неуспешную попытку очистки; успешное удаление остатков не является условием начала ожидания.

После обслуживания `GetResult` либо истечения таймаута агент завершает процесс. Получение результата не возвращает его к приёму заданий; потенциально неочищенная среда не используется повторно в этом процессе. Новый запуск обязан пройти начальную очистку. Локальная очистка не удаляет опубликованные S3-артефакты. Механизм определения собственных каталогов и boxes задаётся вместе с workspace, box IDs и конфигурацией в Q-09/Q-11.

## 5. S3 и целостность файлов

**REQ-15.** Конфигурация агента должна задавать два bucket:

| Роль | Bucket | Ссылка во входном задании или результате |
| --- | --- | --- |
| Исходный код | Отдельный bucket исходного кода | Входные `key` и ожидаемый `sha256` |
| Вход теста | Общий bucket данных и артефактов | Входные `key` и ожидаемый `sha256` |
| Stdout и stderr компилятора | Общий bucket данных и артефактов | Отдельные фактические выходные `key` и вычисленный `sha256` каждого потока |
| Stdout и stderr тестов | Общий bucket данных и артефактов | Фактические выходные `key` и вычисленный `sha256` |

Bucket создаются заранее при развёртывании. Агент их не создаёт и не меняет их настройки. Bucket выбирается агентом по роли объекта. Для выходных файлов ключи формируются внутри `result_prefix` мастера с согласованными суффиксами:

| Артефакт | Путь внутри `result_prefix` |
| --- | --- |
| Stdout компилятора | `compilation/stdout.txt` |
| Stderr компилятора | `compilation/stderr.txt` |
| Stdout теста | `tests/{test_id}/stdout.txt` |
| Stderr теста | `tests/{test_id}/stderr.txt` |

В ключах используется исходный номер теста. Мастер должен выдавать новый `result_prefix` для каждого запуска, включая повторное выполнение задания. Агент не ведёт реестр использованных префиксов и не выполняет дополнительных проверок существования выходных объектов; загрузка может перезаписать объект по тому же ключу, если мастер повторно использовал префикс. Уникальность обеспечивает мастер. Агент возвращает фактические ссылки на опубликованные объекты.

Входные `key` и `result_prefix` должны быть непустыми; пустое значение даёт `INVALID_ARGUMENT`. Завершающий `/` в `result_prefix` допускается. При формировании выходного ключа между префиксом и согласованным суффиксом добавляется `/`, только если префикс ещё не заканчивается `/`. S3-ключи не используются как локальные пути; размещение локальных файлов определяет агент.

Отдельные лимиты размеров исходного файла и входных файлов тестов не вводятся. Resource limits компиляции и исполнения сохраняются.

**REQ-16.** После скачивания входного объекта агент должен проверить SHA-256 до помещения файла в sandbox. Несовпадение hash — ошибка подготовки; такой файл не запускается и не используется при компиляции. ETag не заменяет SHA-256. Контракт не использует `version_id` и не требует включения S3 versioning. Для выходных артефактов агент вычисляет и возвращает SHA-256.

`sha256` передаётся как массив ровно из 32 байт хеша, одинаково для входных ссылок и выходных артефактов; в protobuf используется `bytes`. Текстовое hex-представление не используется. Неверная длина входного `sha256` является ошибкой валидации запроса (`INVALID_ARGUMENT`); несовпадение корректно заданного хеша с содержимым скачанного объекта является ошибкой подготовки согласно REQ-16. При сравнении повторных заданий сравнивается содержимое массивов байт.

**REQ-17.** Политикой повторов скачивания и загрузки MinIO управляет агент. Для каждой операции допускается не более трёх попыток всего, включая первую; задержки перед второй и третьей — 200 мс и 500 мс соответственно. Автоматические повторы `AWSSDK.S3` отключаются, включая дополнительные механизмы повторов выбранной версии SDK; скрытые повторы не должны увеличивать число попыток.

Повторяются обрывы соединения, сетевые таймауты, HTTP `429`, `500`, `502`, `503`, `504` и S3 `SlowDown`. Неудачное скачивание начинается заново, частичные данные предыдущей попытки не используются. Отсутствие объекта или bucket, отказ в доступе, неверные credentials и несовпадение SHA-256 не повторяются. Отмена самой storage-операции прекращает попытки; отмена RPC по-прежнему не отменяет принятое задание. Прочие ошибки не повторяются, если они не относятся к согласованному перечню временных ошибок.

После исчерпания попыток или неповторяемой ошибки фиксируется инфраструктурная ошибка соответствующей стадии. Ошибка отдельного теста не останавливает остальные тесты. Конкретная библиотека/реализация policy выбирается при реализации без изменения этой семантики.

При неуспешной публикации одного артефакта агент должен продолжить загрузку остальных. Успешно опубликованные объекты не удаляются; результат содержит доступные ссылки и диагностику ошибок по правилам раздела 8. Выходной объект с неуспешной публикацией нельзя обозначать как успешно доступный. Повтор загрузки одного артефакта использует тот же ключ и то же содержимое в рамках согласованного бюджета попыток.

Агент не удаляет опубликованные артефакты, в том числе при частичной публикации, выдаче результата или локальной очистке. Срок хранения и удаление относятся к мастеру или lifecycle-политике MinIO. Решения по S3-контракту закрывают Q-07; оставшиеся параметры клиента уточняются в Q-08, credential provider и политика повторов согласованы в REQ-06 и REQ-17.

## 6. Sandbox и профиль языка

**REQ-18.** Компилятор обрабатывает недоверенный исходный код и должен запускаться в собственном sandbox с отдельными лимитами. В execution sandbox каждого теста передаются только необходимый исполняемый артефакт и разрешённые файлы. Рабочие файлы одного теста не должны передаваться следующему.

**REQ-19.** Для обеих стадий должны соблюдаться следующие ограничения:

- Нет доступа к сети, управляющим endpoint и S3/AWS credentials.
- Окружение формируется по allowlist: `PATH`, при необходимости `LANG` и согласованные переменные языка. Секреты не наследуются процессом isolate, компилятором или решением.
- Перед каждым запуском isolate агент полностью очищает окружение дочернего процесса и задаёт разрешённые значения явно. В sandbox запрещены `--full-env` и наследование секретных переменных; фильтрации только известных `AWS_*` недостаточно. Credentials не передаются в аргументах, рабочих файлах, mounts, логах или результатах. Из sandbox должны быть недоступны окружение и файлы процесса агента, включая `/proc/<agent-pid>/environ`, `/proc/<agent-pid>/root` и `/proc/<agent-pid>/fd`. Эти свойства проверяются отдельно для компиляции и исполнения; конкретные mounts/права выбираются в Q-09 так, чтобы обеспечить данное требование.
- Доступны только необходимые локальные файлы и разрешённые mounts. Рабочая область агента и другие задания недоступны.
- Исходный код, stdin, stdout/stderr и вывод компилятора передаются через локальные файлы под управлением агента.
- Workspace и isolate box привязаны к заданию/стадии и очищаются после завершения, ошибки или управляемой остановки. Ожидание чтения результата не требует сохранять sandbox.

**REQ-20.** Учёт compilation и execution должен быть раздельным. Память и процессы агента не должны включаться в потребление решения.

**REQ-21.** Один экземпляр агента должен обслуживать один конкретный компилятор с фиксированным профилем: версией toolchain, командами компиляции/запуска, всеми флагами, файлами и окружением. Для MVP это g++ с C++23. Мастер передаёт данные для проверки совместимости с профилем агента и resource limits, но не выбирает компилятор внутри агента и не задаёт произвольные команды или дополнительные compiler flags. Реализация language provider задаётся на стороне агента и регистрируется явно; первый provider использует g++.

Согласованная команда профиля: `g++ -std=c++23 -O2 -pipe -DONLINE_JUDGE` с явно заданными исходником и выходным файлом. Используется динамическая линковка; необходимые библиотеки доступны в execution sandbox только для чтения. Конкретная версия g++ фиксируется в образе при реализации.

Системные файлы и toolchain доступны по разрешённому списку только для чтения. Запись разрешена в собственные рабочие и временные каталоги стадии. Процессы компилятора/решения работают без root; окружение, файловые дескрипторы и mounts не раскрывают ресурсы агента. Экземпляры получают непересекающиеся workspace, box IDs и cgroups. Конкретные rootfs/mounts, права и делегирование подбираются и проверяются при реализации без ослабления REQ-19.

Для MVP обязательны cgroups v2. До приёма заданий агент должен проверить доступность контроллеров и метрик, необходимых для согласованных лимитов и результатов, включая `memory.peak`, управление swap/OOM и `pids.max` / `pids.events`. Если среда не позволяет обеспечить эти требования, запуск завершается с ошибкой без принятия заданий; переход к менее точному режиму не допускается.

Swap для песочницы должен быть отключён. При OOM завершается вся группа процессов песочницы, чтобы дочерние процессы не продолжали выполнение после гибели основного.

Версии g++ и isolate, конкретные rootfs/mounts, права, идентификаторы box и делегирование cgroups фиксируются при реализации по согласованным выше правилам. Поведение очистки после падения определено в разделе 4.4; механизм определения собственных workspace/boxes уточняется с окружением. Изоляцию нельзя считать обеспеченной одним фактом использования isolate.

## 7. Лимиты и измерения

**REQ-22.** Агент должен различать следующие ограничения; имена полей предварительные:

| Лимит | Поле | Единица и смысл |
| --- | --- | --- |
| CPU time | `cpu_time_ms` | Суммарные миллисекунды процессорного времени всех процессов и потоков песочницы |
| Wall time | `wall_time_ms` | Миллисекунды реального времени |
| Memory | `memory_bytes` | Память всей cgroup песочницы в байтах, включая учитываемый ядром файловый кеш |
| Stdout | `stdout_bytes` | Отдельный максимальный размер stdout в байтах |
| Stderr | `stderr_bytes` | Отдельный максимальный размер stderr в байтах |
| Processes | `processes` | Общее допустимое число процессов и потоков песочницы, включая основной |

Compilation и execution имеют самостоятельные наборы лимитов. Мастер должен явно передавать оба профиля и все значения в каждом из них. Все значения положительные; отсутствие профиля или обязательного значения, ноль и отрицательные значения дают `INVALID_ARGUMENT`. Значений по умолчанию и обозначения «без ограничений» нет. Поля времени в миллисекундах и размеров в байтах имеют тип `int64`, поле `processes` — `int32`. Значение, которое невозможно корректно применить в выбранной реализации песочницы, должно отклоняться через `INVALID_ARGUMENT` до принятия задания.

Stdout и stderr компилятора разделены: каждый поток имеет собственный лимит `stdout_bytes` / `stderr_bytes`, отдельный локальный файл и отдельный S3-артефакт (`compilation/stdout.txt` / `compilation/stderr.txt`). Объединённый журнал и отдельный `log_bytes` не используются. Согласованные правила публикации вывода компилятора применяются к каждому потоку отдельно: сбой публикации одного не скрывает успешно опубликованный другой. При превышении любого из двух лимитов агент останавливает компиляцию, сохраняет оба частичных потока в пределах их собственных лимитов и не запускает тесты. Общий статус задания — `CompilationError`, причина завершения — `OutputLimitExceeded`, если нет другого подтверждённого нарушения с более высоким приоритетом.

CPU и память учитываются суммарно для всей песочницы, включая дочерние процессы и потоки, с использованием cgroups. `processes` включает основной процесс и все дочерние процессы/потоки. Память ограничивается для всей cgroup; результат возвращает её пиковое потребление в байтах, включая учитываемый ядром файловый кеш. Метрика лимита и результата едина. CPU time не заменяет wall time: ожидание и блокировка могут расходовать реальное время без значительного CPU time.

Запрошенный `memory_bytes` округляется вверх до ближайшего значения, кратного размеру страницы памяти хоста. В результате соответствующей стадии возвращается фактически применённый лимит памяти; исходное значение запроса не изменяется и используется при сравнении повторов `StartJob`. Округление выполняется с проверкой переполнения; невозможность корректно применить значение даёт `INVALID_ARGUMENT`. Пиковое потребление читается из `memory.peak` cgroup этой стадии до её удаления. Гранулярность памяти и семантика пика описаны в [документации cgroups v2](https://docs.kernel.org/admin-guide/cgroup-v2.html#memory).

Лимит числа процессов/потоков применяется через `pids.max`, а его нарушение подтверждается событием `pids.events`, относящимся к текущему запуску песочницы. Заблокированная попытка создать лишний процесс или поток фиксирует `ProcessLimitExceeded`, даже если программа обработала отказ и вернула код 0. При обнаружении нарушения агент останавливает оставшиеся процессы песочницы; основная причина выбирается с учётом общего приоритета подтверждённых нарушений. Интерфейс описан в [документации PID-контроллера](https://docs.kernel.org/admin-guide/cgroup-v2.html#pid).

Execution limits применяются отдельно к каждому тесту, не к сумме потребления набора. Отдельный общий предел длительности задания не вводится (Q-06 закрыт). Сохраняются лимиты компиляции и каждого теста; deadline RPC и таймаут ожидания результата при остановке не ограничивают длительность задания. Конкретные границы применимости значений и преобразование единиц для выбранной версии isolate ещё уточняются в Q-05.

При нескольких подтверждённых нарушениях основная причина завершения выбирается в порядке: `MemoryLimitExceeded` → `OutputLimitExceeded` → `CpuTimeLimitExceeded` → `WallTimeLimitExceeded` → `ProcessLimitExceeded` → `RuntimeError`. Остальные обнаруженные причины сохраняются в диагностике. Превышение лимита должно подтверждаться данными о нарушении; один сигнал завершения сам по себе не является достаточным основанием для такого verdict. Инфраструктурные ошибки отражаются отдельно согласно разделу 8.4, не стирая известную причину завершения процесса.

**REQ-23.** При превышении отдельного лимита stdout или stderr агент должен остановить процесс с `OutputLimitExceeded`, если нет другого подтверждённого нарушения с более высоким приоритетом. Уже полученная часть каждого потока сохраняется и публикуется в пределах собственного лимита. Сумма размеров потоков не заменяет проверку каждого из них. Для execution после этого обработка остальных тестов продолжается; для compilation действуют описанные выше `CompilationError` и отсутствие запусков тестов.

CPU учитывается по всей cgroup стадии, wall time измеряется монотонными часами за время исполнения процесса. Причины превышений подтверждаются измерениями и событиями соответствующей песочницы; сигнал сам по себе доказательством не считается. Преобразования единиц проверяются на переполнение; неприменимые значения отклоняются до принятия задания. Точные технические границы и mapping для выбранной версии isolate фиксируются и проверяются тестами при реализации, с сохранением согласованного приоритета причин и правил инфраструктурных ошибок.

## 8. Результат и обработка ошибок

### 8.1. Состав результата

**REQ-24.** Структурированный результат должен содержать:

| Уровень | Данные |
| --- | --- |
| Задание | Исходный `job_id`, итоговый статус, стадия возникновения ошибки, результат единственной компиляции, коллекция результатов тестов, отдельная инфраструктурная диагностика задания |
| Компиляция | Статус/причина прекращения, CPU time, wall time, peak memory всей cgroup, exit code и signal при наличии, отдельные ссылки на опубликованные stdout/stderr компилятора, доступная инфраструктурная диагностика |
| Тест | Исходный `test_id`, итоговый статус теста, отдельно результат исполнения (verdict/причина прекращения, CPU time, wall time, peak memory, exit code и signal при наличии), ссылки на опубликованные stdout/stderr, отдельная инфраструктурная диагностика |
| Артефакт | Фактическая ссылка на опубликованный объект и вычисленный SHA-256 |

Отсутствующие exit code/signal должны представляться явно отсутствующими, а не фиктивным нулём. Для инфраструктурных ошибок сохраняются известные метрики и доступные артефакты; отсутствующие данные не подменяются успешным результатом. Если компиляция не начиналась, её результат должен быть явно отсутствующим. Если данные компиляции появились до инфраструктурного сбоя, они сохраняются в доступном объёме.

Результаты компиляции и исполнения содержат фактически применённый лимит памяти с учётом округления, когда он был установлен. Если после запуска не удалось получить обязательные данные, необходимые для корректного результата, фиксируется инфраструктурная ошибка соответствующей стадии или теста. Доступные сведения сохраняются, недостающие не заменяются нулями или успехом. Допустимое отсутствие необязательных полей, например signal при нормальном выходе, само по себе не является ошибкой метрик.

Для процесса компиляции и процесса решения согласован набор причин завершения: `Success`, `RuntimeError`, `CpuTimeLimitExceeded`, `WallTimeLimitExceeded`, `MemoryLimitExceeded`, `OutputLimitExceeded`, `ProcessLimitExceeded`. Основная причина выбирается по правилам раздела 7. Неуспешный исход процесса компиляции даёт общий `CompilationError` с конкретной причиной; инфраструктурные сбои обрабатываются отдельно и не подменяются ошибкой компиляции кода. Согласованы общий статус задания `InfrastructureError` для сбоев подготовки исходника или компиляции из-за инфраструктуры и итоговый статус теста `InfrastructureError` при инфраструктурном сбое этого теста. Mapping конкретных данных isolate/cgroups на эти причины ещё требуется определить; состав причин не означает, что mapping уже реализован или проверен.

### 8.2. Общий статус после обработки набора

Если компиляция успешна и каждый переданный тест получил результат, общий статус задания должен быть `Completed`. Статусы отдельных тестов сохраняются независимо: успешное исполнение, ошибка исполнения, превышение лимита или инфраструктурная ошибка теста не меняют этот общий статус. `Completed` означает, что агент закончил обработку набора, а не что решение прошло проверку. AC/WA по-прежнему определяет мастер.

Например, если один тест выполнен, второй превысил время, а для третьего не удалось скачать вход, задание получает `Completed` и три соответствующих результата тестов. Результат инфраструктурной ошибки теста учитывается как результат обработки, даже если процесс решения для этого теста не запускался.

Общий статус задания следует отличать от одноимённого состояния ответа `GetResult`: RPC возвращает `Completed` при любом готовом результате, в том числе с общим статусом `CompilationError` или `InfrastructureError`. Общий статус задания `Completed` относится к успешной компиляции и обработанному набору, как описано выше.

### 8.3. Поведение при ошибках

**REQ-25.** Ошибки должны обрабатываться согласно следующей таблице:

| Событие | Требуемое поведение |
| --- | --- |
| Компиляция успешна, каждый переданный тест получил результат | Общий статус `Completed` независимо от статусов отдельных тестов; сохранить все их результаты |
| Ошибка компиляции | Итоговый статус `CompilationError`, данные компиляции и вывод компилятора; тесты не запускаются, коллекция результатов тестов пуста |
| Ошибка публикации вывода компилятора | Сохранить данные компиляции, записать инфраструктурную ошибку на уровне задания и не возвращать ссылку на неопубликованный поток. При успешной компиляции продолжить тесты и после обработки набора вернуть общий `Completed`; при ошибке компиляции сохранить общий `CompilationError` и пустой список тестов |
| Runtime error или превышение лимита теста | Сохранить verdict, метрики и доступные артефакты; продолжить остальные тесты |
| Сбой скачивания входа, запуска isolate или публикации артефактов отдельного теста | Итоговый статус теста `InfrastructureError`; отдельно сохранить известный результат исполнения и инфраструктурную диагностику; продолжить набор |
| Общая ошибка подготовки исходного кода или невозможность компиляции из-за инфраструктуры | Итоговый статус `InfrastructureError`, стадия и причина сбоя; тесты не запускаются, коллекция результатов тестов пуста; доступные данные компиляции сохраняются, а если она не начиналась — результат компиляции явно отсутствует |
| Перезапуск или падение процесса до выдачи результата | Потеря состояния допустима для MVP; опубликованные S3-артефакты сохраняются |

К общим инфраструктурным ошибкам до тестов относятся, например, сбой скачивания исходного файла, несовпадение его SHA-256 или невозможность запустить isolate для компиляции. Фиктивные результаты невыполненных тестов не создаются. Обычная ошибка компиляции исходного кода по-прежнему даёт `CompilationError`; сбой инфраструктуры не должен подменяться этой категорией.

Ошибка публикации вывода компилятора не меняет известный исход компиляции и сама по себе не блокирует исполнение тестов после успешной компиляции. Она сохраняется как инфраструктурная диагностика задания, независимо от общего `Completed` или `CompilationError`; данные компиляции не теряются, отсутствующая ссылка не подменяется ожидаемым ключом объекта.

Сбой storage не должен маскироваться под ошибку программы участника. Общий статус при смешанных результатах тестов определён в разделе 8.2, совместное представление ошибки исполнения и инфраструктуры отдельного теста — в разделе 8.4. Приоритет подтверждённых причин определён в разделе 7; mapping конкретных данных isolate/cgroups ещё уточняется; поведение при ошибках очистки описано в разделе 4.4; продолжение частичной публикации и хранение объектов описаны в разделе 5.

Финальный результат, включая ошибку компиляции или инфраструктуры, выдаётся через `GetResult` и освобождает ресурс по общим правилам, если процесс агента сохранился до выдачи.

### 8.4. Результат исполнения и инфраструктурная ошибка теста

При инфраструктурной ошибке теста его итоговый статус должен быть `InfrastructureError`, даже если процесс решения уже завершился с известным verdict. Результат исполнения сохраняется отдельно и не заменяется инфраструктурной ошибкой: например, ошибка исполнения и последующий сбой публикации stdout дают итоговый `InfrastructureError`, отдельный результат исполнения с `RuntimeError`, известными метриками, exit code и signal и диагностику сбоя публикации stdout.

Если процесс решения вообще не запускался, результат исполнения должен быть явно отсутствующим. Если запуск состоялся, сохраняются известные данные, а неизвестные значения не подменяются успешным результатом. Ссылки возвращаются только на успешно опубликованные артефакты; ошибка одного артефакта не скрывает ссылки на другие успешно опубликованные артефакты.

После инфраструктурной ошибки теста обработка остальных тестов продолжается. Если компиляция успешна и каждый тест получил результат, общий статус задания остаётся `Completed` согласно разделу 8.2. Окончательное protobuf-представление раздельных полей определяется в Q-02.

## 9. Компоненты и внутренние контракты

**REQ-26.** Реализация должна сохранять следующие логические границы. Они не требуют отдельного assembly на каждый компонент.

| Компонент | Ответственность |
| --- | --- |
| `Grpc` / `JudgeRunnerService` | Принятие запросов, преобразование transport models, выдача результата |
| Orchestration | Состояние задания в памяти, занятость до чтения, независимая от RPC обработка, координация storage/workspace/runner и публикации |
| `Storage` / `IObjectStorage`, `S3ObjectStorage` | Получение и публикация S3-объектов, метаданные хранилища |
| `Execution` / `ISubmissionRunner`, `IsolateSubmissionRunner` | Локальная компиляция и execution pipeline, преобразование isolate metadata |
| `Languages` / `ILanguageProvider`, `CppLanguageProvider` | Единственный профиль компилятора экземпляра агента, проверка совместимости задания, toolchain, команды, файлы и окружение |
| `Workspace` / `WorkspaceManager` | Создание рабочих областей, размещение локальных файлов и очистка |

`IsolateSubmissionRunner` не должен зависеть от gRPC или S3. Он получает локальное задание с одним файлом исходного кода и набором тестов и возвращает локальные результаты и пути артефактов. Финальный внутренний контракт должен явно представлять отдельные compilation/execution limits. Точная сигнатура и распределение операций получения входов между orchestration и runner пока не определены.

Выделение низкоуровневого `ISandboxRunner` возможно как деталь реализации. Дополнительные языки должны добавляться без переноса логики gRPC/S3 в runner.

**REQ-27.** Разработка начинается с .NET 10 JIT. Код должен учитывать целевую Native AOT publication: статически известные типы, сгенерированные protobuf-модели, явная регистрация providers, `System.Text.Json` source generation при необходимости JSON; без runtime plugins, dynamic loading и ненужной reflection-heavy сериализации.

Проверка `PublishAot=true` и trimming/AOT warnings планируется при появлении реализации. Совместимость конкретных gRPC-библиотек и `AWSSDK.S3` с AOT не доказана. Переход production-образа на AOT требует проверки gRPC, S3, isolate и результатов на целевой Linux-платформе. AOT не заменяет sandbox; compiler/runtime поддерживаемого языка остаётся самостоятельной частью образа.

MVP остаётся на JIT. В CI предусматривается отдельная информационная проверка AOT: её неуспех виден в результатах, но не блокирует рабочий JIT-образ. Переход production на AOT допускается после успешной сборки и полного набора интеграционных тестов AOT-варианта, включая platform/OpenTelemetry; совместимость не считается доказанной заранее.

## 10. Конфигурация и эксплуатация

Обычные параметры задаются в `appsettings.json`; переменные окружения переопределяют значения файла. Credentials читаются только из окружения по REQ-06 и в файл не записываются. Параметры хранилища группируются в секции `S3`, workspace и остановки — в `Runner`; platform/OpenTelemetry сохраняют собственные имена настроек, включая `SERVICE_NAME`. Конфигурация фиксируется при запуске: для её изменения нужен перезапуск, горячая перезагрузка не предусматривается. Точные имена оставшихся параметров внутри секций ещё выбираются.

Корневой каталог workspace задаётся конфигурацией; по умолчанию — `/var/lib/runner-agent`. Агент создаёт внутри собственные рабочие каталоги. S3-ключи не преобразуются в локальные пути. Правила начальной очистки только собственных рабочих областей сохраняются; механизм владения каталогами и isolate boxes уточняется в Q-09.

Из согласованных требований следуют следующие категории настроек:

| Настройка | Зафиксированная семантика |
| --- | --- |
| gRPC endpoint и порт | HTTP/2 без TLS и аутентификации в доверенной внутренней сети; по умолчанию `0.0.0.0:8080` внутри контейнера, адрес и порт настраиваются |
| MinIO endpoint | Задаётся конфигурацией агента; `ForcePathStyle = true` |
| Регион подписи MinIO | По умолчанию `us-east-1`, можно переопределить; сервер без явно заданного региона поддерживается |
| Имя сервиса телеметрии | Имя различает язык и версию языка: для C++23 — `SERVICE_NAME=runner-agent-cpp-23`; другие языковые профили используют другие имена. Экземпляры одного профиля различаются по `service.instance.id` |
| Экспорт телеметрии | Адрес коллектора и параметры экспорта задаются при развёртывании средствами platform/OpenTelemetry |
| Bucket исходного кода | Отдельный от данных тестов и результатов |
| Общий bucket | Входы тестов и выходные артефакты |
| Credential provider | Только окружение агента: `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, необязательный `AWS_SESSION_TOKEN`; без fallback, с изоляцией секретов по REQ-19 |
| Workspace и isolate | Корень workspace настраивается в `Runner`, по умолчанию `/var/lib/runner-agent`; структура собственных каталогов, mounts, box IDs и cgroups требуют выбора |
| Профиль C++23 | Контролируемые агентом команды, флаги и окружение; конкретное содержимое требует выбора |
| Таймаут получения результата при завершении | Настраиваемый, по умолчанию 30 секунд; не действует при обычной работе долгоживущего агента |

Resource limits задания поступают от мастера; это не разрешение менять профиль toolchain. Способ задания host/container limits и их согласования с isolate ещё требует проработки.

**REQ-28.** Runtime credentials должны задаваться при развёртывании агента. Токены registry и S3 credentials не записываются в Dockerfile, build args или слои образа. При необходимости приватного NuGet используются BuildKit secret mounts; наличие такой зависимости пока не установлено.

Для логирования и OpenTelemetry выбран [Texnokaktus.ProgOlymp.Platform](https://github.com/Texnokaktus-ProgOlymp/platform). Сохраняется его стандартное текстовое логирование в stdout; требование JSON-формата отменено. OpenTelemetry подключается через platform, использующую [Texnokaktus.ProgOlymp.OpenTelemetry](https://github.com/Texnokaktus-ProgOlymp/OpenTelemetry-Library), без повторной независимой регистрации тех же providers/exporters.

По изученному исходному коду platform на 2 октября 2026 года точка подключения — `WebApplicationBuilder.UsePlatform()`, обязательна переменная `SERVICE_NAME`; доступны `ConfigureOpenTelemetry.WithTracerConfiguration`, `WithMeterConfiguration` и `ConfigureSerilog.ConfigureSerilog`. Пакет ориентирован на `net10.0` и настраивает Serilog Console и OpenTelemetry. Это описание API зависимости, а не уже реализованной интеграции RunnerAgent. Версия пакета, источник пакетов и AOT-совместимость проверяются при создании приложения; согласованная семантика наблюдаемости приведена ниже, точные имена инструментов и технические детали инструментации ещё выбираются.

Логи сохраняют контекст `job_id`, для событий конкретного теста — также `test_id`, стадию и причину ошибки, когда они применимы. Секреты, исходники, входные данные и содержимое stdout/stderr, включая потоки компилятора, не включаются в служебные логи и экспортируемую телеметрию. Это ограничение распространяется и на сообщения исключений/библиотек и обогащение логов; публикация потоков как S3-артефактов сохраняется. Стандартный текстовый шаблон не обязан отображать все структурированные свойства контекста.

Проверка работоспособности использует стандартный gRPC Health Checking на существующем gRPC-порту без отдельного HTTP endpoint. После успешной локальной инициализации API имеет статус `SERVING`; выполнение задания и ожидание выдачи результата его не меняют. Занятость определяется ответом `StartJob`; недоступность MinIO сама по себе health-статус не меняет. До готовности API статус `SERVING` не публикуется. При остановке и завершении после ошибки очистки API остаётся `SERVING`, пока завершается принятое задание и обслуживается `GetResult`; новые задания отклоняются по согласованным правилам. `NOT_SERVING` выставляется непосредственно перед остановкой RPC-сервера, чтобы health-проверка не препятствовала получению результата. Этот статус описывает доступность API, а не наличие свободного ресурса для нового задания.

Код завершения процесса — `0` при штатной остановке, включая истечение согласованного ожидания результата; `1` при ошибке запуска или завершении из-за невозможности очистить sandbox. Ошибки компиляции, тестов и отдельные сбои storage сами по себе не завершают агент. При ошибке очистки сохраняются правила выдачи результата и завершения из раздела 4.4. Это коды управляемого завершения; принудительное внешнее завершение ими не нормализуется.

Ручной деплой предполагает выбор проверенного образа по тегу версии, подготовку Linux judge-host, bucket, конфигурации, credentials и workspace, запуск контейнера с долгоживущим агентом и контрольное задание C++ с получением результата. Точная команда запуска, проверка готовности сервиса, оставшиеся настройки логирования, метрики, эксплуатационные лимиты и аварийная очистка должны быть описаны после выбора среды. Численные требования к пропускной способности, доступности и задержке API в источниках отсутствуют.

Трассировка принятого задания включает отдельную операцию на всю обработку и стадии подготовки, компиляции, тестирования и публикации. Завершение или отмена RPC `StartJob` не завершает операцию обработки задания и не отменяет её стадии. `SERVICE_NAME` задаётся при развёртывании и различает язык и версию языка профиля агента: в `runner-agent-cpp-23` суффикс `cpp-23` означает C++23, а не версию g++ или сборки агента. Агенты других языков или версий языка получают другие `SERVICE_NAME`; экземпляры одного профиля различаются по `service.instance.id`. Это правило именования будущих профилей, а не расширение языков текущего MVP. Адрес коллектора и параметры экспорта задаются при развёртывании средствами platform/OpenTelemetry.

Собственные метрики агента: количество заданий по исходу, длительность стадий, ошибки и повторы storage. `job_id` и `test_id` сохраняются в логах и трассах и не используются как метки метрик. Точные имена инструментов, единицы, остальные поля и техническая связь контекстов уточняются при реализации; согласованная семантика не зависит от этих имён.

## 11. Репозиторий и поставка

**REQ-29.** Согласованы solution `.slnx`, production-код в `src/`, тесты в `tests/`, workflows в `.github/workflows/`, корневой `Directory.Build.props` и CPM в `Directory.Packages.props`. Вложенные `Directory.Build.props` должны явно импортировать родительские настройки. Общие тестовые зависимости относятся к `tests/`, а `InternalsVisibleTo` для соответствующего `.Tests` и `DynamicProxyGenAssembly2` задаётся в `src/Directory.Build.props`.

**REQ-30.** Тесты должны использовать NUnit на Microsoft.Testing.Platform с нативным MTP-режимом `dotnet test` в .NET 10. Версия SDK и `test.runner=Microsoft.Testing.Platform` задаются через `global.json`; настройки NUnit runner и MTP-расширения coverage/TRX — через `tests/Directory.Build.props`. Общие зависимости включают NUnit и NSubstitute. Версии пакетов и SDK patch ещё не выбраны.

**REQ-31.** GitHub Actions должен собирать и тестировать приложение, упаковывать Docker image и публиковать его в GHCR. Формат версии — `YYYY.M.D.<run_number>` с датой исходного коммита в Europe/Moscow; повтор workflow сохраняет версию. Образ выбирается для ручного деплоя по тегу версии. Pipeline заканчивается публикацией; автоматический деплой не планируется.

Для MVP согласован один production-проект с каталогами `Grpc`, `Storage`, `Execution`, `Languages`, `Workspace`, без выделения отдельных библиотек. Два тестовых проекта: `.Tests` для локальной логики без внешних сервисов и `.IntegrationTests` для gRPC, MinIO и isolate; оба используют NUnit на Microsoft.Testing.Platform.

Общие настройки проектов: `TargetFramework=net10.0`, `LangVersion=14.0`, `Nullable=enable`, `ImplicitUsings=enable`. Версии NuGet-зависимостей централизованно фиксируются в `Directory.Packages.props`, без плавающих версий; конкретные версии выбираются и проверяются при создании каркаса. Платформа MVP — `linux/amd64`; поддержку `arm64` добавляют отдельно после проверки isolate и toolchain. Эти решения описывают план реализации, проекты и образ ещё не созданы.

CI запускается на push в `master` публичного GitHub-репозитория; pull request и отдельные PR-проверки не предусматриваются. Pipeline выполняет сборку, unit-тесты, сборку Docker-образа и интеграционные тесты; только после успешных обязательных проверок публикует тот же образ в GHCR без пересборки. Между jobs образ передаётся через `docker save/load`. TRX и coverage сохраняются, в том числе при неуспешных тестах, если файлы сформированы; summary публикации содержит полное имя образа с тегом для деплоя.

Интеграционные тесты используют стандартный одноразовый GitHub-hosted Linux VM runner, бесплатный для публичного репозитория; платные larger runners и постоянный judge-host не используются. Выбран `ubuntu-24.04`; совместимость privileged Docker/cgroups v2/isolate ещё проверяется пробным запуском. Бесплатность вычислений не отменяет квоту artifact storage: временный Docker-архив и отчёты должны укладываться в бесплатное хранение, параметры retention/удаления ещё выбираются. Условия и источники приведены в [описании CI](REPOSITORY.md#github-actions).

Согласованный runner — стандартный `ubuntu-24.04` (Linux VM); перед интеграционными тестами проверяются необходимые возможности privileged Docker/cgroups v2/isolate. Имя образа — `ghcr.io/texnokaktus-progolymp/runner-agent-cpp-23`. Для истории выпусков после успешной публикации образа создаётся Git-тег `vYYYY.M.D.<run_number>` на коммите, из которого собран образ. Тег Docker-образа сохраняет формат `YYYY.M.D.<run_number>` без `v`. При повторном запуске существующий Git-тег на том же коммите считается нормальным; тег на другом коммите вызывает ошибку без перезаписи. Сбой создания Git-тега делает этап выпуска неуспешным, опубликованный образ сохраняется. Устаревшие проверки от push можно отменять до публикации, но уже начатая публикация новым push не прерывается.

Следующие детали остаются **предложениями** из [REPOSITORY.md](REPOSITORY.md), а не утверждёнными ограничениями продукта:

- Deterministic build и настройки анализаторов; ReportGenerator как local tool; конкретные наборы настроек и версии проверяются при создании каркаса.
- Multi-stage Dockerfile рядом с production `.csproj`, build context в корне, `.dockerignore` для локальных и секретных файлов.
- OCI revision и версия в metadata образа.
- Техническая организация отдельного AOT job; его информационный статус и условия перехода согласованы в разделе 9.

Подробное дерево, MSBuild/CPM-настройки и план pipeline сохраняются в `REPOSITORY.md`. Создание Git-тегов для истории выпусков RunnerAgent, префикс `v`, порядок после публикации и правила повторов согласованы выше.

## 14. Порядок реализации

1. Оформить `.proto`, техническую валидацию и модель результатов по согласованному контракту.
2. Выбрать и зафиксировать совместимые версии окружения/зависимостей; проверить sandbox, cgroups и границы применения лимитов.
3. Создать реальные `.slnx`, props, проекты, Dockerfile и workflow вместе с проверяемым минимальным приложением.
4. Реализовать и проверить вертикальный сценарий: принятие задания → MinIO → компиляция → тесты → публикация → очистка → `GetResult`, затем сценарии отказов и остановки из раздела 12.
5. Подтвердить критерии приёмки, описать проверенные команды сборки и ручного деплоя; выпуск образа следует согласованным правилам CI. AOT-проверку вести отдельно без блокировки рабочего JIT-варианта.

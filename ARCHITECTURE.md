# RunnerAgent — архитектура и проектные решения

Статус: архитектурные решения для проектируемого MVP; согласованная часть сведена в техническую спецификацию.
Дата фиксации: 2 октября 2026 года.
Источник: обсуждение «Идеи для песочницы judge» и уточнения задачи по сохранению наработок.

Документ фиксирует выбранное направление, границы ответственности и будущие контракты. Проверяемые требования, критерии приёмки и реестр открытых вопросов собраны в [технической спецификации](docs/SPECIFICATION.md). Примеры типов здесь концептуальны; детали протокола, эксплуатации и безопасности ещё требуют проработки. Реализация приложения пока отсутствует.

## 1. Назначение и первый MVP

RunnerAgent — агент проверяющей системы, который получает задание, подготавливает локальные файлы, компилирует и запускает решение в isolate, собирает результаты и сохраняет артефакты.

Начать с C++23: одно задание содержит один исходный файл и набор из N тестов. Исходный код компилируется через g++ один раз на весь набор; полученный исполняемый артефакт используется для запусков на входных данных тестов. Для MVP выбран стандарт C++23. Агент возвращает структурированный результат с данными компиляции, результатами отдельных тестов и ссылками на артефакты. После обработки набора песочницы очищаются. Первый образ условно называется `judge-cpp` и содержит .NET Runner Agent, isolate, compiler/runtime и необходимые системные библиотеки.

Участники не могут самостоятельно запускать программы в этой среде. Запуск инициирует член жюри после ручного просмотра кода. Для MVP принимается упрощённая модель развёртывания, ориентированная прежде всего на ограничение типичных опасных действий: бесконечных циклов, чрезмерного расхода памяти, создания процессов, записи файлов и сетевых обращений. Ручной просмотр кода не является технической границей изоляции.

## 2. Развёртывание: MVP и целевая архитектура

### MVP: privileged Docker

Linux Docker-контейнер запускается с `--privileged` и содержит:

- .NET 10 Runner Agent;
- isolate;
- g++ и необходимые compiler/runtime libraries;
- локальную временную рабочую область для заданий.

Каждая компиляция и каждое исполнение получают отдельный sandbox isolate. Контейнер дополнительно ограничивается по CPU, RAM и числу процессов там, где это совместимо с работой isolate и cgroups.

Рассматриваются две ветки жизненного цикла агента; окончательный выбор ещё не сделан:

- **Долгоживущий агент.** Обрабатывает наборы последовательно. С момента принятия задания и до выдачи его итогового результата ресурс занят. Запрос с другим `job_id` в это время получает ошибку «ресурс занят»; повтор с текущим `job_id` получает ответ «задание уже принято» без повторного исполнения. Точные статусы протокола ещё предстоит выбрать.
- **Контейнер на один набор тестов.** Альтернативная ветка реализации: агент выполняет одно задание, ожидает получения результата мастером и завершает работу, затем контейнер останавливается и удаляется. При завершении действует описанный ниже таймаут ожидания `GetResult`. Нужно определить, кто запускает и удаляет контейнер.

Создание и удаление контейнеров для заданий относится к runtime orchestration. Автоматический деплой через CI по-прежнему не планируется.

```text
Проверяющая система
        | gRPC
        v
Docker worker --privileged
  Runner Agent
      +-- isolate: compilation --> g++
      +-- isolate: execution   --> solution для каждого теста
```

Privileged Docker здесь служит упаковкой и способом запуска, а не самостоятельной security boundary. Основная техническая граница для кода решения — isolate; возможность компрометации judge-host при такой модели остаётся существенным риском, принятым для первого этапа.

Промежуточный вариант с ручным подбором capabilities, user namespaces и cgroup delegation внутри Docker не является задачей MVP.

### Цель: dedicated Judge VM/host

Более безопасное направление — отдельная заменяемая Judge VM либо выделенный host, native isolate, cgroup delegation, минимальные необходимые привилегии и изолированные toolchain/rootfs.

```text
Проверяющая система
        | gRPC
        v
Dedicated Judge VM / host
  Runner Agent
      +-- native isolate: compilation
      +-- native isolate: execution
          delegated cgroups + isolated toolchain/rootfs
```

Точный способ делегирования cgroups и выдачи привилегий будет выбран в спецификации для конкретной Linux-среды. Переход к целевому развёртыванию должен сохранять внешний gRPC/S3-контракт и логику orchestration. Native AOT не заменяет sandbox и не является security boundary.

## 3. Внешние границы: gRPC и S3

**gRPC — control plane.** Через него передаются задания, параметры запуска и небольшие структурированные результаты. Исходный код, входные данные, stdout/stderr и журнал компиляции через gRPC не передаются.

Для MVP gRPC работает по HTTP/2 без HTTPS/TLS и без аутентификации в доверенной внутренней сети. Проверка токенов и аутентификация клиента через mTLS в текущий API не входят.

**S3 — data plane.** Агент скачивает входные объекты в локальную рабочую область и после обработки загружает выходные артефакты.

Хранилище — MinIO. Доступ к нему реализуется через пакет `AWSSDK.S3` за интерфейсом `IObjectStorage`; адрес MinIO задаётся конфигурацией агента. Конкретная версия пакета и параметры S3-клиента уточняются при реализации и проверяются интеграционными тестами с MinIO.

```text
Проверяющая система -- gRPC --> Runner Agent
                                  |   |
                                  |   +--> isolate: compile / run
                                  |
                                  +<--> S3: sources, input, artifacts

Runner Agent -- gRPC result + S3 references --> Проверяющая система
```

Выбрана асинхронная модель gRPC: при принятии задания агент сразу подтверждает, что оно начато, а итоговый результат мастер получает отдельным запросом. Выполнение принятого задания не привязано к длительности исходного RPC или сохранности соединения.

Операция получения результата — `GetResult`; предварительное имя операции запуска — `StartJob`. Это эскиз, а не утверждённый `.proto`. Ответ `StartJob` подтверждает принятие в работу, а не успешность компиляции или тестов. Пока задание не завершено, `GetResult` сразу возвращает состояние «не завершено» и сохраняет ресурс занятым; ожидания окончания внутри RPC нет. Операция отмены задания в текущем API не предусматривается.

| Данные запроса | Назначение |
| --- | --- |
| `job_id` | Идентификатор задания типа `int64`, заданный мастером и возвращаемый агентом в результате |
| `language`, `language_version` | Выбор поддерживаемого профиля агента; команда и флаги компилятора в запросе не передаются |
| `source` | Ссылка на один S3-объект с исходным кодом |
| `tests[]` | Набор тестов; каждый содержит заданный мастером `test_id` типа `int64` и ссылку на входные данные в S3 |
| `result_prefix` | Префикс выходных объектов в S3, заданный мастером; bucket результатов берётся из конфигурации агента |
| Compilation limits | Отдельные лимиты стадии компиляции |
| Execution limits | Общий профиль лимитов из задания, применяемый отдельно к каждому тесту |

Для долгоживущего агента завершение вычислений само по себе не освобождает ресурс: он остаётся занят до выдачи готового результата через `GetResult`. Этот же вызов освобождает ресурс и сразу удаляет сохранённый результат из состояния агента; отдельного подтверждения получения нет. Повторно получить выданный результат у агента нельзя. Обращение за ещё не готовым результатом или результатом другого задания ресурс не освобождает. Удаление результата из состояния агента не удаляет артефакты в S3.

Во время обычной работы долгоживущий агент ожидает `GetResult` без таймаута: непрочитанный результат не истекает, ресурс остаётся занят независимо от длительности отсутствия мастера. Таймаут ожидания результата применяется только при завершении агента, как описано в разделе о штатной остановке.

Повторный `StartJob` с текущим `job_id` возвращает «задание уже принято» и не запускает работу заново. Это относится как к выполнению, так и к ожиданию выдачи готового результата. Запрос с другим `job_id` получает «ресурс занят». Правила повторного использования завершённых `job_id`, обработки запроса с тем же ID и изменённым содержимым, deadlines отдельных RPC ещё требуют спецификации.

Для MVP состояние задания и непрочитанный результат хранятся в памяти. После перезапуска агента их потеря допустима; автоматическое восстановление или возобновление задания не требуется. Решение о повторном запуске принимает мастер. Уже опубликованные артефакты в S3 сохраняются независимо от состояния процесса агента.

## 4. S3-объекты и целостность

Предварительное описание объекта:

| Поле | Смысл |
| --- | --- |
| `bucket` | Определяется конфигурацией агента по роли объекта; в задании не выбирается |
| `key` | Ключ объекта |
| `sha256` | Ожидаемый SHA-256 содержимого |

Текущий S3-контракт использует ключ и SHA-256; `version_id` не передаётся и включённый S3 versioning не требуется. Задание определяет ожидаемые байты через hash. SHA-256 проверяется после скачивания и до помещения входных файлов в sandbox. Несовпадение hash — ошибка подготовки задания; запуск таких файлов не выполняется. ETag не считается заменой SHA-256.

В конфигурации агента задаются два bucket: отдельный для исходного кода и общий для входных данных тестов и выходных артефактов. Для `source` используется bucket исходного кода; для входных данных тестов, журнала компиляции и stdout/stderr — общий bucket. Входные ссылки в задании определяют ключ и hash, а bucket агент выбирает по роли объекта.

Мастер передаёт в задании общий `result_prefix`, внутри которого агент формирует ключи журнала компиляции и stdout/stderr каждого теста. Агент возвращает фактические ссылки на созданные объекты. Точная схема суффиксов ключей и правила уникальности префикса ещё уточняются.

Для выходных артефактов агент вычисляет SHA-256 и возвращает ссылки с ключами и hash. Формат hash, политика хранения, максимальные размеры входных объектов и поведение при частично успешной загрузке ещё требуют спецификации.

Для скачивания и загрузки объектов MinIO предусматривается resilience policy: при временной ошибке выполняется не более трёх попыток всего (первая и до двух повторов) с небольшой задержкой между ними. Отсутствие объекта и несовпадение SHA-256 повторов не вызывают. После исчерпания попыток ошибка фиксируется как инфраструктурная на соответствующей стадии; ошибка отдельного теста не останавливает остальные тесты. Точная задержка, перечень временных ошибок и способ реализации policy уточняются при разработке. Политика агента и настройки повторов `AWSSDK.S3` должны быть согласованы, чтобы вложенные повторы не превышали общий бюджет попыток.

S3/AWS credentials принадлежат только агенту. Получение credentials выполняется на стороне агента через выбранный credential provider; конкретная схема аутентификации ещё не зафиксирована.

## 5. Sandbox и рабочая область

Sandbox компиляции и sandbox исполнения разделены. Компилятор также обрабатывает недоверенные данные, поэтому запускается с собственными лимитами. Компиляция выполняется один раз на задание. После успешной компиляции в sandbox исполнения каждого теста переносится только необходимый исполняемый артефакт и разрешённые файлы. Рабочие файлы одного теста не передаются следующему.

Обе стадии соблюдают общие границы:

- У sandbox отсутствует доступ к сети, S3/AWS credentials и управляющим endpoint.
- Окружение строится по allowlist (`PATH`, при необходимости `LANG` и согласованные language-specific переменные). Секреты не наследуются ни процессом isolate, ни компилятором, ни решением.
- Агент предоставляет только необходимые локальные файлы и разрешённые mounts; рабочая область агента и другие задания не должны быть доступны.
- Исходный код, stdin, stdout/stderr и журнал компиляции передаются через локальные файлы под управлением агента.
- Workspace и isolate box принадлежат конкретному заданию/стадии и очищаются после завершения, ошибки или управляемой остановки агента.

После завершения набора и сохранения необходимых артефактов песочницы и временные рабочие файлы очищаются. Структурированный результат и ссылки на артефакты сохраняются отдельно до чтения мастером. Ожидание чтения результата не требует сохранять sandbox, а очистка sandbox не делает агент доступным для нового задания.

Память и процессы агента не должны учитываться как потребление решения. Учёт ресурсов compilation и execution ведётся отдельно. Детали доступного rootfs, mounts, прав файлов, идентификаторов box и очистки после аварий уточняются в спецификации.

## 6. Лимиты

Нужно поддержать и явно различать:

| Лимит | Предварительное поле | Единица / значение |
| --- | --- | --- |
| CPU time | `cpu_time_ms` | Миллисекунды процессорного времени |
| Wall time | `wall_time_ms` | Миллисекунды реального времени |
| Memory | `memory_bytes` | Байты памяти sandbox |
| Stdout | `stdout_bytes` | Максимальный размер stdout в байтах |
| Stderr | `stderr_bytes` | Максимальный размер stderr в байтах |
| Processes | `processes` | Допустимое число процессов/задач |

Compilation и execution имеют самостоятельные наборы лимитов. CPU time и wall time не взаимозаменяемы: ожидание или блокировка могут расходовать wall time без заметного CPU time. Журнал компиляции также должен быть ограничен.

Execution limits задаются в задании на тестирование единым профилем для набора и применяются независимо к каждому тесту. Например, лимит CPU time — бюджет каждого запуска, а не сумма времени всех тестов. Лимиты компиляции задаются отдельно. Тесты выполняются последовательно в порядке запроса. Необходимость общего предела длительности всего задания ещё не определена.

Лимиты stdout и stderr задаются отдельно и учитываются независимо. При превышении любого из них агент останавливает процесс и назначает тесту статус `OutputLimitExceeded`. Уже полученная часть каждого потока сохраняется в пределах его собственного лимита и публикуется как частичный вывод. После этого выполняются остальные тесты набора.

До разработки необходимо определить учёт дочерних процессов и потоков, точную метрику памяти, допустимые значения и приоритет verdict при нескольких одновременно нарушенных лимитах. Настройки isolate и cgroups должны соответствовать этим правилам, а не только именам полей.

## 7. Структурированный result и verdict

Результат задания должен содержать полученный от мастера `job_id`, итоговый статус, стадию возникновения ошибки, общий результат единственной компиляции и коллекцию результатов отдельных тестов. Каждый результат теста содержит соответствующий `test_id` без замены идентификатора агентом. Оба идентификатора имеют тип `int64` — знаковое 64-битное целое; допустимые значения и правила проверки уникальности ещё уточняются. Для компиляции и каждого выполненного теста сохраняются соответствующие данные:

- CPU time, wall time и peak memory;
- exit code и signal, когда они доступны, с явным отсутствием вместо фиктивного нуля;
- причину прекращения процесса или превышенный лимит;
- ссылки на stdout, stderr и журнал компиляции в S3;
- диагностические сведения об ошибках агента, isolate или storage, отличимые от ошибок решения.

Предварительные категории результата: успешное выполнение, compilation error, runtime error, CPU/wall time limit exceeded, memory limit exceeded, output limit exceeded, process limit exceeded и infrastructure error. Согласованы имена `CompilationError` и `OutputLimitExceeded`; полный состав enum, mapping isolate metadata и остальные правила классификации ещё не утверждены.

Проверка корректности ответа лежит на мастере: он получает stdout через S3, сравнивает ответ с эталоном либо запускает checker и определяет AC/WA. RunnerAgent возвращает статусы исполнения, метрики и артефакты; успешное выполнение процесса само по себе не означает Accepted. При compilation error стадия execution не запускается. Сбой загрузки артефакта не должен маскироваться под ошибку программы участника.

При ошибке компиляции итоговый статус задания — `CompilationError`; результат содержит данные компиляции и ссылку на журнал компиляции в S3, а коллекция результатов тестов пуста. Тесты не запускаются, фиктивные результаты для них не создаются. Ошибка публикации журнала компиляции отражается отдельно как инфраструктурная; недоступный журнал компиляции не представляется успешно опубликованным.

После runtime error или превышения лимита на отдельном тесте агент продолжает остальные тесты. Итоговый результат содержит полную картину по набору: verdict, метрики и артефакты каждого теста. Остановка на первой ошибке решения не предусматривается.

Инфраструктурная ошибка отдельного теста — например, сбой скачивания его входных данных, запуска isolate или загрузки его артефактов — также не останавливает набор. Тест получает отдельный статус инфраструктурной ошибки (предварительное имя `InfrastructureError`), после чего агент переходит к следующему тесту. Известные метрики и доступные артефакты сохраняются в результате; отсутствующие данные не подменяются успешным результатом. Общие ошибки задания, которые не позволяют подготовить исходный код или выполнить компиляцию, рассматриваются отдельно.

Представление невыполненных тестов при других общих ошибках задания и правила общего статуса задания, кроме согласованного `CompilationError`, ещё требуют спецификации. Финальный результат, включая ошибку компиляции или инфраструктуры, доступен мастеру через `GetResult`; выдача готового результата освобождает ресурс. Если сам агент завершился до выдачи результата, для MVP допускается потеря этого результата.

## 8. Внутренние компоненты

Это логические границы, а не требование создать отдельный проект/assembly для каждого раздела.

```text
RunnerAgent
  Grpc
    JudgeRunnerService
  Storage
    IObjectStorage
    S3ObjectStorage
  Execution
    ISubmissionRunner
    IsolateSubmissionRunner
  Languages
    ILanguageProvider
    CppLanguageProvider
  Workspace
    WorkspaceManager
```

| Компонент | Ответственность |
| --- | --- |
| `Grpc` | Приём заданий, перевод transport models, возврат результата |
| `Storage` | Скачивание/загрузка объектов и метаданные S3 через `IObjectStorage` |
| `Execution` | Локальный compilation/execution pipeline и преобразование isolate metadata |
| `Languages` | Поддерживаемые версии, toolchain, команды компиляции/запуска, необходимые файлы и окружение |
| `Workspace` | Создание, размещение файлов и очистка локальных рабочих областей |

Orchestration связывает получение задания, storage, workspace, runner и публикацию результата. `IsolateSubmissionRunner` не знает о S3 или gRPC: он получает локальные файлы и возвращает локальный результат и пути артефактов.

Orchestration также хранит состояние асинхронного задания в памяти, обеспечивает занятость ресурса до чтения результата и отделяет выполнение от жизненного цикла принимающего RPC. Локальное задание runner содержит один файл исходного кода и набор тестов; runner компилирует исходный код один раз и собирает результаты запусков. Сохранение состояния задания и непрочитанного результата на диск для MVP не требуется.

Концептуальный контракт, не готовый код приложения:

```csharp
Task<ExecutionResult> ExecuteAsync(
    LocalSubmission submission,
    ExecutionLimits limits,
    CancellationToken cancellationToken);
```

В финальной форме контракта необходимо явно представить отдельные compilation/execution limits. `ISubmissionRunner` позволяет менять реализацию исполнения независимо от transport/storage. При необходимости низкоуровневый запуск одной стадии isolate можно выделить за дополнительную границу `ISandboxRunner`; это деталь будущей реализации.

Внутренний `CancellationToken` предназначен для управления выполнением операций, включая необходимое принудительное прекращение. Он не означает наличие `CancelJob` и не связывает фоновое выполнение с отключением клиента исходного RPC. Начало штатной остановки само по себе не отменяет принятое задание: агент должен завершить набор и предоставить результат для получения мастером в пределах таймаута ожидания.

Language providers выбираются из заранее зарегистрированного набора. Первый provider — C++23 с g++; дальнейшие языки добавляются без переноса логики S3/gRPC в runner. Команда компиляции, все флаги и настройки toolchain задаются на стороне агента в его профиле языка. Мастер не передаёт дополнительные флаги или произвольные команды. Отдельные resource limits компиляции по-прежнему поступают в задании. Конкретная версия g++ и значения флагов профиля ещё требуют выбора.

## 9. Жизненный цикл задания

1. Для текущего `job_id` вернуть «задание уже принято» без повторного исполнения. Если долгоживущий агент занят другим заданием, вернуть «ресурс занят». При принятии нового задания проверить его структуру: один файл исходного кода, набор тестов, язык, версию, параметры и ссылки на объекты. Проверки и фиксация принятия должны учитывать конкурентные запросы.
2. Зафиксировать принятие задания и занятость ресурса, сразу вернуть gRPC-подтверждение начала работы. Последующая обработка выполняется независимо от исходного RPC.
3. Создать рабочую область; скачать исходный код и необходимые входные данные тестов из S3, проверяя SHA-256 до использования.
4. Один раз скомпилировать исходный код в compilation sandbox с compilation limits.
5. При успешной компиляции последовательно выполнить все тесты в порядке запроса с использованием общего исполняемого артефакта и отдельного execution sandbox для каждого запуска. К каждому тесту независимо применить execution limits из задания. После ошибки решения, превышения лимита или инфраструктурной ошибки отдельного теста продолжить остальные тесты; собрать verdict исполнения, metadata и доступные stdout/stderr по каждому тесту. При превышении отдельного лимита stdout или stderr остановить процесс и сохранить частичный вывод каждого потока в пределах его лимита. Проверку корректности ответов выполняет мастер.
6. Сформировать структурированный результат задания, включая журнал компиляции, результаты тестов и причины завершения; загрузить доступные артефакты в S3.
7. Сохранить итоговый результат и ссылки на артефакты отдельно от рабочей области. Очистить workspace и isolate boxes; при ошибках также выполнить очистку и сформировать соответствующий результат.
8. Ожидать чтения результата мастером, сохраняя ресурс занятым.
9. Вызовом `GetResult` выдать готовый результат, сразу забыть его в состоянии агента и освободить ресурс без отдельного подтверждения мастера. Артефакты в S3 сохраняются согласно их политике хранения. Если запрошена штатная остановка или выбрана альтернативная ветка контейнера на одно задание, после обслуживания запроса завершить процесс; в альтернативной ветке контейнер затем удаляется внешним управляющим компонентом.

Переходы принятия задания и освобождения ресурса при `GetResult` должны учитывать одновременные запросы. При перезапуске состояние задания не восстанавливается; повторный запуск организует мастер. Отмена задания мастером пока не поддерживается. Очистка оставшихся рабочих областей и isolate boxes после падения ещё требует спецификации. Локальная очистка не означает удаление опубликованных S3-артефактов.

### Штатная остановка агента

При запросе штатной остановки агент прекращает принимать новые задания, завершает текущий набор тестов, публикует артефакты и очищает песочницы. Затем он ожидает получения готового результата мастером через `GetResult`. Таймаут этого ожидания задаётся в конфигурации; значение по умолчанию — **30 секунд**. Отсчёт начинается после готовности результата, публикации артефактов и очистки; если результат уже готов на момент запроса остановки — с момента этого запроса. Время выполнения задания в эти 30 секунд не входит.

Во время ожидания gRPC остаётся доступным для `GetResult`. Если мастер забирает результат до истечения таймаута, агент завершает обслуживание запроса и затем останавливает сервер и процесс. Отдельного подтверждения от мастера по-прежнему нет. Если мастер не забрал результат за отведённое время, агент завершает работу с потерей непрочитанного результата в памяти; опубликованные S3-артефакты сохраняются.

Если задания и непрочитанного результата нет, агент может завершиться сразу. Точный статус отказа новым заданиям при остановке ещё нужно определить. Настройки остановки приложения и контейнера должны позволять завершить задание и выдержать настроенное ожидание результата. Аварийное или принудительное завершение может привести к допустимой для MVP потере состояния.

В альтернативной ветке контейнера на один набор тестов перед выходом агента и удалением контейнера также ожидается получение результата мастером в пределах этого таймаута. Выбор самой ветки и владельца управления контейнерами остаётся открытым. Таймаут относится к завершению агента; во время обычной работы долгоживущего агента ожидание `GetResult` не ограничено по времени, ресурс остаётся занят.

## 10. .NET 10: JIT сначала, Native AOT как цель

Первая разработка и отладка — .NET 10 JIT. Архитектурная цель для production — Native AOT publication после стабилизации агента и подтверждения совместимости выбранных зависимостей.

Код с самого начала писать AOT-friendly:

- Использовать статически известные типы, заранее генерируемые protobuf-модели и явную регистрацию language providers.
- Для JSON, если он понадобится, применять `System.Text.Json` source generation.
- Избегать runtime plugins, dynamic loading и ненужной reflection-heavy сериализации.
- При появлении реализации проверять публикацию с `PublishAot=true` в CI и разбирать trimming/AOT warnings.
- Проверять на целевой Linux-платформе реальную работу gRPC, S3, запуска isolate и обработки результатов в опубликованной AOT-сборке.

AOT-совместимость конкретных версий gRPC-библиотек и выбранного `AWSSDK.S3` не считается доказанной этими заметками. Совместимость зависимостей и способ размещения gRPC service должны проверяться отдельно.

Для долгоживущей ветки скорость старта не является главным аргументом выбора. Если будет выбрана ветка контейнера на один набор тестов, стоимость запуска агента и контейнера нужно оценить отдельно. Ожидаемый эффект AOT — более компактное развёртывание агента и меньше динамического поведения; это не гарантия безопасности или конкретного выигрыша памяти. При Native AOT публикации самому агенту не нужен отдельно установленный .NET runtime. Compiler/runtime поддерживаемых языков остаются самостоятельной частью образа: будущая поддержка C# не зависит от JIT/AOT режима RunnerAgent.

## 11. Открытые решения для реализации

Согласованные требования оформлены в [технической спецификации](docs/SPECIFICATION.md); она сохраняет перечисленные ниже вопросы открытыми и не утверждает предложенные варианты автоматически.

До реализации следует согласовать:

- Окончательный асинхронный `.proto`, endpoint/порт HTTP/2 без TLS, deadlines, повторное использование завершённых `job_id` и запросы с тем же ID, но другим содержимым. Для MVP аутентификация не предусмотрена. Выданный через `GetResult` результат агент сразу забывает; точный статус отсутствующего результата ещё нужно выбрать.
- Общие ошибки задания до запуска тестов, кроме согласованного результата ошибки компиляции (`CompilationError`, журнал компиляции, пустой список тестов); необходимость общего предела длительности задания, допустимые значения и уникальность идентификаторов `int64` от мастера, остальные общие статусы результата. Для инфраструктурной ошибки отдельного теста согласован отдельный статус с продолжением набора.
- Выбор долгоживущего агента либо контейнера на один набор тестов; для второй ветки — владельца lifecycle контейнера.
- S3 contract: hash encoding, схему ключей внутри префикса мастера, размеры, credentials MinIO, параметры `AWSSDK.S3`, lifecycle и частичные ошибки публикации. Версии объектов в текущий контракт не входят.
- Linux/base image, версии isolate/toolchain, cgroup setup, mounts/rootfs и проверяемые правила sandbox.
- Точные лимиты каждой стадии, метрики ресурсов, verdict enum и mapping isolate metadata.
- Workspace cleanup/recovery, наблюдаемость и эксплуатационные ограничения host/container.
- AOT-совместимые зависимости и критерии перехода от JIT MVP к Native AOT production.

Эти вопросы перечислены как открытые. Согласованы C++23 MVP в privileged Docker, один файл исходного кода и N тестов с одной компиляцией, отдельные sandbox compilation/execution, очистка после набора, асинхронный gRPC и занятость ресурса до чтения результата, идентификаторы `int64`, S3 для файлов с проверкой SHA-256 без версий объектов, .NET 10 JIT при разработке и Native AOT как production-цель.

Дополнительный вариант для обсуждения — брокер сообщений, например Kafka, для приёма заданий и публикации результатов тестирования (Q-14 в [спецификации](docs/SPECIFICATION.md)). Использование брокера пока не принято как требование MVP. Нужно определить, заменяет ли он gRPC или дополняет его, правила доставки и подтверждений, обработку дубликатов по `job_id`, поведение при сбоях и перезапуске, момент освобождения ресурса и роль S3 для файлов. До отдельного решения сохраняется согласованный gRPC/S3-контракт с `StartJob`/`GetResult`.

## 12. Структура репозитория и CI/CD

Согласована организация репозитория: README с функционалом, API, сборкой, тестированием и деплоем; solution в формате `.slnx`; production-код в `src/`; тестовые проекты в `tests/`; workflow в `.github/workflows/`. Pipeline собирает и тестирует приложение, упаковывает Docker image и публикует его в GHCR.

Общие MSBuild-настройки располагаются в корневом `Directory.Build.props`, версии NuGet-пакетов — в `Directory.Packages.props` с CPM. В `src/`, `tests/` и при необходимости отдельных проектах допускаются свои `Directory.Build.props` с явным импортом родительского файла. Общие тестовые зависимости, включая NUnit и NSubstitute, относятся к `tests/`. В `src/Directory.Build.props` задаётся `InternalsVisibleTo` для соответствующего проекта с суффиксом `.Tests` и для `DynamicProxyGenAssembly2`; эти настройки наследуются всеми production-проектами.

Тесты с самого начала используют NUnit на Microsoft.Testing.Platform, включая нативный MTP-режим `dotnet test` в .NET 10. Версия SDK и выбор `test.runner=Microsoft.Testing.Platform` фиксируются в `global.json`; общие настройки NUnit runner и MTP-расширения покрытия/TRX — в `tests/Directory.Build.props`.

Образ публикуется с тегом версии `YYYY.M.D.<run_number>`; дата берётся из исходного коммита в Europe/Moscow. Повторная попытка workflow сохраняет версию. Для ручного деплоя достаточно тега версии. Автоматический деплой не планируется: pipeline заканчивается публикацией в GHCR.

Подробное дерево и предложение по проектам, наследованию настроек, Docker и CI находятся в [структуре репозитория](docs/REPOSITORY.md). Там отдельно обозначены ещё не утверждённые детали: состав проектов, платформы и имя образа, версии зависимостей, CI runner и политика AOT check. [README](README.md) служит краткой точкой входа; инструкции сборки и ручного деплоя пока описывают план, поскольку реализация отсутствует.

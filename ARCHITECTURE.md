# RunnerAgent — архитектура и проектные решения

Статус: требования MVP согласованы; техническая детализация и проверка выполняются при реализации.
Дата первоначальной фиксации: 2 октября 2026 года. Модель взаимодействия пересмотрена 5 ноября 2026 года.
Источник: обсуждение «Идеи для песочницы judge» и уточнения задачи по сохранению наработок.

Документ фиксирует выбранное направление, границы ответственности и будущие контракты. Проверяемые требования, сценарии приёмки и задачи реализации находятся в [начальном изменении OpenSpec](openspec/changes/implement-runner-agent/README.md). Оно остаётся активным до реализации MVP; основные спецификации заполняются при архивировании после приёмки. Создан независимый каркас host, MSBuild/CPM, NUnit/MTP и базового CI. Локальный isolate-runner и тестовый образ реализованы; gRPC/S3 orchestration ещё отсутствует. Оставшиеся детали протокола описывают целевую реализацию.

## 1. Назначение и первый MVP

RunnerAgent — агент проверяющей системы, который получает задание, подготавливает локальные файлы, компилирует и запускает решение в isolate, собирает результаты и сохраняет артефакты.

Начать с C++23: одно задание содержит один исходный файл и набор из N тестов. Исходный код компилируется через g++ один раз на весь набор; полученный исполняемый артефакт используется для запусков на входных данных тестов. Для MVP выбран стандарт C++23. Агент возвращает структурированный результат с данными компиляции, результатами отдельных тестов и ссылками на артефакты. После обработки набора песочницы очищаются. Первый образ условно называется `judge-cpp` и содержит .NET Runner Agent, isolate, compiler/runtime и необходимые системные библиотеки.

Участники не могут самостоятельно запускать программы в этой среде. Запуск инициирует член жюри после ручного просмотра кода. Для MVP принимается упрощённая модель развёртывания, ориентированная прежде всего на ограничение типичных опасных действий: бесконечных циклов, чрезмерного расхода памяти, создания процессов, записи файлов и сетевых обращений. Ручной просмотр кода не является технической границей изоляции.

## 2. Развёртывание: MVP и целевая архитектура

### MVP: privileged Docker

Обязательны cgroups v2 и доступ к контроллерам/метрикам, необходимым для лимитов. До приёма заданий агент проверяет среду, включая `memory.peak`, управление swap/OOM и `pids.max` / `pids.events`. Если согласованные гарантии обеспечить нельзя, запуск завершается с ошибкой без приёма заданий; упрощённый режим без нужных метрик не используется. Конкретная настройка делегирования cgroups ещё выбирается.

Linux Docker-контейнер запускается с `--privileged` и содержит:

- .NET 10 Runner Agent;
- isolate;
- g++ и необходимые compiler/runtime libraries;
- локальную временную рабочую область для заданий.

Каждая компиляция и каждое исполнение получают отдельный sandbox isolate. Контейнер дополнительно ограничивается по CPU, RAM и числу процессов там, где это совместимо с работой isolate и cgroups.

Для MVP выбран **долгоживущий агент**, обрабатывающий один RunJob за раз. Контейнер используется для нескольких последовательных заданий. Единственный слот занят обработкой и очисткой, в том числе после отмены RPC. Все конкурентные вызовы, включая тот же job_id с любым содержимым, получают RESOURCE_EXHAUSTED без очереди. После успешной очистки и завершения обработчика агент может принять следующий вызов, если не начата штатная остановка.

Решение закрывает Q-01: контейнер на один набор тестов и отдельный компонент управления такими контейнерами не входят в MVP. Отдельные sandbox компиляции/тестов и их очистка сохраняются.

Автоматический деплой через CI по-прежнему не планируется.

Решение от 6 ноября 2026 года: поставка разделяется на базовый образ и производные языковые образы. Базовый образ содержит Linux, .NET runtime, isolate, агент и общую подготовку sandbox, без конкретного компилятора. Производный образ добавляет toolchain/runtime языка и фиксированную конфигурацию профиля раннера; первым остаётся C++23. Один запущенный контейнер обслуживает один профиль, RunJob не задаёт команды и флаги. Общий startup-пробник проверяет доступность инструментов выбранного профиля, а не жёстко заданный g++. Базовый образ без профиля не является готовым worker. Реализация разделения образов — следующий шаг после startup-проверки; текущий tests/prototype/Dockerfile пока объединённый.

```text
Проверяющая система
        | gRPC
        v
Docker worker --privileged
  Runner Agent
      +-- isolate: compilation --> g++
      +-- isolate: execution   --> solution для каждого теста
```

Privileged Docker здесь служит упаковкой и способом запуска, а не самостоятельной security boundary. Основная техническая граница для кода решения — isolate; возможность компрометации judge-host при такой модели остаётся существенным риском, принятым для первого этапа.

Промежуточный вариант с ручным подбором capabilities, user namespaces и cgroup delegation внутри Docker не является задачей MVP.

### Цель: dedicated Judge VM/host

Более безопасное направление — отдельная заменяемая Judge VM либо выделенный host, native isolate, cgroup delegation, минимальные необходимые привилегии и изолированные toolchain/rootfs.

```text
Проверяющая система
        | gRPC
        v
Dedicated Judge VM / host
  Runner Agent
      +-- native isolate: compilation
      +-- native isolate: execution
          delegated cgroups + isolated toolchain/rootfs
```

Точный способ делегирования cgroups и выдачи привилегий будет выбран в спецификации для конкретной Linux-среды. Переход к целевому развёртыванию должен сохранять внешний gRPC/S3-контракт и логику orchestration. Native AOT не заменяет sandbox и не является security boundary.

## 3. Внешние границы: gRPC и S3

**gRPC — control plane.** Через него передаются задания, параметры запуска и небольшие структурированные результаты. Исходный код, входные данные, stdout/stderr и вывод компилятора через gRPC не передаются.

Для MVP gRPC работает по HTTP/2 без HTTPS/TLS и без аутентификации в доверенной внутренней сети. По умолчанию агент слушает `0.0.0.0:8080` внутри контейнера; адрес прослушивания и порт настраиваются. Проверка токенов и аутентификация клиента через mTLS в текущий API не входят.

**S3 — data plane.** Агент скачивает входные объекты в локальную рабочую область и после обработки загружает выходные артефакты.

Хранилище — MinIO. Доступ к нему реализуется через пакет `AWSSDK.S3` за интерфейсом `IObjectStorage`; адрес MinIO задаётся конфигурацией агента, `ForcePathStyle = true`. Credential provider читает только окружение агента: `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` и необязательный `AWS_SESSION_TOKEN`, без fallback к профилям или metadata-сервисам. Отсутствие обязательных значений — ошибка конфигурации при запуске. Решение принято при обязательной изоляции секретов от isolate и обеих песочниц, описанной в разделе 5. Регион подписи клиента по умолчанию — `us-east-1`, с возможностью переопределения; поддержка MinIO без явно заданного серверного региона проверяется интеграционно, перенастройка сервера не требуется. При запуске проверяется локальная конфигурация, включая обязательные credentials; обязательных сетевых проверок MinIO нет. Доступность storage, существование bucket и права проверяются рабочими операциями с согласованными повторами. Временная недоступность MinIO сама по себе не препятствует запуску агента; проверка локальной sandbox-среды остаётся обязательной. Конкретная версия пакета и оставшиеся настройки уточняются в Q-08 и проверяются интеграционными тестами.

```text
Проверяющая система -- gRPC --> Runner Agent
                                  |   |
                                  |   +--> isolate: compile / run
                                  |
                                  +<--> S3: sources, input, artifacts

Runner Agent -- gRPC result + S3 references --> Проверяющая система
```

Согласован единственный unary RPC `RunJob`: мастер отправляет задание и получает итоговый структурированный результат в ответе того же вызова. RPC остаётся открытым до окончания обработки, публикации и очистки. Промежуточного подтверждения, отдельного чтения, кэша результата, истории ID и дедупликации нет. Занятость логическая: обработка использует асинхронные операции, health и отказы конкурентным вызовам не ожидают завершения прогона.

| Данные запроса | Назначение |
| --- | --- |
| `job_id` | Положительный идентификатор задания типа `int64` (`1..9223372036854775807`), заданный мастером и возвращаемый агентом в результате |
| `language`, `language_version` | Проверка совместимости с единственным профилем агента: для MVP строго `"cpp"` / `"23"`; команда и флаги компилятора в запросе не передаются |
| `source` | Ссылка на один S3-объект с исходным кодом |
| `tests[]` | Непустой набор тестов; каждый содержит заданный мастером положительный `test_id` типа `int32` (`1..2147483647`) — порядковый номер теста в группе — и ссылку на входные данные в S3 |
| `result_prefix` | Префикс выходных объектов в S3, заданный мастером; bucket результатов берётся из конфигурации агента |
| Compilation limits | Отдельные лимиты стадии компиляции |
| Execution limits | Общий профиль лимитов из задания, применяемый отдельно к каждому тесту |

`test_id` уникален внутри задания; в разных заданиях номера могут повторяться. Нулевые или отрицательные ID, повторяющиеся номера тестов и пустой набор вызывают `INVALID_ARGUMENT`, задание не принимается. Агент обрабатывает именно переданный список в порядке запроса, сохраняя исходные номера. Полноту группы, пропуски и возрастание номеров он не проверяет: поднаборы и произвольный порядок положительных уникальных номеров допустимы. Агент не добавляет отсутствующие тесты, не сортирует и не перенумеровывает список. Правила ошибки компиляции и продолжения после ошибки отдельного теста сохраняются.

Отдельные верхние пределы числа тестов и размера gRPC-запроса задания не вводятся; настройки транспорта должны соответствовать этому решению. Корректное задание не отклоняется по таким порогам. Требования к непустому набору и ID сохраняются, как и resource limits компиляции и исполнения. Отдельные лимиты размеров исходника и входных S3-объектов тестов также не вводятся.

При обычной занятости каждый конкурентный RunJob сразу получает RESOURCE_EXHAUSTED, независимо от ID и содержимого. Во время штатной остановки новые вызовы получают UNAVAILABLE. Допуск атомарен с остановкой: сначала проверяется остановка и захватывается свободный слот без очереди, затем проверяется задание. Ошибка валидации у получившего слот вызова даёт INVALID_ARGUMENT без создания workspace; слот освобождается. Занятый раннер не валидирует конкурентное задание ради специального ответа.

При завершённом неотменённом вызове gRPC OK несёт результат со статусом Completed, CompilationError либо InfrastructureError по правилам обработки. Ошибка программы участника не превращается в транспортную ошибку. Мастер выдаёт новые job_id и result_prefix для новых запусков; повтор после потери ответа может исполнить задание заново, поскольку истории и безопасного автоматического повтора нет.

Отмена RunJob, истечение deadline или обнаруженный сервером разрыв соединения прекращают обработку задания. Агент останавливает текущую компиляцию или тест, завершает все процессы его песочницы и дожидается их завершения; следующие тесты не запускаются. Мягкость относится к управляемой остановке проверки и обязательной очистке, а не к ожиданию естественного завершения программы участника. Механизм завершения процессов выбирается при реализации так, чтобы не оставлять дочерние процессы.

Скачивания, загрузки, задержки и повторы storage прекращаются; новые публикации и допубликация частичных результатов не выполняются. Уже опубликованные S3-объекты остаются. Отмена клиента не является RuntimeError или превышением лимита решения. Доставка частичного либо итогового структурированного результата отменённого RPC не гарантируется.

Очистка запускается независимо от уже отменённого токена RPC и завершается до освобождения слота. Клиент может получить ошибку отмены раньше окончания серверной очистки; до её успешного завершения новые вызовы отклоняются. Ошибка очистки запрещает повторное использование среды и завершает агент с кодом 1 по REQ-14.

Deadline задаёт мастер, агент не вводит своего значения по умолчанию или отдельного общего лимита длительности задания. В новой модели deadline ограничивает время ожидания RPC и при истечении запускает отмену; лимиты компиляции и каждого теста сохраняются. Разрыв соединения действует как отмена после уведомления сервера транспортом; мгновенное обнаружение сетевой потери не гарантируется.

| Ситуация | Код gRPC | Ответ |
| --- | --- | --- |
| Прогон завершён, включая ошибки кода и обработанные инфраструктурные ошибки | `OK` | Структурированный результат задания |
| Другой вызов занимает раннер, включая отмену и очистку | `RESOURCE_EXHAUSTED` | Агент занят |
| Агент останавливается или выведен из работы после ошибки очистки | `UNAVAILABLE` | Агент не принимает задания |
| Свободный агент получил некорректное задание | `INVALID_ARGUMENT` | Описание ошибки |
| Клиент явно отменил RPC | `CANCELLED` на стороне клиента | Итоговый результат не гарантируется |
| Истёк deadline клиента | `DEADLINE_EXCEEDED` на стороне клиента | Итоговый результат не гарантируется |

Источники семантики транспорта: [стандартные коды gRPC](https://grpc.io/docs/guides/status-codes/), [отмена](https://grpc.io/docs/guides/cancellation/) и [deadlines](https://grpc.io/docs/guides/deadlines/). Точный код сетевого сбоя определяется gRPC. Транспорт не гарантирует доставку ответа при разрыве соединения.

## 4. S3-объекты и целостность

Bucket создаются заранее при развёртывании; агент их не создаёт и не меняет их настройки.

Предварительное описание объекта:

| Поле | Смысл |
| --- | --- |
| `bucket` | Определяется конфигурацией агента по роли объекта; в задании не выбирается |
| `key` | Ключ объекта |
| `sha256` | SHA-256 содержимого как массив ровно из 32 байт; ожидаемый для входа, вычисленный для выхода |

Текущий S3-контракт использует ключ и SHA-256; `version_id` не передаётся и включённый S3 versioning не требуется. Задание определяет ожидаемые байты через hash. SHA-256 проверяется после скачивания и до помещения входных файлов в sandbox. Несовпадение hash — ошибка подготовки задания; запуск таких файлов не выполняется. ETag не считается заменой SHA-256.

В конфигурации агента задаются два bucket: отдельный для исходного кода и общий для входных данных тестов и выходных артефактов. Для `source` используется bucket исходного кода; для входных данных тестов, вывода компилятора и stdout/stderr — общий bucket. Входные ссылки в задании определяют ключ и hash, а bucket агент выбирает по роли объекта.

Мастер передаёт в задании общий `result_prefix`, внутри которого агент формирует ключи с суффиксами `compilation/stdout.txt` и `compilation/stderr.txt`, `tests/{test_id}/stdout.txt` и `tests/{test_id}/stderr.txt`, используя исходный номер теста. Мастер выдаёт новый префикс для каждого запуска, включая повторное выполнение задания. Агент не ведёт реестр использованных префиксов и возвращает фактические ссылки на опубликованные объекты. Агент не проверяет существование выходных объектов перед загрузкой: ошибочное повторное использование префикса может перезаписать объект по тому же ключу. Входные `key` и `result_prefix` должны быть непустыми (`INVALID_ARGUMENT` при пустом значении). Завершающий `/` допустим; перед суффиксом он добавляется, только если его ещё нет. S3-ключи не используются как локальные пути.

Для выходных артефактов агент вычисляет SHA-256 и возвращает ссылки с ключами и hash. Во входных и выходных ссылках хеш передаётся как массив 32 байт (`bytes` в protobuf), без текстового hex-кодирования. Неверная длина входного хеша даёт `INVALID_ARGUMENT`; содержимое входа проверяется по этим байтам. Отдельные лимиты размеров исходника и входных файлов тестов не вводятся.

Если один артефакт не опубликован, агент продолжает загрузку остальных. Уже опубликованные объекты не удаляются; результат содержит доступные ссылки и диагностику ошибок. Повтор загрузки артефакта использует тот же ключ и содержимое. Агент не удаляет опубликованные артефакты ни при частичном успехе, ни при выдаче результата или очистке workspace; срок хранения и удаление — ответственность мастера или lifecycle-политики MinIO.

Политикой повторов MinIO управляет агент: не более трёх попыток на операцию (первая и до двух повторов), задержки перед второй и третьей — 200 мс и 500 мс. Автоматические повторы SDK отключаются, включая дополнительные механизмы выбранной версии. Повторяются обрывы соединения, сетевые таймауты, HTTP `429`, `500`, `502`, `503`, `504` и S3 `SlowDown`; скачивание начинается заново без использования частичных данных. Отсутствие объекта или bucket, отказ в доступе, неверные credentials, несовпадение SHA-256 и прочие ошибки вне согласованного перечня не повторяются. Отмена storage-операции прекращает попытки; отмена RunJob прекращает storage-операции и повторы и переводит задание к очистке. После окончательной ошибки фиксируется инфраструктурная ошибка соответствующей стадии; ошибка отдельного теста не останавливает остальные тесты. Выбор реализации policy не меняет эту семантику.

S3/AWS credentials принадлежат только агенту. Provider читает только `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` и необязательный `AWS_SESSION_TOKEN` из окружения, без fallback к профилям и metadata-сервисам. Отсутствие обязательных значений — ошибка конфигурации при запуске; секреты изолируются от обеих песочниц.

## 5. Sandbox и рабочая область

Sandbox компиляции и sandbox исполнения разделены. Компилятор также обрабатывает недоверенные данные, поэтому запускается с собственными лимитами. Компиляция выполняется один раз на задание. После успешной компиляции в sandbox исполнения каждого теста переносится только необходимый исполняемый артефакт и разрешённые файлы. Рабочие файлы одного теста не передаются следующему.

Обе стадии соблюдают общие границы:

- У sandbox отсутствует доступ к сети, S3/AWS credentials и управляющим endpoint.
- Окружение строится по allowlist (`PATH`, при необходимости `LANG` и согласованные language-specific переменные). Секреты не наследуются ни процессом isolate, ни компилятором, ни решением.
- Агент полностью очищает окружение дочернего процесса перед каждым запуском isolate и явно задаёт разрешённые значения; `--full-env` запрещён. Фильтрации только `AWS_*` недостаточно. Credentials не попадают в аргументы, рабочие файлы, mounts, логи или результаты. Sandbox не получает доступ к окружению и файлам агента через `/proc/<agent-pid>/environ`, `/proc/<agent-pid>/root` или `/proc/<agent-pid>/fd`. Для обеих стадий обязательны интеграционные проверки с тестовыми секретами; фактическая гарантия требует реализации и проверки mounts/прав по Q-09.
- Агент предоставляет только необходимые локальные файлы и разрешённые mounts; рабочая область агента и другие задания не должны быть доступны.
- Исходный код, stdin, stdout/stderr и вывод компилятора передаются через локальные файлы под управлением агента.
- Workspace и isolate box принадлежат конкретному заданию/стадии и очищаются после завершения, ошибки или управляемой остановки агента.

После завершения набора и публикации доступных артефактов sandbox и workspace очищаются до ответа RunJob. При отмене выполняются остановка процессов и очистка без обязательной допубликации; слот освобождается только после завершения серверной обработки и успешной очистки.

Память и процессы агента не должны учитываться как потребление решения. Учёт ресурсов compilation и execution ведётся отдельно. Детали доступного rootfs, mounts, прав файлов, идентификаторов box и определения собственных workspace/boxes уточняются в спецификации. Поведение начальной очистки и ошибки очистки после задания согласовано ниже.

Системные файлы и toolchain доступны по разрешённому списку только для чтения; запись разрешена в собственные рабочие и временные каталоги стадии. Компилятор и решение работают без root. Окружение, дескрипторы и mounts не раскрывают ресурсы агента. Для экземпляров выделяются непересекающиеся workspace, box IDs и cgroups; конкретная настройка проверяется при реализации.

## 6. Лимиты

Нужно поддержать и явно различать:

| Лимит | Предварительное поле | Единица / значение |
| --- | --- | --- |
| CPU time | `cpu_time_ms` | Суммарные миллисекунды процессорного времени всех процессов и потоков песочницы |
| Wall time | `wall_time_ms` | Миллисекунды реального времени |
| Memory | `memory_bytes` | Память всей cgroup в байтах, включая учитываемый ядром файловый кеш |
| Stdout | `stdout_bytes` | Максимальный размер stdout в байтах |
| Stderr | `stderr_bytes` | Максимальный размер stderr в байтах |
| Processes | `processes` | Общее допустимое число процессов и потоков, включая основной |

Compilation и execution имеют самостоятельные наборы лимитов. Мастер явно передаёт оба профиля и все значения; каждое значение должно быть положительным. Отсутствие профиля/значения, ноль или отрицательное значение дают `INVALID_ARGUMENT`; defaults и обозначения «без ограничений» не используются. CPU time и wall time не взаимозаменяемы: ожидание или блокировка могут расходовать wall time без заметного CPU time.

CPU и память учитываются для всей песочницы, включая дочерние процессы и потоки, через cgroups. Метрика памяти для лимита и результата едина: потребление всей cgroup, включая учитываемый ядром файловый кеш; результат возвращает пик в байтах. `processes` учитывает основной процесс и все процессы/потоки песочницы.

Swap для песочницы отключён; при OOM завершается вся группа процессов, включая дочерние. Лимит `memory_bytes` округляется вверх до размера страницы памяти хоста с проверкой переполнения; фактически применённый лимит возвращается в результате соответствующей стадии. Исходное значение запроса сохраняется без изменения; результат показывает фактически применённый лимит. Пик читается из `memory.peak` cgroup стадии до очистки.

Лимит процессов/потоков задаётся через `pids.max`, подтверждение нарушения берётся из событий `pids.events` текущего запуска. Заблокированная попытка создания лишнего процесса/потока означает `ProcessLimitExceeded` даже при обработанном отказе и exit code 0. При обнаружении нарушения оставшиеся процессы песочницы останавливаются; основная причина учитывает общий приоритет подтверждённых нарушений.

Stdout и stderr компилятора сохраняются раздельно с независимыми лимитами `stdout_bytes` и `stderr_bytes`, отдельными локальными файлами и S3-артефактами `compilation/stdout.txt` и `compilation/stderr.txt`. Они заменяют ранее выбранный единый журнал. Правила публикации вывода компилятора действуют на каждый поток отдельно: сбой одного не скрывает успешно опубликованный другой. При превышении лимита любого потока компиляция останавливается; оба частичных потока сохраняются в своих лимитах. Общий статус — `CompilationError`, причина — `OutputLimitExceeded`, если нет подтверждённого нарушения с более высоким приоритетом; тесты не запускаются. Единый `log_bytes` не вводится.

Execution limits задаются в задании на тестирование единым профилем для набора и применяются независимо к каждому тесту. Например, лимит CPU time — бюджет каждого запуска, а не сумма времени всех тестов. Лимиты компиляции задаются отдельно. Тесты выполняются последовательно в порядке запроса. Отдельного общего предела длительности задания нет (Q-06 закрыт); deadline RunJob задаёт мастер; при его истечении проверка отменяется с последующей очисткой.

Лимиты stdout и stderr задаются отдельно и учитываются независимо. При превышении любого из них агент останавливает процесс и фиксирует `OutputLimitExceeded`; основная причина и итоговый статус учитывают подтверждённые нарушения с более высоким приоритетом и отдельные инфраструктурные ошибки. Уже полученная часть каждого потока сохраняется в пределах его собственного лимита и публикуется как частичный вывод. После этого выполняются остальные тесты набора.

Поля времени в миллисекундах и размеров в байтах имеют тип `int64`, `processes` — `int32`. Невозможность корректно применить значение в выбранной песочнице даёт `INVALID_ARGUMENT` до принятия задания. Конкретные границы применимости и преобразование единиц для выбранной версии isolate ещё уточняются. Настройки isolate и cgroups должны соответствовать согласованным правилам, включая общую метрику памяти лимита и результата.

При нескольких подтверждённых нарушениях основная причина выбирается в порядке `MemoryLimitExceeded` → `OutputLimitExceeded` → `CpuTimeLimitExceeded` → `WallTimeLimitExceeded` → `ProcessLimitExceeded` → `RuntimeError`; остальные обнаруженные причины сохраняются в диагностике. Один сигнал завершения без подтверждения нарушения не является основанием назначить превышение лимита. Инфраструктурные ошибки сохраняются отдельно от известного результата исполнения.

CPU учитывается по всей cgroup стадии, wall time — монотонными часами за время исполнения. Причины превышений подтверждаются измерениями и событиями соответствующей песочницы, а не одним сигналом. Все преобразования единиц проверяются на переполнение; неприменимые значения отклоняются до принятия. Точные границы и mapping выбранной версии isolate фиксируются и проверяются тестами при реализации.

## 7. Структурированный result и verdict

Результат задания должен содержать полученный от мастера `job_id`, итоговый статус, стадию возникновения ошибки, общий результат единственной компиляции и коллекцию результатов отдельных тестов. Каждый результат теста содержит соответствующий `test_id` без замены идентификатора агентом. `job_id` — положительный `int64`, `test_id` — положительный `int32`, порядковый номер теста в группе, уникальный внутри задания. Для компиляции и каждого выполненного теста сохраняются соответствующие данные:

- CPU time, wall time и peak memory;
- exit code и signal, когда они доступны, с явным отсутствием вместо фиктивного нуля;
- причину прекращения процесса или превышенный лимит;
- ссылки на stdout, stderr и вывод компилятора в S3;
- диагностические сведения об ошибках агента, isolate или storage, отличимые от ошибок решения.

Результат стадии также содержит фактически применённый лимит памяти с учётом округления, если он был установлен. Невозможность получить обязательные данные после запуска — инфраструктурная ошибка; все доступные сведения сохраняются, отсутствующие не заменяются нулями или успехом. Допустимое отсутствие необязательного exit code/signal не считается ошибкой метрик.

Согласованы причины завершения процесса компиляции и процесса решения: `Success`, `RuntimeError`, `CpuTimeLimitExceeded`, `WallTimeLimitExceeded`, `MemoryLimitExceeded`, `OutputLimitExceeded`, `ProcessLimitExceeded`. Неуспешный исход процесса компиляции даёт общий `CompilationError` с конкретной причиной; инфраструктурные ошибки обрабатываются отдельно. Приоритет причин определён в разделе 6; mapping конкретных данных isolate/cgroups ещё требует проработки. Общие статусы задания и инфраструктурная диагностика описаны ниже.

Проверка корректности ответа лежит на мастере: он получает stdout через S3, сравнивает ответ с эталоном либо запускает checker и определяет AC/WA. RunnerAgent возвращает статусы исполнения, метрики и артефакты; успешное выполнение процесса само по себе не означает Accepted. При compilation error стадия execution не запускается. Сбой загрузки артефакта не должен маскироваться под ошибку программы участника.

При ошибке компиляции итоговый статус задания — `CompilationError`; результат содержит данные компиляции и отдельные ссылки на stdout/stderr компилятора в S3 при успешной публикации соответствующих потоков, а коллекция результатов тестов пуста. Тесты не запускаются, фиктивные результаты для них не создаются.

Ошибка публикации вывода компилятора сохраняется отдельно как инфраструктурная диагностика на уровне задания. Данные компиляции сохраняются, ссылка на неопубликованный поток не возвращается. Если компиляция успешна, тесты продолжаются и после обработки набора общий статус — `Completed`. Если компиляция завершилась ошибкой, сохраняются общий `CompilationError` и пустой список тестов. Сбой публикации потока компилятора сам по себе не меняет известный исход компиляции.

После runtime error или превышения лимита на отдельном тесте агент продолжает остальные тесты. Итоговый результат содержит полную картину по набору: verdict, метрики и артефакты каждого теста. Остановка на первой ошибке решения не предусматривается.

Обычная инфраструктурная ошибка отдельного теста при безопасной для продолжения среде — например, сбой скачивания его входных данных, запуска isolate или загрузки его артефактов — также не останавливает набор. Итоговый статус теста — `InfrastructureError`, после чего агент переходит к следующему тесту. Результат исполнения сохраняется отдельно от инфраструктурной диагностики: например, ошибка исполнения и последующий сбой загрузки stdout дают итоговый `InfrastructureError` теста, отдельный результат с `RuntimeError`, известными метриками/exit code/signal и диагностику публикации stdout. Если процесс решения не запускался, результат исполнения явно отсутствует. Ссылки возвращаются только на успешно опубликованные артефакты; неизвестные данные не подменяются успешным результатом. Общие ошибки задания, которые не позволяют подготовить исходный код или выполнить компиляцию, рассматриваются отдельно.

Для общей ошибки подготовки исходного кода или невозможности компиляции из-за инфраструктуры согласован итоговый статус задания `InfrastructureError` с указанием стадии и причины. Примеры: сбой скачивания исходника, несовпадение его SHA-256, невозможность запустить isolate для компиляции. Тесты не запускаются, список их результатов пуст; фиктивные результаты не создаются. Доступные данные компиляции сохраняются, если они появились; если компиляция не начиналась, её результат явно отсутствует. Обычная ошибка компиляции кода по-прежнему даёт `CompilationError`.

Если после начала тестов фатальная ошибка завершения процессов или очистки промежуточной песочницы не позволяет безопасно продолжить набор, оставшиеся тесты не запускаются. Согласован общий `InfrastructureError` с сохранением компиляции, известных результатов тестов, метрик, артефактов и диагностики прерывания. Фиктивные результаты оставшихся тестов не создаются. При доступном неотменённом RunJob агент пытается вернуть результат с gRPC `OK`, затем завершает процесс с кодом `1`, не принимая новые задания. Ошибка завершающей очистки после полностью обработанного набора сохраняет известные статусы и добавляет диагностику; это отдельный случай.

После успешной компиляции и получения результата для каждого переданного теста общий статус задания — `Completed`, независимо от статусов отдельных тестов. Успешные исполнения, ошибки решения, превышения лимитов и инфраструктурные ошибки отдельных тестов сохраняются в их результатах. Например, успешный тест, превышение времени и ошибка скачивания входа дают общий `Completed` с тремя результатами; процесс решения для теста с ошибкой скачивания не запускается. Этот общий статус означает завершение обработки набора, а не прохождение проверки.

Общий статус задания Completed означает успешную компиляцию и обработку всех тестов; остальные статусы сохраняются по правилам выше. RunJob возвращает структурированный результат с gRPC OK после попытки очистки, если вызов не отменён и транспорт доступен. Отмена не требует формирования результата для последующего чтения; известные S3-артефакты остаются, повтор может выполнить задание заново.

## 8. Внутренние компоненты

Это логические границы, а не требование создать отдельный проект/assembly для каждого раздела.

```text
RunnerAgent
  Grpc
    JudgeRunnerService
  Storage
    IObjectStorage
    S3ObjectStorage
  Execution
    ISubmissionRunner
    IsolateSubmissionRunner
  Languages
    ILanguageProvider
    CppLanguageProvider
  Workspace
    WorkspaceManager
```

| Компонент | Ответственность |
| --- | --- |
| `Grpc` | Приём заданий, перевод transport models, возврат результата |
| `Storage` | Скачивание/загрузка объектов и метаданные S3 через `IObjectStorage` |
| `Execution` | Локальный compilation/execution pipeline и преобразование isolate metadata |
| `Languages` | Поддерживаемые версии, toolchain, команды компиляции/запуска, необходимые файлы и окружение |
| `Workspace` | Создание, размещение файлов и очистка локальных рабочих областей |

Orchestration связывает получение задания, storage, workspace, runner и публикацию результата. `IsolateSubmissionRunner` не знает о S3 или gRPC: он получает локальные файлы и возвращает локальный результат и пути артефактов.

Orchestration удерживает единственный слот RunJob, связывает операции с отменой RPC и координирует независимую от отменённого токена очистку. Состояние текущего задания хранится в памяти только на время обработчика; кэша результата и восстановления нет. Локальный runner получает исходный файл и список тестов, компилирует один раз и возвращает локальные результаты.

Концептуальный контракт, не готовый код приложения:

```csharp
Task<ExecutionResult> ExecuteAsync(
    LocalSubmission submission,
    ExecutionLimits limits,
    CancellationToken cancellationToken);
```

В финальной форме контракта необходимо явно представить отдельные compilation/execution limits. `ISubmissionRunner` позволяет менять реализацию исполнения независимо от transport/storage. При необходимости низкоуровневый запуск одной стадии isolate можно выделить за дополнительную границу `ISandboxRunner`; это деталь будущей реализации.

Внутренний CancellationToken рабочей обработки связан с отменой RunJob, deadline и обнаруженным разрывом соединения; отмена останавливает текущую песочницу и дальнейший прогон. Для завершения процессов и очистки используется отдельный механизм управления, чтобы отменённый токен не пропускал очистку. Сигнал штатной остановки запрещает новые задания, но сам по себе не отменяет активный RPC.

Один экземпляр агента обслуживает один конкретный компилятор с фиксированным профилем. Реализация language provider задаётся на стороне агента и регистрируется явно; первый provider — C++23 с g++. Поля задания служат валидации совместимости с этим профилем, а не выбору компилятора внутри агента. Для MVP принимается только точная пара `language = "cpp"`, `language_version = "23"`; пустые значения, алиасы, другой регистр и неподдерживаемые значения дают `INVALID_ARGUMENT`. `"23"` — версия стандарта C++. Версия g++ остаётся внутренней деталью образа агента: мастер не должен её знать или передавать, отдельного поля версии компилятора в контракте задания нет. Совместимость задания проверяется только по `language` и `language_version`.

Дальнейшие реализации providers позволяют добавлять языки без переноса логики S3/gRPC в runner; каждый экземпляр агента по-прежнему обслуживает один конкретный компилятор. Команда компиляции, все флаги и настройки toolchain задаются на стороне агента в его профиле. Мастер не передаёт дополнительные флаги или произвольные команды. Отдельные resource limits компиляции по-прежнему поступают в задании. Конкретная версия g++ определяется и фиксируется образом агента при реализации. Согласованы флаги `g++ -std=c++23 -O2 -pipe -DONLINE_JUDGE` с явно заданными исходником и выходным файлом, динамическая линковка и необходимые runtime-библиотеки в execution sandbox только для чтения.

При выборе параметров новых профилей используем [настройки компиляторов Яндекс Контеста](https://contest.yandex.ru/docs/ru/compilers) как ориентир (сверено 6 ноября 2026 года), проверяя каждый параметр на нашей версии toolchain и в sandbox; автоматического копирования команд и версий нет. Для C++ сохраняются C++23, `-O2`, `-pipe`, `-DONLINE_JUDGE` и динамическая линковка. `ONLINE_JUDGE` — общее правило профилей: для компиляторов с условной компиляцией задаётся одноимённый символ средствами языка; для всех языков компиляция и исполнение получают явную переменную окружения `ONLINE_JUDGE=1`. Она задаётся агентом, не наследуется от host и не управляется заданием. Новые языки остаются за рамками MVP.

## 9. Жизненный цикл задания

1. Атомарно проверить остановку и занять единственный слот без очереди; при отказе вернуть UNAVAILABLE либо RESOURCE_EXHAUSTED. Проверить задание, при ошибке освободить слот без запуска и вернуть INVALID_ARGUMENT.
2. Создать workspace, скачать исходник и входы с проверкой SHA-256.
3. Один раз скомпилировать исходник, затем последовательно выполнить тесты в отдельных sandbox с независимыми лимитами. Если RPC не отменён, ошибки отдельных тестов не прерывают набор.
4. Опубликовать доступные артефакты и собрать результат. При отмене на любой стадии остановить текущие процессы и storage-операции, не начинать следующие тесты и новые публикации.
5. В обязательном завершающем участке очистить собственные процессы, sandbox и workspace независимо от токена RPC. Во время очистки слот занят.
6. При доступном неотменённом вызове вернуть результат в RunJob; завершить обработчик и после успешной очистки разрешить следующее задание. При отмене результат клиенту не гарантируется. Ошибка очистки запрещает новое задание и завершает процесс с кодом 1.

Логические состояния: свободен → обработка → очистка → свободен. При отмене между обработкой и очисткой завершаются процессы песочницы. Остановку можно запросить на любом этапе; при остановке или ошибке очистки возврата к приёму заданий нет. Кэша результатов и восстановления после перезапуска нет. Начальная очистка удаляет только собственные остатки; её ошибка завершает запуск без приёма заданий. Опубликованные S3-объекты не удаляются.

### Штатная остановка агента

При штатной остановке новые RunJob получают UNAVAILABLE. Активный RPC заканчивает набор, публикацию, очистку и ответ; затем сервер и процесс останавливаются. Если клиент отменяет его во время остановки, текущая песочница останавливается и очищается, затем процесс выходит. Незанятый агент завершается сразу. Дополнительного ожидания чтения результата или отдельного таймаута его получения нет. Настройки host/container должны позволять завершить текущий вызов и очистку; принудительное внешнее завершение может прервать их.

Ошибка очистки после обычного или отменённого вызова запрещает повторное использование среды и завершает процесс с кодом 1. При доступном RPC сохраняются известные результаты/статусы и диагностика очистки, агент пытается вернуть их до завершения; при отменённом или потерянном соединении ошибка фиксируется в служебной диагностике без ожидания клиента. Следующий запуск обязан успешно выполнить начальную очистку.

### Служебные логи

Для логирования и OpenTelemetry выбран [Texnokaktus.ProgOlymp.Platform](https://github.com/Texnokaktus-ProgOlymp/platform), использующий [OpenTelemetry-Library](https://github.com/Texnokaktus-ProgOlymp/OpenTelemetry-Library). Сохраняется стандартный текстовый stdout пакета; прежнее требование JSON отменено. Изученный API platform предоставляет `WebApplicationBuilder.UsePlatform()`, требует `SERVICE_NAME` и позволяет расширять Serilog, tracing и metrics. Повторно регистрировать те же OpenTelemetry providers/exporters отдельно от platform не требуется. Версия/источник пакета и технические детали инструментации ещё уточняются; интеграция и AOT-совместимость пока не проверены.

Контекст логов содержит стадию и причину ошибки, когда они применимы, `job_id` для событий задания и `test_id` для событий конкретного теста. Стандартный консольный шаблон не обязан печатать все структурированные свойства. Секреты, исходники, входные данные и содержимое stdout/stderr, включая потоки компилятора, не включаются в служебные логи и телеметрию, в том числе через исключения, сообщения библиотек и обогащение. Потоки по-прежнему публикуются как S3-артефакты.

`SERVICE_NAME` различает язык и версию языка профиля агента. Для C++23 при развёртывании задаётся `SERVICE_NAME=runner-agent-cpp-23`: `cpp-23` означает язык/версию языка, а не версию g++ или сборки агента. Агенты других языков или версий языка получают другие имена сервиса; экземпляры одного профиля различаются по `service.instance.id`. Это правило будущих профилей не расширяет состав языков MVP. Адрес коллектора и параметры экспорта задаются при развёртывании средствами platform/OpenTelemetry.

Принятое задание получает отдельную операцию трассировки на всю обработку со стадиями подготовки, компиляции, тестирования и публикации. Трасса включает рабочие стадии и обязательную очистку, в том числе после отмены RunJob, и заканчивается после завершения серверной обработки. Собственные метрики агента включают количество заданий по исходу, длительность стадий, ошибки и повторы storage. `job_id` и `test_id` используются в логах и трассах, но не в метках метрик. Точные имена инструментов и техническая связь контекстов уточняются при реализации.

### Конфигурация

Обычные параметры задаются в `appsettings.json`, переменные окружения переопределяют значения файла; credentials поступают только из окружения. Хранилище настраивается в секции `S3`, workspace и остановка — в `Runner`. Platform/OpenTelemetry сохраняют собственные имена настроек, включая `SERVICE_NAME`. Конфигурация фиксируется при запуске, изменение требует перезапуска; горячая перезагрузка не предусматривается.

Корень workspace задаётся конфигурацией, по умолчанию `/var/lib/runner-agent`. Агент создаёт внутри собственные рабочие каталоги; S3-ключи в локальные пути не преобразуются. Начальная очистка затрагивает только собственные рабочие области; механизм владения каталогами/boxes ещё уточняется в Q-09.

### Работоспособность API и код завершения

Стандартный gRPC Health Checking работает на существующем gRPC-порту без отдельного HTTP endpoint. После успешной локальной инициализации API имеет SERVING; обработка RunJob, отмена и очистка, недоступность MinIO сами по себе этот статус не меняют. Health не занимает слот задания. При штатной остановке API остаётся SERVING, пока завершается текущий вызов и очистка; новые RunJob получают UNAVAILABLE. Перед остановкой RPC-сервера выставляется NOT_SERVING. При ошибке очистки новые задания также запрещены, после завершения обработки текущего вызова сервер и процесс останавливаются. Health означает доступность API, а не свободный слот.

Код управляемого завершения — 0 при штатной остановке после текущего вызова и очистки, 1 при ошибке запуска или невозможности очистить sandbox/завершить его процессы. Ошибки компиляции, тестов и отдельные сбои storage сами по себе процесс не завершают. Успешная отмена с очисткой освобождает раннер для следующего задания, если агент не останавливается. При отменённом RPC ожидание доставки результата не требуется. Принудительное внешнее завершение этими кодами не нормализуется.

## 10. .NET 10: JIT сначала, Native AOT как цель

Первая разработка и отладка — .NET 10 JIT. Архитектурная цель для production — Native AOT publication после стабилизации агента и подтверждения совместимости выбранных зависимостей.

Код с самого начала писать AOT-friendly:

- Использовать статически известные типы, заранее генерируемые protobuf-модели и явную регистрацию language providers.
- Для JSON, если он понадобится, применять `System.Text.Json` source generation.
- Избегать runtime plugins, dynamic loading и ненужной reflection-heavy сериализации.
- При появлении реализации проверять публикацию с `PublishAot=true` в CI и разбирать trimming/AOT warnings.
- Проверять на целевой Linux-платформе реальную работу gRPC, S3, запуска isolate и обработки результатов в опубликованной AOT-сборке.

AOT-совместимость конкретных версий gRPC-библиотек и выбранного `AWSSDK.S3` не считается доказанной этими заметками. Совместимость зависимостей и способ размещения gRPC service должны проверяться отдельно.

Для выбранного долгоживущего агента скорость старта не является главным аргументом выбора AOT. Ожидаемый эффект AOT — более компактное развёртывание агента и меньше динамического поведения; это не гарантия безопасности или конкретного выигрыша памяти. При Native AOT публикации самому агенту не нужен отдельно установленный .NET runtime. Compiler/runtime поддерживаемых языков остаются самостоятельной частью образа: будущая поддержка C# не зависит от JIT/AOT режима RunnerAgent.

## 11. Статус согласования и техническая реализация

Требования MVP согласованы единым завершающим пакетом. Окончательный `.proto` оформляется по принятым сообщениям, статусам и правилам; нумерация полей, вложенные типы и техническая валидация определяются при реализации без изменения семантики API.

Независимый каркас и минимальный локальный прототип не ждут готовой реализации wire-контракта и lifecycle; эти работы могут выполняться параллельно. Возможности Linux-среды и isolate проверяются на прототипе. Это порядок разработки уже согласованного долгоживущего агента, а не пересмотр требований. Семь этапов и декомпозиция каркаса на задачи 1.1–1.6 перенесены в [design](openspec/changes/implement-runner-agent/design.md#implementation-sequence) и [tasks](openspec/changes/implement-runner-agent/tasks.md).

MVP остаётся на JIT. В CI добавляется отдельная информационная AOT-проверка: неуспех отражается в результатах, но не блокирует рабочий JIT-образ. Переход production на AOT требует успешной сборки и полного набора интеграционных тестов AOT-варианта, включая platform/OpenTelemetry. Эти проверки ещё не выполнены.

Разработчик самостоятельно выбирает, фиксирует и проверяет совместимые версии Linux-образа, SDK, isolate, g++, пакетов и actions, техническую настройку rootfs/cgroups, имена настроек/метрик, fixtures, concurrency и хранение CI artifacts в бесплатной квоте. Новых пользовательских лимитов и платных сервисов не добавляется. Существенные отклонения от требований выносятся на обсуждение; обычные инженерные детали не требуют отдельного согласования.

Kafka и другие транспорты отложены за пределы MVP. Сохраняется gRPC/S3-контракт с единственным RunJob. Подробный реестр технической детализации находится в [design](openspec/changes/implement-runner-agent/design.md#open-questions), отслеживаемые задачи реализации — в [tasks](openspec/changes/implement-runner-agent/tasks.md). Он не является списком незакрытых продуктовых решений и не подтверждает работоспособность полного MVP; проверки каркаса описаны отдельно.

## 12. Структура репозитория и CI/CD

GitHub выбран основным репозиторием кода, CI и выпусков, Gitea — независимым зеркалом. Перенос, обновление origin и пересоздание Gitea-репозитория пользователь выполняет самостоятельно; это внешняя настройка, а не задача реализации RunnerAgent. Зеркалирование настраивается только на стороне Gitea: GitHub и его Actions не содержат workflow, secrets, проверок или зависимостей для зеркала. Доступность Gitea не влияет на проверки и выпуск в GitHub/GHCR. Сам факт переноса и адрес нового origin фиксируются после его выполнения, а не считаются уже настроенными.

Согласованный runner — стандартный `ubuntu-24.04` (Linux VM); перед интеграционными тестами проверяются необходимые возможности privileged Docker/cgroups v2/isolate. Имя образа — `ghcr.io/texnokaktus-progolymp/runner-agent-cpp-23`. Для истории выпусков после успешной публикации образа создаётся Git-тег `vYYYY.M.D.<run_number>` на коммите, из которого собран образ. Тег Docker-образа сохраняет формат `YYYY.M.D.<run_number>` без `v`. При повторном запуске существующий Git-тег на том же коммите считается нормальным; тег на другом коммите вызывает ошибку без перезаписи. Сбой создания Git-тега делает этап выпуска неуспешным, опубликованный образ сохраняется. Устаревшие проверки от push можно отменять до публикации, но уже начатая публикация новым push не прерывается.

CI запускается на push в `master` публичного GitHub-репозитория; pull request и отдельные PR-проверки не предусматриваются. Pipeline выполняет сборку, unit-тесты, сборку Docker-образа и интеграционные тесты; только после успешных обязательных проверок публикует тот же образ в GHCR без пересборки. Между jobs образ передаётся через `docker save/load`. TRX и coverage сохраняются, в том числе при неуспешных тестах, если файлы сформированы; summary публикации содержит полное имя образа с тегом для деплоя.

Интеграционные тесты используют стандартный одноразовый GitHub-hosted Linux VM runner, бесплатный для публичного репозитория; платные larger runners и постоянный judge-host не используются. Выбран `ubuntu-24.04`; совместимость privileged Docker/cgroups v2/isolate ещё проверяется пробным запуском. Бесплатность вычислений не отменяет квоту artifact storage: временный Docker-архив и отчёты должны укладываться в бесплатное хранение, параметры retention/удаления ещё выбираются. Условия и источники приведены в [описании CI](openspec/changes/implement-runner-agent/repository.md#github-actions).

Для MVP согласован один production-проект с каталогами `Grpc`, `Storage`, `Execution`, `Languages`, `Workspace`, без выделения отдельных библиотек. Два тестовых проекта: `.Tests` для локальной логики без внешних сервисов и `.IntegrationTests` для gRPC, MinIO и isolate; оба используют NUnit на Microsoft.Testing.Platform.

Общие настройки проектов: `TargetFramework=net10.0`, `LangVersion=14.0`, `Nullable=enable`, `ImplicitUsings=enable`. Версии NuGet-зависимостей централизованно фиксируются в `Directory.Packages.props`, без плавающих версий. Платформа MVP — `linux/amd64`; поддержку `arm64` добавляют отдельно после проверки isolate и toolchain. Проекты host, `.Tests` и `.IntegrationTests` созданы; интеграционный проект уже проверяет entry point, HTTP pipeline и конфигурацию через WebApplicationFactory. Production-образ ещё не создан.

Согласована организация репозитория: README с функционалом, API, сборкой, тестированием и деплоем; solution в формате `.slnx`; production-код в `src/`; тестовые проекты в `tests/`; workflow в `.github/workflows/`. Pipeline собирает и тестирует приложение, упаковывает Docker image и публикует его в GHCR.

Общие MSBuild-настройки располагаются в корневом `Directory.Build.props`, версии NuGet-пакетов — в `Directory.Packages.props` с CPM. В `src/`, `tests/` и при необходимости отдельных проектах допускаются свои `Directory.Build.props` с явным импортом родительского файла. Общие тестовые зависимости, включая NUnit и NSubstitute, относятся к `tests/`. В `src/Directory.Build.props` задаётся `InternalsVisibleTo` для соответствующего проекта с суффиксом `.Tests` и для `DynamicProxyGenAssembly2`; эти настройки наследуются всеми production-проектами.

Тесты с самого начала используют NUnit на Microsoft.Testing.Platform, включая нативный MTP-режим `dotnet test` в .NET 10. Версия SDK и выбор `test.runner=Microsoft.Testing.Platform` фиксируются в `global.json`; общие настройки NUnit runner и MTP-расширения покрытия/TRX — в `tests/Directory.Build.props`.

Образ публикуется с тегом версии `YYYY.M.D.<run_number>`; дата берётся из исходного коммита в Europe/Moscow. Повторная попытка workflow сохраняет версию. Для ручного деплоя достаточно тега версии. Автоматический деплой не планируется: pipeline завершается публикацией в GHCR и фиксацией выпуска Git-тегом.

Подробное дерево, наследование настроек, версии каркаса и план Docker/CI находятся в [структуре репозитория](openspec/changes/implement-runner-agent/repository.md). [README](README.md) содержит проверенные команды каркаса; ручной production-деплой пока остаётся планом.

### Реализованный каркас (5 ноября 2026)

Entry point и настройка host находятся непосредственно в top-level коде `Program.cs`, без отдельного класса-фабрики, метода CreateApplication и общего catch. Пустая partial-декларация Program нужна только для доступа WebApplicationFactory к entry point. По текущему решению пользователя нормализация ошибок старта к коду 1 пока отложена до задачи 6.5; необработанная ошибка .NET даёт ненулевой код и стандартную диагностику. Используются стандартные источники конфигурации ASP.NET Core; горячая перезагрузка отключается штатным параметром `hostBuilder:reloadConfigOnChange=false`, без очистки и ручной пересборки источников. Для исходников и конфигурации принят отступ в четыре пробела. `.editorconfig` не используется; преобразованием окончаний строк управляет Git через `autocrlf`. В test props global usings и PackageReference размещаются в отдельных ItemGroup.

Зафиксированы SDK 10.0.403 с `latestPatch`/без preview, встроенные .NET analyzers `10.0-recommended`, deterministic build и warnings as errors. Platform 2026.9.19.2 подключается однократно через `UsePlatform()`; её транзитивная OpenTelemetry — 2026.9.19.15. NUnit 4.6.1, adapter 6.3.1/MTP 2.4.1, NSubstitute 6.2.0, CodeCoverage 18.11.2, TrxReport 2.4.1 и ReportGenerator 5.5.11 образуют проверенный тестовый стек. Тестовые пакеты находятся только в `tests/Directory.Build.props`; доступ internal для `.Tests`/DynamicProxy задан в `src/Directory.Build.props`.

Host проверяет непустой environment `SERVICE_NAME` до подключения platform. `appsettings.json` читается рядом со сборкой без reload; окружение и аргументы запуска переопределяют настройки. `Runner:WorkspaceRoot` по умолчанию `/var/lib/runner-agent`; на стадии каркаса оператор подготавливает существующий абсолютный каталог, отличный от корня файловой системы. Проверка записи использует уникальный файл с DeleteOnClose, не создаёт job workspace и не очищает существующие файлы. Рабочие области и начальная очистка собственных остатков относятся к последующим этапам. Пока нет обязательных проверок MinIO/isolate, RunJob и health; это приложение для проверки каркаса, а не готовый агент.

Базовый workflow использует `ubuntu-24.04`, checkout 4.2.2, setup-dotnet 4.3.1 и upload-artifact 4.6.2; retention отчётов 3 дня. Restore получает GitHub Packages credentials только в соответствующем шаге через встроенный token с read-доступом к platform/OpenTelemetry. Production secrets не нужны. Linux AOT job отдельный, информационный, сохраняет лог; результат реального GitHub CI/AOT ещё не получен. После обновления WSL Docker Desktop подтверждает cgroups v2, kernel 6.18.54.1 и необходимые memory/pids-файлы. Probe isolate v2.7 в приватном cgroup namespace успешно запустил g++ 13.3.0 и очистил box/cgroup. Полная приёмка sandbox ещё не выполнена.

### Локальный sandbox-прототип

Реализован `IsolateSubmissionRunner` за публичным `ISubmissionRunner`: локальный `LocalSubmission` содержит WorkspacePath, SourcePath, упорядоченные LocalTest и независимые compilation/execution limits. Результаты содержат nullable метрики/exit code/signal, локальные stdout/stderr/metadata, подтверждённые нарушения и отдельные статические инфраструктурные коды. Признак EnvironmentReusable запрещает продолжение после ошибки cleanup; принудительная остановка всего host будет соединена с orchestration на этапах 5–6. Runner не зависит от gRPC/S3.

WorkspaceManager выдаёт JobWorkspace в runner-agent-jobs под настроенным корнем. Создавший lease код владеет им до чтения/публикации артефактов, затем Dispose удаляет только этот уникальный каталог. Каждый sandbox стадии использует заново созданные box 0/cgroup box-0 и UID/GID 60000 в приватном контейнере; box и cgroup удаляются до следующего запуска. Число тестов не ограничивается количеством box IDs.

Зафиксированы isolate v2.7 commit 8f185bb37f3f23e29b33b0c7727c91c13429abe3, g++ 13.3.0 (Ubuntu package 13.3.0-6ubuntu2~24.04.1) и runtime 10.0.14/Ubuntu 24.04. Экспериментальные Dockerfile, cgroup bootstrap и запуск тестов находятся в tests/prototype и не являются production deployment. Bootstrap требует приватный cgroup namespace, перемещает управляющие процессы в отдельную cgroup и включает cpu/memory/pids для boxes. Startup-проверка подключена стандартным IHostedService до запуска HTTP-сервера: приватная cgroup управляющего процесса, делегированные cpu/memory/pids, обязательные файлы, запись/readback swap/OOM/pids и пробный процесс isolate с метриками и cleanup. Эксклюзивная блокировка /run/isolate/runner-agent.lock удерживается до Dispose host. Crash recovery ещё не подключён.

Isolate получает полностью очищенное окружение с PATH/LANG, а компилятор и решение — также явную ONLINE_JUDGE=1; его стандартная переменная LIBC_FATAL_STDERR_=1 разрешена. Read-only mounts: usr/bin/lib/lib64; proc ограничен isolate, dev содержит только четыре необходимых устройства, box/tmp отдельны и доступны для записи. Stdout/stderr читаются как байтовые pipe-потоки с независимыми ограничениями в файлы вне sandbox. Метрики берутся из cgroup и монотонного wall time isolate до cleanup. Memory.max сверяется с округлённым до страницы бюджетом; memory.peak читается в байтах. Timers ограничены signed int32 миллисекундами выбранного isolate, memory после округления — signed int32 KiB, преобразования проверяются до запуска.

Для отмены применяется cgroup.kill и SIGTERM keeper, чтобы isolate собрал proxy, вместо немедленного SIGKILL keeper. POSIX kill подключён через LibraryImport; AllowUnsafeBlocks включён только для source-generated interop в host-проекте. Cleanup не зависит от отменённого токена. Проверены CPU дочерних процессов, групповой OOM, лимиты процессов/потоков с обработанным отказом, выходные потоки, UID/environment/proc/network namespaces, независимость файлов/порядок 8,2,5 и отмена без оставшихся proxy/box/cgroup. Полная приёмка AT и граничные инфраструктурные сбои остаются открытыми задачами.

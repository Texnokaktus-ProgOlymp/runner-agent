# RunnerAgent

Агент проверяющей системы для компиляции и исполнения олимпиадных решений в isolate. Первый MVP рассчитан на C++23: одно задание содержит один файл исходного кода и N тестов, исходный код компилируется один раз на набор. Агент отдельно ограничивает компиляцию и запуски, собирает результаты по тестам и очищает песочницы после обработки набора.

**Состояние проекта:** требования MVP согласованы; следующий этап — реализация и техническая проверка. Сейчас в репозитории находятся документация и инструкции для разработки. Описанные ниже solution, проекты, Dockerfile и workflow запланированы; приложение и опубликованный образ пока отсутствуют.

## Документация

- [Техническая спецификация](docs/SPECIFICATION.md) — требования MVP, контракты, жизненный цикл, обработка ошибок, критерии приёмки и технические задачи реализации.
- [Архитектура](ARCHITECTURE.md) — согласованные решения, границы ответственности и целевое развитие.
- [Структура репозитория и сборка](docs/REPOSITORY.md) — организация проектов и предложение по Docker/CI.

Согласованный профиль: `g++ -std=c++23 -O2 -pipe -DONLINE_JUDGE` с явными исходником/выходным файлом, динамическая линковка. Sandbox предоставляет системные файлы/toolchain только для чтения, запись — в собственные рабочие/временные каталоги; compiler/solution работают без root. Возможности окружения ещё должны быть подтверждены тестами.

MVP остаётся на JIT; отдельный информационный AOT check не блокирует JIT-выпуск. Переход на AOT требует успешной сборки и полного integration-набора, включая platform/OpenTelemetry. Kafka и другие транспорты отложены за пределы MVP. Версии зависимостей и остальные инженерные детали выбираются и проверяются при реализации без новых пользовательских лимитов и платных сервисов; существенные отклонения обсуждаются.

## API и обмен файлами

```text
Мастер -- StartJob: исходный код + N тестов --> RunnerAgent
Мастер <-- подтверждение начала работы ---+
                                          +-- S3: скачать входные файлы
                                          +-- isolate: одна компиляция
                                          +-- isolate: запуск тестов
                                          +-- S3: загрузить артефакты
                                          +-- очистить песочницы
                                          +-- сохранить результат; занят
Мастер -- GetResult ---------------------->+
Мастер <-- результат набора + S3 refs -----+ ресурс свободен
```

Модель API асинхронная: агент сразу подтверждает принятие задания, мастер забирает итоговый результат через `GetResult`. Имена RPC `StartJob` и `GetResult`, состояния ответов и коды gRPC согласованы в [спецификации, раздел 3.4](docs/SPECIFICATION.md#34-имена-rpc-ответы-и-коды-grpc); окончательный `.proto` ещё не утверждён.

Для MVP gRPC работает по HTTP/2 без HTTPS/TLS и без аутентификации в доверенной внутренней сети. Endpoint внутри контейнера по умолчанию — `0.0.0.0:8080`; адрес и порт настраиваются. Deadline вызова задаёт мастер; отмена RPC или истечение deadline не прекращают уже принятое задание и не восстанавливают уже извлечённый результат. Команда и все флаги компиляции C++23 задаются агентом; мастер передаёт resource limits, но не дополнительные флаги компилятора.

- Запрос: заданный мастером положительный `job_id` типа `int64` и положительный `test_id` каждого теста типа `int32` — порядковый номер теста в группе, язык/версия, ссылки на один файл исходного кода и входные данные тестов в S3 по ключам и SHA-256, префикс выходных объектов, отдельные лимиты компиляции и общий профиль execution limits, применяемый независимо к каждому тесту.
- Итоговый результат: исходный `job_id`, общий результат компиляции, результаты отдельных тестов с исходными `test_id`, метрики ресурсов, exit code/signal и ссылки на stdout, stderr, вывод компилятора.
- Сбой подготовки исходника или компиляции из-за инфраструктуры даёт общий `InfrastructureError` со стадией и причиной и пустым списком тестов. Доступные данные компиляции сохраняются; если она не начиналась, её результат явно отсутствует. Ошибка компиляции кода даёт `CompilationError`.
- После успешной компиляции и получения результата каждого теста общий статус задания — `Completed`, включая смешанные результаты с ошибками исполнения, превышением лимитов или инфраструктурными ошибками отдельных тестов. Это завершение обработки набора; правильность ответов оценивает мастер.
- При инфраструктурном сбое тест получает итоговый `InfrastructureError`, а известный результат исполнения и инфраструктурная диагностика сохраняются отдельно. Если процесс не запускался, результат исполнения отсутствует. Ссылки возвращаются только на опубликованные артефакты; остальные тесты продолжаются.
- Сбой публикации вывода компилятора отражается в диагностике задания, без потери данных компиляции и без ссылки на неопубликованный поток. Успешная компиляция позволяет продолжить тесты до общего `Completed`; при ошибке компиляции сохраняется `CompilationError` без запуска тестов.
- Задание содержит хотя бы один тест; номера тестов уникальны внутри задания и могут повторяться в разных заданиях. Нулевые/отрицательные ID, повтор номера внутри задания или пустой набор дают `INVALID_ARGUMENT` без принятия задания.
- Агент обрабатывает переданный список в порядке запроса, без проверки полноты группы, пропусков или возрастания номеров. Он не добавляет тесты, не сортирует и не перенумеровывает их.
- Отдельных верхних пределов числа тестов и размера gRPC-запроса задания нет. Лимиты ресурсов компиляции и исполнения сохраняются.
- Общего таймаута выполнения задания нет. Мастер явно передаёт все положительные значения лимитов компиляции и исполнения; пропуски, ноль и отрицательные значения дают `INVALID_ARGUMENT`.
- CPU и память учитываются для всей cgroup с дочерними процессами и потоками; лимит процессов включает основной процесс и потоки. Память лимитируется и измеряется одной метрикой cgroup с файловым кешем, пик возвращается в байтах.
- cgroups v2 обязательны; при недоступности необходимых контроллеров/метрик агент завершает запуск с ошибкой. Swap песочницы отключён, OOM завершает всю группу. Лимит памяти округляется вверх до страницы и возвращается в результате; пик читается из `memory.peak`.
- `pids.max` и события `pids.events` обеспечивают лимит процессов/потоков и подтверждение `ProcessLimitExceeded`, в том числе при обработанном программой отказе. Отсутствие обязательных метрик после запуска отражается как инфраструктурная ошибка с сохранением доступных данных.
- Stdout/stderr компилятора сохраняются раздельно, с независимыми лимитами и артефактами `compilation/stdout.txt` / `compilation/stderr.txt`.
- Превышение лимита любого потока компилятора останавливает компиляцию: оба частичных потока сохраняются, общий статус — `CompilationError`, причина — `OutputLimitExceeded` при отсутствии более приоритетного нарушения; тесты не запускаются.
- Время в миллисекундах и размеры в байтах имеют тип `int64`, лимит процессов/потоков — `int32`. Неприменимые в песочнице значения дают `INVALID_ARGUMENT`.
- Причины завершения: `Success`, `RuntimeError`, `CpuTimeLimitExceeded`, `WallTimeLimitExceeded`, `MemoryLimitExceeded`, `OutputLimitExceeded`, `ProcessLimitExceeded`. При нескольких подтверждённых нарушениях приоритет: память → вывод → CPU → wall time → процессы → runtime error; остальные причины остаются в диагностике.
- Один экземпляр агента обслуживает один конкретный компилятор. Для MVP поля `language = "cpp"` и `language_version = "23"` проверяются на точное соответствие его фиксированному профилю; они не переключают компилятор. Версия g++ — внутренняя деталь образа; мастер её не передаёт и не обязан знать. Пустые или неподдерживаемые значения, другой регистр и алиасы дают `INVALID_ARGUMENT`.
- При ошибке компиляции возвращаются `CompilationError` и вывод компилятора; список результатов тестов пуст, тесты не запускаются.
- Тесты выполняются последовательно в порядке запроса. После ошибки решения, превышения лимита или инфраструктурной ошибки отдельного теста агент продолжает набор. Инфраструктурная ошибка получает отдельный статус теста.
- Для stdout и stderr задаются отдельные лимиты. Превышение любого из них останавливает процесс с `OutputLimitExceeded`; полученная часть каждого потока сохраняется в пределах его лимита.
- Проверку корректности ответов и вынесение AC/WA выполняет мастер; агент возвращает статусы исполнения и выходные артефакты.
- Файлы хранятся в MinIO, агент обращается к нему через `AWSSDK.S3` с endpoint из конфигурации и `ForcePathStyle = true`. Credentials читаются только из окружения агента (`AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, необязательный `AWS_SESSION_TOKEN`); отсутствие обязательных значений — ошибка запуска. Регион подписи клиента по умолчанию — `us-east-1`, с возможностью переопределения; сервер без явно заданного региона поддерживается. При запуске проверяется локальная конфигурация без обязательных сетевых проверок MinIO; доступность и права проверяются рабочими операциями. gRPC используется для управления.
- Sandbox не получает сеть или credentials агента. Перед запуском isolate окружение дочернего процесса полностью очищается и собирается по allowlist; `--full-env` запрещён. Секреты недоступны также через файлы, аргументы и `/proc` агента. Эти требования должны быть проверены для компиляции и исполнения при реализации.
- Версии объектов S3 не используются в текущем контракте; содержимое входных файлов проверяется по SHA-256. Хеши входных и выходных объектов передаются массивом из 32 байт (`bytes` в protobuf).
- Внутри `result_prefix` используются `compilation/stdout.txt` и `compilation/stderr.txt`, `tests/{test_id}/stdout.txt` и `tests/{test_id}/stderr.txt`. Мастер выдаёт новый префикс на каждый запуск; агент не хранит историю префиксов.
- `key` и `result_prefix` непустые; завершающий `/` у префикса допустим, разделитель перед суффиксом добавляется при его отсутствии. S3-ключи не используются как локальные пути. Проверки существования выходных объектов нет: повторный префикс может привести к перезаписи. Отдельных лимитов размера исходника и входов тестов нет.
- Сбой публикации артефакта не останавливает загрузку остальных; повторы используют тот же ключ и содержимое. Уже опубликованные объекты агент не удаляет. Хранение и удаление задаются мастером или lifecycle-политикой MinIO.
- Повторами MinIO управляет агент, автоматические повторы SDK отключены: до трёх попыток на операцию, задержки 200 мс и 500 мс. Повторяются обрывы соединения, сетевые таймауты, HTTP `429`/`500`/`502`/`503`/`504` и `SlowDown`; скачивание начинается заново. Отсутствие объекта/bucket, ошибки доступа/credentials и SHA-256 не повторяются; отмена storage-операции прекращает попытки.
- В конфигурации агента задаются два bucket: отдельный для исходного кода и общий для входных данных тестов и результатов. Префикс выходных объектов задаёт мастер; ключи вывода компилятора и stdout/stderr тестов внутри него формирует агент.
- Задание продолжает выполняться после завершения исходного RPC. Агент занят до выдачи готового результата через `GetResult`, даже если вычисления и очистка уже завершены. `GetResult` атомарно забирает готовый результат из состояния агента и освобождает ресурс до отправки ответа; артефакты в S3 остаются. После извлечения обрыв соединения не восстанавливает результат. Отдельного подтверждения нет.
- Пока ресурс занят, запрос с другим `job_id` получает ошибку «ресурс занят», а повтор с текущим `job_id` и одинаковым содержимым — ответ «задание уже принято», без повторного исполнения. Изменённое содержимое при текущем ID вызывает ошибку конфликта; принятое задание и результат не меняются.
- При повторе сравниваются разобранные значения всех полей задания, включая порядок тестов, ссылки и хеши, префикс результатов и лимиты. Байты protobuf не сравниваются, файлы из S3 для этой проверки повторно не скачиваются.
- Проверки `StartJob` идут в порядке: корректность запроса → текущий ID и содержимое → остановка → занятость → принятие. Некорректный запрос всегда получает `INVALID_ARGUMENT`; валидные повторы текущего задания обрабатываются и при остановке. Для `GetResult` сначала проверяется корректность запроса, затем наличие задания и готовность результата; остановка не мешает чтению, пока сервер работает.
- После выдачи результата или перезапуска история ID не хранится: прежний ID может быть принят заново. Мастер выдаёт новый `job_id` для каждого нового запуска.
- Пока запрошенное задание выполняется, `GetResult` сразу отвечает «не завершено», без ожидания и освобождения ресурса. Если запрошенного задания нет, включая чужой ID или уже выданный результат, ответ — «не найдено»; состояние текущего задания не меняется.
- В обычном режиме долгоживущий агент ожидает получения готового результата без таймаута и остаётся занят до `GetResult`.
- Операция отмены задания в текущем API не предусмотрена.
- В MVP состояние задания и непрочитанный результат хранятся в памяти и теряются при перезапуске агента; повторный запуск организует мастер.

При штатной остановке агент перестаёт принимать новые задания, завершает текущий набор, публикует артефакты и очищает песочницы. Затем ожидает `GetResult` в течение настраиваемого таймаута, по умолчанию 30 секунд; время выполнения задания в него не входит. Если результат уже готов, отсчёт начинается при запросе остановки. После обслуживания `GetResult` агент завершает работу; если мастер не забрал результат до истечения таймаута — выходит с потерей результата в памяти, сохраняя S3-артефакты.

Перед приёмом заданий агент очищает оставшиеся собственные workspace и isolate boxes; при неуспехе завершает запуск с ошибкой. Ошибка очистки после задания сохраняет результаты и их статусы с дополнительной диагностикой, запрещает новые задания и переводит агент к завершению с тем же таймаутом получения результата. Среда после неуспешной очистки повторно не используется в этом процессе.

Для MVP выбран долгоживущий агент, обрабатывающий одно задание за раз. Контейнер запускается при развёртывании и используется для нескольких заданий; после выдачи результата агент принимает следующее задание, если не начата штатная остановка. Подробности: [архитектура](ARCHITECTURE.md).

Bucket создаются заранее при развёртывании; агент их не создаёт и не меняет их настройки. Для логирования и OpenTelemetry выбран [Texnokaktus.ProgOlymp.Platform](https://github.com/Texnokaktus-ProgOlymp/platform): сохраняется стандартный текстовый stdout, JSON не требуется. Контекст включает `job_id`/`test_id`, стадию и причину ошибки, когда они применимы; подключение через `UsePlatform()` требует `SERVICE_NAME`. При развёртывании задаётся `SERVICE_NAME=runner-agent-cpp-23`; экспорт настраивается средствами platform/OpenTelemetry. Версия пакета ещё уточняется. Секреты, исходники, входные данные и содержимое stdout/stderr в служебные логи и телеметрию не включаются.

Для проверки API согласован gRPC Health Checking на том же порту. `SERVING` сохраняется при занятости, ожидании результата, недоступности MinIO и завершении принятого задания при остановке; новые задания при остановке отклоняются. `NOT_SERVING` выставляется перед остановкой RPC-сервера. Код управляемого завершения — `0` при штатной остановке (включая таймаут ожидания результата), `1` при ошибке запуска или завершении из-за ошибки очистки. Ошибки заданий сами по себе агент не завершают.

Трассировка охватывает обработку задания со стадиями подготовки, компиляции, тестирования и публикации независимо от длительности `StartJob`. Метрики включают количество заданий по исходу, длительность стадий, ошибки и повторы storage. `job_id`/`test_id` используются в логах и трассах, но не в метках метрик; экземпляры агента различаются по `service.instance.id`.

В имени `runner-agent-cpp-23` суффикс `cpp-23` обозначает язык и его версию. Агенты других языковых профилей используют другие `SERVICE_NAME`, экземпляры одного профиля различаются по `service.instance.id`.

Обычные параметры задаются в `appsettings.json`, переменные окружения переопределяют их; credentials остаются только в окружении. Секции: `S3` для хранилища, `Runner` для workspace/остановки; platform/OpenTelemetry сохраняют собственные имена. Конфигурация фиксируется при запуске, изменение требует перезапуска. Корень workspace настраивается, по умолчанию `/var/lib/runner-agent`; рабочие каталоги создаются внутри, S3-ключи в локальные пути не преобразуются.

## Структура репозитория

Согласованы `.slnx`, общие `Directory.Build.props`, CPM в `Directory.Packages.props` без плавающих версий, один production-проект в `src/`, два тестовых проекта (`.Tests` и `.IntegrationTests`) в `tests/` и GitHub Actions в `.github/workflows/`. Внутри production-проекта — каталоги `Grpc`, `Storage`, `Execution`, `Languages`, `Workspace`, без отдельных библиотек. Настройки: `net10.0`, C# 14, nullable reference types и implicit usings. Конкретные версии зависимостей выбираются и проверяются при создании каркаса; реализация пока отсутствует.

Платформа MVP — Linux `amd64`; arm64 добавляется отдельно после проверки isolate и toolchain.

Полное дерево, область действия настроек и проект pipeline описаны в [структуре репозитория](docs/REPOSITORY.md).

## Сборка и тестирование

После создания проектов SDK и тестовая платформа Microsoft.Testing.Platform будут выбираться через `global.json`. Тесты пишутся на NUnit. Планируемая последовательность из корня репозитория:

```sh
dotnet tool restore
dotnet restore Texnokaktus.ProgOlymp.RunnerAgent.slnx
dotnet build Texnokaktus.ProgOlymp.RunnerAgent.slnx -c Release --no-restore
dotnet test --project tests/Texnokaktus.ProgOlymp.RunnerAgent.Tests/Texnokaktus.ProgOlymp.RunnerAgent.Tests.csproj -c Release --no-build -- --coverage --coverage-output-format cobertura --report-trx
docker build -f src/Texnokaktus.ProgOlymp.RunnerAgent/Dockerfile -t runner-agent:local .
```

Эти команды описывают будущий порядок; в текущем репозитории запускать их ещё рано. Unit-тесты не требуют isolate. Integration-тесты будут проверять собранный образ в Linux-среде с Docker, privileged containers и подходящей конфигурацией cgroups. Способ передачи образа и настройки тестового окружения будут добавлены вместе с тестовыми fixtures.

## Публикация и деплой

Согласованный runner — стандартный `ubuntu-24.04` (Linux VM); перед интеграционными тестами проверяются необходимые возможности privileged Docker/cgroups v2/isolate. Имя образа — `ghcr.io/texnokaktus-progolymp/runner-agent-cpp-23`. Для истории выпусков после успешной публикации образа создаётся Git-тег `vYYYY.M.D.<run_number>` на коммите, из которого собран образ. Тег Docker-образа сохраняет формат `YYYY.M.D.<run_number>` без `v`. При повторном запуске существующий Git-тег на том же коммите считается нормальным; тег на другом коммите вызывает ошибку без перезаписи. Сбой создания Git-тега делает этап выпуска неуспешным, опубликованный образ сохраняется. Устаревшие проверки от push можно отменять до публикации, но уже начатая публикация новым push не прерывается.

CI запускается на push в `master` публичного GitHub-репозитория; pull request и отдельные PR-проверки не предусматриваются. Pipeline выполняет сборку, unit-тесты, сборку Docker-образа и интеграционные тесты; только после успешных обязательных проверок публикует тот же образ в GHCR без пересборки. Между jobs образ передаётся через `docker save/load`. TRX и coverage сохраняются, в том числе при неуспешных тестах, если файлы сформированы; summary публикации содержит полное имя образа с тегом для деплоя.

Интеграционные тесты используют стандартный одноразовый GitHub-hosted Linux VM runner, бесплатный для публичного репозитория; платные larger runners и постоянный judge-host не используются. Выбран `ubuntu-24.04`; совместимость privileged Docker/cgroups v2/isolate ещё проверяется пробным запуском. Бесплатность вычислений не отменяет квоту artifact storage: временный Docker-архив и отчёты должны укладываться в бесплатное хранение, параметры retention/удаления ещё выбираются. Условия и источники приведены в [описании CI](docs/REPOSITORY.md#github-actions).

GitHub Actions будет собирать и тестировать приложение, упаковывать его в Docker и публиковать образ в GHCR после успешных проверок. Имя образа: `ghcr.io/texnokaktus-progolymp/runner-agent-cpp-23`. Тег версии имеет формат `YYYY.M.D.<run_number>`. Этапы описаны в [проекте pipeline](docs/REPOSITORY.md#github-actions).

Планируемый порядок ручного деплоя MVP:

1. Выбрать проверенный образ в GHCR по тегу версии, подготовить Linux judge-host и при необходимости доступ на чтение registry.
2. Подготовить конфигурацию gRPC/S3, credentials только для агента и локальную рабочую область.
3. Запустить образ с долгоживущим агентом как privileged Docker-контейнер с согласованными mounts/cgroup-настройками и ограничениями host/container.
4. Проверить доступность агента, отправить контрольное C++-задание с набором тестов и получить его результат отдельным запросом.

Endpoint агента по умолчанию — `0.0.0.0:8080` внутри контейнера. Имена переменных конфигурации, публикация порта на host и команда запуска будут зафиксированы после спецификации окружения. Автоматический деплой не планируется; pipeline завершается публикацией в GHCR и фиксацией выпуска Git-тегом. Целевая более безопасная схема — dedicated Judge VM/host с native isolate.

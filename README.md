# RunnerAgent

Агент проверяющей системы для компиляции и исполнения олимпиадных решений в isolate. Первый MVP рассчитан на C++23: одно задание содержит один исходник и N тестов, исходник компилируется один раз на набор. Агент отдельно ограничивает компиляцию и запуски, собирает результаты по тестам и очищает песочницы после обработки набора.

**Состояние проекта:** проектирование. Сейчас в репозитории находятся документация и инструкции для разработки. Описанные ниже solution, проекты, Dockerfile и workflow запланированы; приложение и опубликованный образ пока отсутствуют.

## API и обмен файлами

```text
Мастер -- StartJob: исходник + N тестов --> RunnerAgent
Мастер <-- подтверждение начала работы ---+
                                          +-- S3: скачать входные файлы
                                          +-- isolate: одна компиляция
                                          +-- isolate: запуск тестов
                                          +-- S3: загрузить артефакты
                                          +-- очистить песочницы
                                          +-- сохранить результат; занят
Мастер -- GetResult ---------------------->+
Мастер <-- результат набора + S3 refs -----+ ресурс свободен
```

Модель API асинхронная: агент сразу подтверждает принятие задания, мастер забирает итоговый результат через `GetResult`. Предварительное имя RPC запуска — `StartJob`; полный контракт ещё не утверждён.

Для MVP gRPC работает по HTTP/2 без HTTPS/TLS и без аутентификации в доверенной внутренней сети. Команда и все флаги компиляции C++23 задаются агентом; мастер передаёт resource limits, но не дополнительные флаги компилятора.

- Запрос: заданные мастером `job_id` и `test_id` каждого теста типа `int64`, язык/версия, ссылки на один исходник и входные данные тестов в S3 по ключам и SHA-256, префикс выходных объектов, отдельные лимиты компиляции и общий профиль execution limits, применяемый независимо к каждому тесту.
- Итоговый результат: исходный `job_id`, общий результат компиляции, результаты отдельных тестов с исходными `test_id`, метрики ресурсов, exit code/signal и ссылки на stdout, stderr, compiler log.
- При ошибке компиляции возвращаются `CompilationError` и compiler log; список результатов тестов пуст, тесты не запускаются.
- Тесты выполняются последовательно в порядке запроса. После ошибки решения, превышения лимита или инфраструктурной ошибки отдельного теста агент продолжает набор. Инфраструктурная ошибка получает отдельный статус теста.
- Для stdout и stderr задаются отдельные лимиты. Превышение любого из них останавливает процесс с `OutputLimitExceeded`; полученная часть каждого потока сохраняется в пределах его лимита.
- Проверку корректности ответов и вынесение AC/WA выполняет мастер; агент возвращает статусы исполнения и выходные артефакты.
- Файлы хранятся в MinIO, агент обращается к нему через `AWSSDK.S3` с endpoint из конфигурации. gRPC используется для управления. Sandbox не получает сеть или credentials агента.
- Версии объектов S3 не используются в текущем контракте; содержимое входных файлов проверяется по SHA-256.
- Временные ошибки MinIO обрабатываются resilience policy: до трёх попыток скачивания/загрузки всего с задержкой. Отсутствие объекта и несовпадение SHA-256 не повторяются.
- В конфигурации агента задаются два bucket: отдельный для исходников и общий для входных данных тестов и результатов. Префикс выходных объектов задаёт мастер; ключи compiler log и stdout/stderr тестов внутри него формирует агент.
- Задание продолжает выполняться после завершения исходного RPC. Агент занят до выдачи готового результата через `GetResult`, даже если вычисления и очистка уже завершены. `GetResult` освобождает ресурс и сразу удаляет сохранённый результат из состояния агента; артефакты в S3 остаются. Отдельного подтверждения нет.
- Пока ресурс занят, запрос с другим `job_id` получает ошибку «ресурс занят», а повтор с текущим `job_id` — ответ «задание уже принято», без повторного исполнения.
- Пока задание выполняется, `GetResult` сразу отвечает «не завершено», без ожидания и освобождения ресурса.
- В обычном режиме долгоживущий агент ожидает получения готового результата без таймаута и остаётся занят до `GetResult`.
- Операция отмены задания в текущем API не предусмотрена.
- В MVP состояние задания и непрочитанный результат хранятся в памяти и теряются при перезапуске агента; повторный запуск организует мастер.

При штатной остановке агент перестаёт принимать новые задания, завершает текущий набор, публикует артефакты и очищает песочницы. Затем ожидает `GetResult` в течение настраиваемого таймаута, по умолчанию 30 секунд; время выполнения задания в него не входит. Если результат уже готов, отсчёт начинается при запросе остановки. После обслуживания `GetResult` агент завершает работу; если мастер не забрал результат до истечения таймаута — выходит с потерей результата в памяти, сохраняя S3-артефакты.

Рассматривается также альтернативная ветка: контейнер на один набор тестов с ожиданием получения результата в пределах того же таймаута перед завершением агента и удалением контейнера; управление контейнерами ещё проектируется. Подробности: [архитектура](ARCHITECTURE.md).

Полное дерево, область действия настроек и проект pipeline описаны в [структуре репозитория](docs/REPOSITORY.md).

## Сборка и тестирование

После создания проектов SDK и тестовая платформа Microsoft.Testing.Platform будут выбираться через `global.json`. Тесты пишутся на NUnit. Планируемая последовательность из корня репозитория:

```sh
dotnet tool restore
dotnet restore Texnokaktus.ProgOlymp.RunnerAgent.slnx
dotnet build Texnokaktus.ProgOlymp.RunnerAgent.slnx -c Release --no-restore
dotnet test --project tests/Texnokaktus.ProgOlymp.RunnerAgent.Tests/Texnokaktus.ProgOlymp.RunnerAgent.Tests.csproj -c Release --no-build -- --coverage --coverage-output-format cobertura --report-trx
docker build -f src/Texnokaktus.ProgOlymp.RunnerAgent/Dockerfile -t runner-agent:local .
```

Эти команды описывают будущий порядок; в текущем репозитории запускать их ещё рано. Unit-тесты не требуют isolate. Integration-тесты будут проверять собранный образ в Linux-среде с Docker, privileged containers и подходящей конфигурацией cgroups. Способ передачи образа и настройки тестового окружения будут добавлены вместе с тестовыми fixtures.

## Публикация и деплой

GitHub Actions будет собирать и тестировать приложение, упаковывать его в Docker и публиковать образ в GHCR после успешных проверок. Предлагаемое имя: `ghcr.io/texnokaktus-progolym/runner-agent`. Тег версии имеет формат `YYYY.M.D.<run_number>`. Этапы описаны в [проекте pipeline](docs/REPOSITORY.md#github-actions).

Планируемый порядок ручного деплоя MVP:

1. Выбрать проверенный образ в GHCR по тегу версии, подготовить Linux judge-host и при необходимости доступ на чтение registry.
2. Подготовить конфигурацию gRPC/S3, credentials только для агента и локальную рабочую область.
3. Для долгоживущей ветки запустить образ как privileged Docker-контейнер с согласованными mounts/cgroup-настройками и ограничениями host/container. Для альтернативы с контейнером на одно задание порядок запуска и удаления ещё проектируется.
4. Проверить доступность агента, отправить контрольное C++-задание с набором тестов и получить его результат отдельным запросом.

Точные порты, переменные конфигурации и команда запуска будут зафиксированы после спецификации окружения. Автоматический деплой не планируется; pipeline заканчивается публикацией в GHCR. Целевая более безопасная схема — dedicated Judge VM/host с native isolate.

# Лимиты и измерения

## Purpose

Спецификация определяет согласованное поведение RunnerAgent в области «Лимиты и измерения» для первого C++23 MVP и его проверку.

## ADDED Requirements

### Requirement: REQ-22 — Лимиты, измерения и приоритет причин

RunnerAgent SHALL независимо применять лимиты стадий, учитывать ресурсы всей cgroup и подтверждать причины завершения.

#### Scenario: REQ-22 — согласованный контракт

- **WHEN** мастер задаёт лимиты и sandbox расходует ресурсы
- **THEN** соблюдаются следующие условия (предложения и технические детали сохраняют явно указанный статус):

Агент должен различать следующие ограничения; имена полей предварительные:

| Лимит | Поле | Единица и смысл |
| --- | --- | --- |
| CPU time | `cpu_time_ms` | Суммарные миллисекунды процессорного времени всех процессов и потоков песочницы |
| Wall time | `wall_time_ms` | Миллисекунды реального времени |
| Memory | `memory_bytes` | Память всей cgroup песочницы в байтах, включая учитываемый ядром файловый кеш |
| Stdout | `stdout_bytes` | Отдельный максимальный размер stdout в байтах |
| Stderr | `stderr_bytes` | Отдельный максимальный размер stderr в байтах |
| Processes | `processes` | Общее допустимое число процессов и потоков песочницы, включая основной |

Compilation и execution имеют самостоятельные наборы лимитов. Мастер должен явно передавать оба профиля и все значения в каждом из них. Все значения положительные; отсутствие профиля или обязательного значения, ноль и отрицательные значения дают `INVALID_ARGUMENT`. Значений по умолчанию и обозначения «без ограничений» нет. Поля времени в миллисекундах и размеров в байтах имеют тип `int64`, поле `processes` — `int32`. Значение, которое невозможно корректно применить в выбранной реализации песочницы, должно отклоняться через `INVALID_ARGUMENT` до принятия задания.

Stdout и stderr компилятора разделены: каждый поток имеет собственный лимит `stdout_bytes` / `stderr_bytes`, отдельный локальный файл и отдельный S3-артефакт (`compilation/stdout.txt` / `compilation/stderr.txt`). Объединённый журнал и отдельный `log_bytes` не используются. Согласованные правила публикации вывода компилятора применяются к каждому потоку отдельно: сбой публикации одного не скрывает успешно опубликованный другой. При превышении любого из двух лимитов агент останавливает компиляцию, сохраняет оба частичных потока в пределах их собственных лимитов и не запускает тесты. Общий статус задания — `CompilationError`, причина завершения — `OutputLimitExceeded`, если нет другого подтверждённого нарушения с более высоким приоритетом.

CPU и память учитываются суммарно для всей песочницы, включая дочерние процессы и потоки, с использованием cgroups. `processes` включает основной процесс и все дочерние процессы/потоки. Память ограничивается для всей cgroup; результат возвращает её пиковое потребление в байтах, включая учитываемый ядром файловый кеш. Метрика лимита и результата едина. CPU time не заменяет wall time: ожидание и блокировка могут расходовать реальное время без значительного CPU time.

Запрошенный `memory_bytes` округляется вверх до ближайшего значения, кратного размеру страницы памяти хоста. В результате соответствующей стадии возвращается фактически применённый лимит памяти; исходное значение запроса не изменяется и используется при сравнении повторов `StartJob`. Округление выполняется с проверкой переполнения; невозможность корректно применить значение даёт `INVALID_ARGUMENT`. Пиковое потребление читается из `memory.peak` cgroup этой стадии до её удаления. Гранулярность памяти и семантика пика описаны в [документации cgroups v2](https://docs.kernel.org/admin-guide/cgroup-v2.html#memory).

Лимит числа процессов/потоков применяется через `pids.max`, а его нарушение подтверждается событием `pids.events`, относящимся к текущему запуску песочницы. Заблокированная попытка создать лишний процесс или поток фиксирует `ProcessLimitExceeded`, даже если программа обработала отказ и вернула код 0. При обнаружении нарушения агент останавливает оставшиеся процессы песочницы; основная причина выбирается с учётом общего приоритета подтверждённых нарушений. Интерфейс описан в [документации PID-контроллера](https://docs.kernel.org/admin-guide/cgroup-v2.html#pid).

Execution limits применяются отдельно к каждому тесту, не к сумме потребления набора. Отдельный общий предел длительности задания не вводится (Q-06 закрыт). Сохраняются лимиты компиляции и каждого теста; deadline RPC и таймаут ожидания результата при остановке не ограничивают длительность задания. Конкретные границы применимости значений и преобразование единиц для выбранной версии isolate ещё уточняются в Q-05.

При нескольких подтверждённых нарушениях основная причина завершения выбирается в порядке: `MemoryLimitExceeded` → `OutputLimitExceeded` → `CpuTimeLimitExceeded` → `WallTimeLimitExceeded` → `ProcessLimitExceeded` → `RuntimeError`. Остальные обнаруженные причины сохраняются в диагностике. Превышение лимита должно подтверждаться данными о нарушении; один сигнал завершения сам по себе не является достаточным основанием для такого verdict. Инфраструктурные ошибки отражаются отдельно согласно [разделу 8.4](../job-results/spec.md), не стирая известную причину завершения процесса.
#### Scenario: AT-12 — CPU и wall time

- **WHEN** программа нагружает CPU либо ожидает без нагрузки
- **THEN** CPU-нагрузка и ожидание проверяют независимые ограничения согласно утверждённому mapping

Связанные требования: REQ-22.

#### Scenario: AT-52 — Обязательные лимиты

- **WHEN** профиль лимитов или обязательное положительное значение отсутствует
- **THEN** Отсутствие compilation/execution профиля или его обязательного значения, ноль и отрицательное значение дают `INVALID_ARGUMENT` до принятия; defaults и обозначения неограниченности не подставляются

Связанные требования: REQ-07, REQ-22.

#### Scenario: AT-53 — Совокупные ресурсы

- **WHEN** песочница создаёт дочерние процессы и потоки и потребляет CPU/память
- **THEN** CPU и память учитываются для всей cgroup с дочерними процессами/потоками; `processes` включает основной процесс; память ограничивается и измеряется одной метрикой с учитываемым ядром файловым кешем, пик возвращается в байтах

Связанные требования: REQ-22.

#### Scenario: AT-54 — Потоки компилятора

- **WHEN** компилятор пишет в оба потока и один артефакт не публикуется
- **THEN** Stdout/stderr сохраняются отдельно с собственными лимитами и ключами `compilation/stdout.txt` / `compilation/stderr.txt`; сбой публикации одного сохраняет ссылку на успешно опубликованный другой; объединённого журнала нет

Связанные требования: REQ-15, REQ-21, REQ-22, REQ-25.

#### Scenario: AT-56 — Приоритет причин завершения

- **WHEN** зафиксированы несколько нарушений либо только сигнал завершения
- **THEN** При нескольких подтверждённых причинах выбирается память → вывод → CPU → wall time → процессы → runtime error; остальные причины сохраняются в диагностике; один сигнал без подтверждения нарушения не превращается в превышение лимита

Связанные требования: [Раздел 7](../resource-limits/spec.md), REQ-24.

#### Scenario: AT-57 — Числовые типы и применимость

- **WHEN** переданы граничные или неприменимые числовые значения лимитов
- **THEN** Время/размеры передаются как `int64`, `processes` — как `int32`; неприменимые значения отклоняются через `INVALID_ARGUMENT` до принятия без переполнения или молчаливой подмены лимита

Связанные требования: REQ-07, REQ-22.

#### Scenario: AT-59 — Память и OOM

- **WHEN** лимит памяти не кратен странице либо возникает OOM
- **THEN** Лимит округляется вверх до страницы без переполнения и возвращается в результате стадии; пик читается из её `memory.peak`; swap отключён, при OOM не остаются работающие дочерние процессы песочницы

Связанные требования: [Разделы 6](../sandbox-execution/spec.md)–8, REQ-22, REQ-24.

#### Scenario: AT-60 — Подтверждённый лимит процессов

- **WHEN** pids.max блокирует создание процесса, а программа обрабатывает отказ
- **THEN** `pids.max` ограничивает процессы/потоки, событие `pids.events` подтверждает отказ созданию; даже при обработанном отказе и exit code 0 фиксируется `ProcessLimitExceeded`, оставшиеся процессы останавливаются, приоритет нарушений сохраняется

Связанные требования: REQ-22.


### Requirement: REQ-23 — Независимые лимиты вывода

RunnerAgent SHALL ограничивать stdout и stderr независимо, сохранять допустимый частичный вывод и продолжать остальные тесты.

#### Scenario: REQ-23 — согласованный контракт

- **WHEN** компилятор или решение пишет в stdout либо stderr
- **THEN** соблюдаются следующие условия (предложения и технические детали сохраняют явно указанный статус):

При превышении отдельного лимита stdout или stderr агент должен остановить процесс с `OutputLimitExceeded`, если нет другого подтверждённого нарушения с более высоким приоритетом. Уже полученная часть каждого потока сохраняется и публикуется в пределах собственного лимита. Сумма размеров потоков не заменяет проверку каждого из них. Для execution после этого обработка остальных тестов продолжается; для compilation действуют описанные выше `CompilationError` и отсутствие запусков тестов.

CPU учитывается по всей cgroup стадии, wall time измеряется монотонными часами за время исполнения процесса. Причины превышений подтверждаются измерениями и событиями соответствующей песочницы; сигнал сам по себе доказательством не считается. Преобразования единиц проверяются на переполнение; неприменимые значения отклоняются до принятия задания. Точные технические границы и mapping для выбранной версии isolate фиксируются и проверяются тестами при реализации, с сохранением согласованного приоритета причин и правил инфраструктурных ошибок.

#### Scenario: AT-13 — Вывод

- **WHEN** отдельный поток stdout или stderr превышает свой лимит
- **THEN** Превышение отдельно stdout и отдельно stderr останавливает процесс с `OutputLimitExceeded`; оба частичных потока не превышают собственные лимиты, набор продолжается

Связанные требования: REQ-23.

#### Scenario: AT-14 — Сумма потоков

- **WHEN** сумма потоков превышает один лимит, но каждый поток укладывается в собственный
- **THEN** Если каждый поток укладывается в свой лимит, превышение их суммой одного из отдельных лимитов не даёт `OutputLimitExceeded`

Связанные требования: REQ-23.

#### Scenario: AT-55 — Лимит вывода компилятора

- **WHEN** stdout или stderr компилятора превысил собственный лимит
- **THEN** Превышение отдельно stdout или stderr останавливает компиляцию, сохраняет оба частичных потока в их лимитах, даёт общий `CompilationError` с причиной `OutputLimitExceeded` при отсутствии более приоритетного нарушения; тесты не запускаются

Связанные требования: REQ-22, REQ-23, REQ-25.

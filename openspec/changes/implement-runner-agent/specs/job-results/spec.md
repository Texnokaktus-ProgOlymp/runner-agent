# Результат и обработка ошибок

## Purpose

Спецификация определяет согласованное поведение RunnerAgent в области «Результат и обработка ошибок» для первого C++23 MVP и его проверку.

## ADDED Requirements

### Requirement: REQ-24 — Структурированный результат

RunnerAgent SHALL возвращать структурированные результаты с исходными ID, доступными метриками, артефактами и отдельной инфраструктурной диагностикой.

#### Scenario: REQ-24 — согласованный контракт

- **WHEN** агент формирует результат задания
- **THEN** соблюдаются следующие условия (предложения и технические детали сохраняют явно указанный статус):

###### 8.1. Состав результата

Структурированный результат должен содержать:

| Уровень | Данные |
| --- | --- |
| Задание | Исходный `job_id`, итоговый статус, стадия возникновения ошибки, результат единственной компиляции, коллекция результатов тестов, отдельная инфраструктурная диагностика задания |
| Компиляция | Статус/причина прекращения, CPU time, wall time, peak memory всей cgroup, exit code и signal при наличии, отдельные ссылки на опубликованные stdout/stderr компилятора, доступная инфраструктурная диагностика |
| Тест | Исходный `test_id`, итоговый статус теста, отдельно результат исполнения (verdict/причина прекращения, CPU time, wall time, peak memory, exit code и signal при наличии), ссылки на опубликованные stdout/stderr, отдельная инфраструктурная диагностика |
| Артефакт | Фактическая ссылка на опубликованный объект и вычисленный SHA-256 |

Отсутствующие exit code/signal должны представляться явно отсутствующими, а не фиктивным нулём. Для инфраструктурных ошибок сохраняются известные метрики и доступные артефакты; отсутствующие данные не подменяются успешным результатом. Если компиляция не начиналась, её результат должен быть явно отсутствующим. Если данные компиляции появились до инфраструктурного сбоя, они сохраняются в доступном объёме.

Результаты компиляции и исполнения содержат фактически применённый лимит памяти с учётом округления, когда он был установлен. Если после запуска не удалось получить обязательные данные, необходимые для корректного результата, фиксируется инфраструктурная ошибка соответствующей стадии или теста. Доступные сведения сохраняются, недостающие не заменяются нулями или успехом. Допустимое отсутствие необязательных полей, например signal при нормальном выходе, само по себе не является ошибкой метрик.

Для процесса компиляции и процесса решения согласован набор причин завершения: `Success`, `RuntimeError`, `CpuTimeLimitExceeded`, `WallTimeLimitExceeded`, `MemoryLimitExceeded`, `OutputLimitExceeded`, `ProcessLimitExceeded`. Основная причина выбирается по правилам раздела 7. Неуспешный исход процесса компиляции даёт общий `CompilationError` с конкретной причиной; инфраструктурные сбои обрабатываются отдельно и не подменяются ошибкой компиляции кода. Согласованы общий статус задания `InfrastructureError` для сбоев подготовки исходника или компиляции из-за инфраструктуры и итоговый статус теста `InfrastructureError` при инфраструктурном сбое этого теста. Mapping конкретных данных isolate/cgroups на эти причины ещё требуется определить; состав причин не означает, что mapping уже реализован или проверен.

###### 8.2. Общий статус после обработки набора

Если компиляция успешна и каждый переданный тест получил результат, общий статус задания должен быть `Completed`. Статусы отдельных тестов сохраняются независимо: успешное исполнение, ошибка исполнения, превышение лимита или инфраструктурная ошибка теста не меняют этот общий статус. `Completed` означает, что агент закончил обработку набора, а не что решение прошло проверку. AC/WA по-прежнему определяет мастер.

Например, если один тест выполнен, второй превысил время, а для третьего не удалось скачать вход, задание получает `Completed` и три соответствующих результата тестов. Результат инфраструктурной ошибки теста учитывается как результат обработки, даже если процесс решения для этого теста не запускался.

Общий статус задания следует отличать от одноимённого состояния ответа `GetResult`: RPC возвращает `Completed` при любом готовом результате, в том числе с общим статусом `CompilationError` или `InfrastructureError`. Общий статус задания `Completed` относится к успешной компиляции и обработанному набору, как описано выше.

###### 8.3. Поведение при ошибках
#### Scenario: AT-20 — Данные результата

- **WHEN** возвращаются результаты с граничными ID и отсутствующими необязательными данными
- **THEN** Положительный `job_id` типа `int64` и положительный `test_id` типа `int32` из допустимых диапазонов сохраняются без изменения; неизвестные exit code/signal не превращаются в ноль; успешное исполнение не объявляется AC

Связанные требования: REQ-03, REQ-07, REQ-24.

#### Scenario: AT-61 — Отсутствие обязательных метрик

- **WHEN** после запуска недоступны обязательные данные результата
- **THEN** Потеря обязательных данных после запуска даёт инфраструктурную ошибку с сохранением доступных сведений, без фиктивных нулей/успеха; допустимое отсутствие необязательного поля не вызывает этой ошибки

Связанные требования: REQ-24.


### Requirement: REQ-25 — Статусы и обработка ошибок

RunnerAgent SHALL различать ошибки кода и инфраструктуры, сохранять известные результаты и продолжать набор после ошибки отдельного теста.

#### Scenario: REQ-25 — согласованный контракт

- **WHEN** возникают ошибки подготовки, компиляции, исполнения или публикации
- **THEN** соблюдаются следующие условия (предложения и технические детали сохраняют явно указанный статус):

Ошибки должны обрабатываться согласно следующей таблице:

| Событие | Требуемое поведение |
| --- | --- |
| Компиляция успешна, каждый переданный тест получил результат | Общий статус `Completed` независимо от статусов отдельных тестов; сохранить все их результаты |
| Ошибка компиляции | Итоговый статус `CompilationError`, данные компиляции и вывод компилятора; тесты не запускаются, коллекция результатов тестов пуста |
| Ошибка публикации вывода компилятора | Сохранить данные компиляции, записать инфраструктурную ошибку на уровне задания и не возвращать ссылку на неопубликованный поток. При успешной компиляции продолжить тесты и после обработки набора вернуть общий `Completed`; при ошибке компиляции сохранить общий `CompilationError` и пустой список тестов |
| Runtime error или превышение лимита теста | Сохранить verdict, метрики и доступные артефакты; продолжить остальные тесты |
| Сбой скачивания входа, запуска isolate или публикации артефактов отдельного теста | Итоговый статус теста `InfrastructureError`; отдельно сохранить известный результат исполнения и инфраструктурную диагностику; продолжить набор |
| Общая ошибка подготовки исходного кода или невозможность компиляции из-за инфраструктуры | Итоговый статус `InfrastructureError`, стадия и причина сбоя; тесты не запускаются, коллекция результатов тестов пуста; доступные данные компиляции сохраняются, а если она не начиналась — результат компиляции явно отсутствует |
| Перезапуск или падение процесса до выдачи результата | Потеря состояния допустима для MVP; опубликованные S3-артефакты сохраняются |

К общим инфраструктурным ошибкам до тестов относятся, например, сбой скачивания исходного файла, несовпадение его SHA-256 или невозможность запустить isolate для компиляции. Фиктивные результаты невыполненных тестов не создаются. Обычная ошибка компиляции исходного кода по-прежнему даёт `CompilationError`; сбой инфраструктуры не должен подменяться этой категорией.

Ошибка публикации вывода компилятора не меняет известный исход компиляции и сама по себе не блокирует исполнение тестов после успешной компиляции. Она сохраняется как инфраструктурная диагностика задания, независимо от общего `Completed` или `CompilationError`; данные компиляции не теряются, отсутствующая ссылка не подменяется ожидаемым ключом объекта.

Сбой storage не должен маскироваться под ошибку программы участника. Общий статус при смешанных результатах тестов определён в [разделе 8.2](../job-results/spec.md), совместное представление ошибки исполнения и инфраструктуры отдельного теста — в разделе 8.4. Приоритет подтверждённых причин определён в [разделе 7](../resource-limits/spec.md); mapping конкретных данных isolate/cgroups ещё уточняется; поведение при ошибках очистки описано в [разделе 4.4](../agent-lifecycle/spec.md); продолжение частичной публикации и хранение объектов описаны в разделе 5.

Финальный результат, включая ошибку компиляции или инфраструктуры, выдаётся через `GetResult` и освобождает ресурс по общим правилам, если процесс агента сохранился до выдачи.

###### 8.4. Результат исполнения и инфраструктурная ошибка теста

При инфраструктурной ошибке теста его итоговый статус должен быть `InfrastructureError`, даже если процесс решения уже завершился с известным verdict. Результат исполнения сохраняется отдельно и не заменяется инфраструктурной ошибкой: например, ошибка исполнения и последующий сбой публикации stdout дают итоговый `InfrastructureError`, отдельный результат исполнения с `RuntimeError`, известными метриками, exit code и signal и диагностику сбоя публикации stdout.

Если процесс решения вообще не запускался, результат исполнения должен быть явно отсутствующим. Если запуск состоялся, сохраняются известные данные, а неизвестные значения не подменяются успешным результатом. Ссылки возвращаются только на успешно опубликованные артефакты; ошибка одного артефакта не скрывает ссылки на другие успешно опубликованные артефакты.

После инфраструктурной ошибки теста обработка остальных тестов продолжается. Если компиляция успешна и каждый тест получил результат, общий статус задания остаётся `Completed` согласно разделу 8.2. Окончательное protobuf-представление раздельных полей определяется в Q-02.

#### Scenario: AT-08 — Ошибка компиляции

- **WHEN** компилятор завершился с ошибкой кода
- **THEN** `CompilationError`, данные компиляции и опубликованный вывод компилятора, пустая коллекция тестов, ни одного исполнения

Связанные требования: REQ-25.

#### Scenario: AT-09 — Ошибки решения на тестах

- **WHEN** решение завершилось ошибкой или превысило лимит теста
- **THEN** Runtime error или превышение лимита не препятствуют обработке следующих тестов; возвращаются результаты набора

Связанные требования: REQ-02, REQ-25.

#### Scenario: AT-10 — Инфраструктурный сбой отдельного теста

- **WHEN** для отдельного теста отказывает загрузка, isolate или публикация
- **THEN** Сбой загрузки входа, isolate или публикации даёт отдельную инфраструктурную ошибку; последующие тесты обрабатываются

Связанные требования: REQ-17, REQ-25.

#### Scenario: AT-21 — Ошибка публикации

- **WHEN** публикация артефакта не удалась
- **THEN** Недоступный артефакт не заявляется опубликованным; сбой не маскируется под ошибку решения, в том числе для вывода компилятора

Связанные требования: REQ-25.

#### Scenario: AT-42 — Инфраструктурный сбой до тестов

- **WHEN** до тестов не удалось скачать/проверить исходник или запустить компиляцию
- **THEN** Сбой скачивания исходника, несовпадение его SHA-256 или невозможность запуска isolate для компиляции дают общий `InfrastructureError` со стадией и причиной, пустой список тестов и отсутствие их запусков; данные компиляции сохраняются, если появились, иначе при неначатой компиляции её результат явно отсутствует

Связанные требования: REQ-24, REQ-25.

#### Scenario: AT-43 — Общий статус обработанного набора

- **WHEN** после успешной компиляции каждый тест получил результат с различными исходами
- **THEN** После успешной компиляции и получения результата для каждого теста общий статус — `Completed`, в том числе для смеси успешного исполнения, ошибок решения, превышений лимита и инфраструктурных ошибок отдельных тестов; все результаты сохраняются

Связанные требования: [Раздел 8.2](../job-results/spec.md), REQ-24, REQ-25.

#### Scenario: AT-44 — Совместные ошибки теста

- **WHEN** ошибка исполнения сопровождается сбоем публикации stdout
- **THEN** Ошибка исполнения и последующий сбой публикации stdout дают итоговый `InfrastructureError` теста, отдельный исходный результат исполнения с известными метриками/exit code/signal и диагностику публикации; ссылки есть только на успешно опубликованные артефакты; следующие тесты обрабатываются

Связанные требования: [Раздел 8.4](../job-results/spec.md), REQ-24, REQ-25.

#### Scenario: AT-45 — Отсутствующее исполнение

- **WHEN** процесс решения не запущен из-за инфраструктуры
- **THEN** Если вход не скачан или процесс решения не запущен из-за инфраструктуры, итоговый статус теста — `InfrastructureError`, результат исполнения явно отсутствует; обработка остальных тестов продолжается

Связанные требования: [Раздел 8.4](../job-results/spec.md), REQ-24, REQ-25.

#### Scenario: AT-46 — Сбой публикации вывода компилятора

- **WHEN** публикация потока компилятора не удалась после успешной или неуспешной компиляции
- **THEN** При успешной компиляции тесты продолжаются, обработанный набор получает общий `Completed`; при ошибке компиляции сохраняются `CompilationError` и пустой список тестов. В обоих случаях данные компиляции сохранены, инфраструктурная ошибка публикации находится на уровне задания, ссылки на неопубликованный поток нет

Связанные требования: [Раздел 8.3](../job-results/spec.md), REQ-24, REQ-25.

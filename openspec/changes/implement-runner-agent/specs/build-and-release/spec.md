# Репозиторий и поставка

## Purpose

Спецификация определяет согласованное поведение RunnerAgent в области «Репозиторий и поставка» для первого C++23 MVP и его проверку.

## ADDED Requirements

### Requirement: REQ-29 — Структура .NET-репозитория

RunnerAgent SHALL использовать .slnx, src/tests, наследуемые MSBuild-настройки и централизованные версии пакетов.

#### Scenario: REQ-29 — согласованный контракт

- **WHEN** создаётся solution и проекты
- **THEN** соблюдаются следующие условия (предложения и технические детали сохраняют явно указанный статус):

Согласованы solution `.slnx`, production-код в `src/`, тесты в `tests/`, workflows в `.github/workflows/`, корневой `Directory.Build.props` и CPM в `Directory.Packages.props`. Вложенные `Directory.Build.props` должны явно импортировать родительские настройки. Общие тестовые зависимости относятся к `tests/`, а `InternalsVisibleTo` для соответствующего `.Tests` и `DynamicProxyGenAssembly2` задаётся в `src/Directory.Build.props`.

### Requirement: REQ-30 — Тестовая платформа

RunnerAgent SHALL использовать NUnit на Microsoft.Testing.Platform в нативном MTP-режиме .NET 10.

#### Scenario: REQ-30 — согласованный контракт

- **WHEN** запускаются локальные и интеграционные тесты
- **THEN** соблюдаются следующие условия (предложения и технические детали сохраняют явно указанный статус):

Тесты должны использовать NUnit на Microsoft.Testing.Platform с нативным MTP-режимом `dotnet test` в .NET 10. Версия SDK и `test.runner=Microsoft.Testing.Platform` задаются через `global.json`; настройки NUnit runner и MTP-расширения coverage/TRX — через `tests/Directory.Build.props`. Общие зависимости включают NUnit и NSubstitute. Версии пакетов и SDK patch ещё не выбраны.

### Requirement: REQ-31 — CI и публикация

RunnerAgent SHALL собирать, проверять и публиковать тот же Linux-образ в GHCR с согласованными версиями и Git-тегами без автоматического деплоя.

#### Scenario: REQ-31 — согласованный контракт

- **WHEN** в master поступает push и выполняется выпуск
- **THEN** соблюдаются следующие условия (предложения и технические детали сохраняют явно указанный статус):

GitHub Actions должен собирать и тестировать приложение, упаковывать Docker image и публиковать его в GHCR. Формат версии — `YYYY.M.D.<run_number>` с датой исходного коммита в Europe/Moscow; повтор workflow сохраняет версию. Образ выбирается для ручного деплоя по тегу версии. Pipeline заканчивается публикацией; автоматический деплой не планируется.

Основной репозиторий кода, CI и выпусков — GitHub. Gitea используется как независимое зеркало, настраиваемое пользователем на своей стороне. GitHub/Actions не содержат интеграции с зеркалом: ни workflow, ни secrets, ни проверок его состояния; доступность зеркала не влияет на проверки или выпуск. Перенос репозитория, смена origin и пересоздание Gitea выполняются пользователем вне реализации приложения.

Для MVP согласован один production-проект с каталогами `Grpc`, `Storage`, `Execution`, `Languages`, `Workspace`, без выделения отдельных библиотек. Два тестовых проекта: `.Tests` для локальной логики без внешних сервисов и `.IntegrationTests` для gRPC, MinIO и isolate; оба используют NUnit на Microsoft.Testing.Platform.

Общие настройки проектов: `TargetFramework=net10.0`, `LangVersion=14.0`, `Nullable=enable`, `ImplicitUsings=enable`. Версии NuGet-зависимостей централизованно фиксируются в `Directory.Packages.props`, без плавающих версий; конкретные версии выбираются и проверяются при создании каркаса. Платформа MVP — `linux/amd64`; поддержку `arm64` добавляют отдельно после проверки isolate и toolchain. Эти решения описывают план реализации, проекты и образ ещё не созданы.

CI запускается на push в `master` публичного GitHub-репозитория; pull request и отдельные PR-проверки не предусматриваются. Pipeline выполняет сборку, unit-тесты, сборку Docker-образа и интеграционные тесты; только после успешных обязательных проверок публикует тот же образ в GHCR без пересборки. Между jobs образ передаётся через `docker save/load`. TRX и coverage сохраняются, в том числе при неуспешных тестах, если файлы сформированы; summary публикации содержит полное имя образа с тегом для деплоя.

Интеграционные тесты используют стандартный одноразовый GitHub-hosted Linux VM runner, бесплатный для публичного репозитория; платные larger runners и постоянный judge-host не используются. Выбран `ubuntu-24.04`; совместимость privileged Docker/cgroups v2/isolate ещё проверяется пробным запуском. Бесплатность вычислений не отменяет квоту artifact storage: временный Docker-архив и отчёты должны укладываться в бесплатное хранение, параметры retention/удаления ещё выбираются. Условия и источники приведены в [описании CI](../../repository.md#github-actions).

Согласованный runner — стандартный `ubuntu-24.04` (Linux VM); перед интеграционными тестами проверяются необходимые возможности privileged Docker/cgroups v2/isolate. Имя образа — `ghcr.io/texnokaktus-progolymp/runner-agent-cpp-23`. Для истории выпусков после успешной публикации образа создаётся Git-тег `vYYYY.M.D.<run_number>` на коммите, из которого собран образ. Тег Docker-образа сохраняет формат `YYYY.M.D.<run_number>` без `v`. При повторном запуске существующий Git-тег на том же коммите считается нормальным; тег на другом коммите вызывает ошибку без перезаписи. Сбой создания Git-тега делает этап выпуска неуспешным, опубликованный образ сохраняется. Устаревшие проверки от push можно отменять до публикации, но уже начатая публикация новым push не прерывается.

Следующие детали остаются **предложениями** из [плана репозитория](../../repository.md), а не утверждёнными ограничениями продукта:

- Deterministic build и настройки анализаторов; ReportGenerator как local tool; конкретные наборы настроек и версии проверяются при создании каркаса.
- Multi-stage Dockerfile рядом с production `.csproj`, build context в корне, `.dockerignore` для локальных и секретных файлов.
- OCI revision и версия в metadata образа.
- Техническая организация отдельного AOT job; его информационный статус и условия перехода согласованы в разделе 9.

Подробное дерево, MSBuild/CPM-настройки и план pipeline сохраняются в [плане репозитория](../../repository.md). Создание Git-тегов для истории выпусков RunnerAgent, префикс `v`, порядок после публикации и правила повторов согласованы выше.

#### Scenario: AT-27 — Сборка и поставка

- **WHEN** выполняются сборка, тестирование и поставка
- **THEN** Общие настройки/CPM наследуются, тесты используют NUnit/MTP, pipeline выдаёт проверенный Docker image в GHCR с согласованным форматом версии

Связанные требования: REQ-29, REQ-30, REQ-31.

#### Scenario: AT-74 — CI и публикация

- **WHEN** push в master проходит или не проходит обязательные проверки
- **THEN** Push в `master` запускает сборку/unit/image/integration; PR-триггеров нет. Публикуется только прошедший обязательные проверки образ, переданный через `docker save/load`, без пересборки; при провале/пропуске обязательных проверок публикации нет. TRX/coverage сохраняются при наличии, включая неуспех, summary содержит image с тегом

Связанные требования: [Раздел 11](../build-and-release/spec.md), REQ-31.

#### Scenario: AT-75 — CI runner

- **WHEN** CI выполняется на выбранном GitHub-hosted runner
- **THEN** В публичном репозитории используется стандартный бесплатный GitHub-hosted Linux VM runner `ubuntu-24.04`; перед интеграционными тестами проверяются privileged Docker, cgroups v2 и isolate. Нет использования larger runners/постоянного judge-host; схема artifacts проверяется на соответствие бесплатной квоте хранения

Связанные требования: [Раздел 11](../build-and-release/spec.md), REQ-31.

#### Scenario: AT-76 — История и конкурирующие push

- **WHEN** выпуск публикуется, повторяется либо конкурирует с новым push
- **THEN** Выпуск использует `ghcr.io/texnokaktus-progolymp/runner-agent-cpp-23` и создаёт Git-тег для истории. Новый push может отменить устаревшие проверки до публикации, но не прерывает начатую публикацию. Git-тег `vYYYY.M.D.<run_number>` создаётся после публикации на коммите сборки; повтор с тем же коммитом допустим, другой коммит даёт ошибку без перезаписи. Сбой создания тега делает выпуск неуспешным, но опубликованный образ сохраняется

Связанные требования: [Раздел 11](../build-and-release/spec.md), REQ-31.

# Компоненты и внутренние контракты

## Purpose

Спецификация определяет согласованное поведение RunnerAgent в области «Компоненты и внутренние контракты» для первого C++23 MVP и его проверку.

## ADDED Requirements

### Requirement: REQ-26 — Логические границы компонентов

RunnerAgent SHALL сохранять логические границы transport, orchestration, storage, execution, languages и workspace без зависимости локального runner от gRPC/S3.

#### Scenario: REQ-26 — согласованный контракт

- **WHEN** реализуются transport, orchestration, storage и локальный runner
- **THEN** соблюдаются следующие условия (предложения и технические детали сохраняют явно указанный статус):

Реализация должна сохранять следующие логические границы. Они не требуют отдельного assembly на каждый компонент.

| Компонент | Ответственность |
| --- | --- |
| `Grpc` / `JudgeRunnerService` | Принятие запросов, преобразование transport models, выдача результата |
| Orchestration | Единственный слот RunJob, координация storage/workspace/runner, распространение отмены и обязательная очистка до освобождения слота |
| `Storage` / `IObjectStorage`, `S3ObjectStorage` | Получение и публикация S3-объектов, метаданные хранилища |
| `Execution` / `ISubmissionRunner`, `IsolateSubmissionRunner` | Локальная компиляция и execution pipeline, преобразование isolate metadata |
| `Languages` / `ILanguageProvider`, `CppLanguageProvider` | Единственный профиль компилятора экземпляра агента, проверка совместимости задания, toolchain, команды, файлы и окружение |
| `Workspace` / `WorkspaceManager` | Создание рабочих областей, размещение локальных файлов и очистка |

`IsolateSubmissionRunner` не должен зависеть от gRPC или S3. Он получает локальное задание с одним файлом исходного кода и набором тестов и возвращает локальные результаты и пути артефактов. Финальный внутренний контракт должен явно представлять отдельные compilation/execution limits. Точная сигнатура и распределение операций получения входов между orchestration и runner пока не определены.

Выделение низкоуровневого `ISandboxRunner` возможно как деталь реализации. Дополнительные языки должны добавляться без переноса логики gRPC/S3 в runner.
#### Scenario: AT-26 — Внешние границы

- **WHEN** выполняется сквозной обмен по gRPC, MinIO и локальному runner
- **THEN** HTTP/2 gRPC без TLS/auth передаёт управление; файлы идут через MinIO с production-реализацией `IObjectStorage`; runner работает с локальными файлами

Связанные требования: REQ-05, REQ-06, REQ-26.


### Requirement: REQ-27 — JIT и условия перехода на AOT

RunnerAgent SHALL начинать с .NET 10 JIT, учитывать AOT-ограничения и переходить на production AOT только после полного подтверждения совместимости.

#### Scenario: REQ-27 — согласованный контракт

- **WHEN** создаётся JIT-приложение или проверяется AOT-вариант
- **THEN** соблюдаются следующие условия (предложения и технические детали сохраняют явно указанный статус):

Разработка начинается с .NET 10 JIT. Код должен учитывать целевую Native AOT publication: статически известные типы, сгенерированные protobuf-модели, явная регистрация providers, `System.Text.Json` source generation при необходимости JSON; без runtime plugins, dynamic loading и ненужной reflection-heavy сериализации.

Проверка `PublishAot=true` и trimming/AOT warnings планируется при появлении реализации. Совместимость конкретных gRPC-библиотек и `AWSSDK.S3` с AOT не доказана. Переход production-образа на AOT требует проверки gRPC, S3, isolate и результатов на целевой Linux-платформе. AOT не заменяет sandbox; compiler/runtime поддерживаемого языка остаётся самостоятельной частью образа.

MVP остаётся на JIT. В CI предусматривается отдельная информационная проверка AOT: её неуспех виден в результатах, но не блокирует рабочий JIT-образ. Переход production на AOT допускается после успешной сборки и полного набора интеграционных тестов AOT-варианта, включая platform/OpenTelemetry; совместимость не считается доказанной заранее.

# Контракт задания и gRPC

## Purpose

Спецификация определяет согласованное поведение RunnerAgent в области «Контракт задания и gRPC» для первого C++23 MVP и его проверку.

## ADDED Requirements

### Requirement: REQ-07 — Контракт и валидация задания

RunnerAgent SHALL проверять идентификаторы, язык, упорядоченный набор тестов, ссылки и лимиты до принятия задания.

#### Scenario: REQ-07 — согласованный контракт

- **WHEN** мастер передаёт новый запрос задания
- **THEN** соблюдаются следующие условия (предложения и технические детали сохраняют явно указанный статус):

###### 3.1. Данные задания

Задание должно содержать следующие данные. Названия полей, кроме явно согласованных, предварительные; номера protobuf-полей, wire types остальных значений и оставшиеся технические правила валидации определяются при реализации. Согласованные ниже типы, ограничения и семантика сохраняются.

| Данные | Смысл и ограничения |
| --- | --- |
| `job_id` | Положительный `int64`: от `1` до `9223372036854775807`, задаётся мастером и возвращается без изменения |
| `language`, `language_version` | Проверка совместимости задания с единственным профилем агента; для MVP — строго `"cpp"` и `"23"` |
| `source` | Одна ссылка на исходный код: ключ S3 и ожидаемый SHA-256 |
| `tests[]` | Непустой упорядоченный набор тестов; каждый содержит заданный мастером `test_id` типа `int32` — порядковый номер теста в группе — и ссылку на входные данные по ключу и SHA-256 |
| `result_prefix` | Префикс выходных объектов, задаётся мастером |
| Compilation limits | Самостоятельные ограничения компиляции |
| Execution limits | Единый профиль ограничений, применяемый независимо к каждому тесту |

`test_id` должен быть положительным: от `1` до `2147483647`. Номера тестов должны быть уникальны внутри задания; в разных заданиях они могут повторяться. Задание должно содержать хотя бы один тест. Нулевые или отрицательные ID, повторяющиеся `test_id` и пустой набор тестов вызывают `INVALID_ARGUMENT`; задание не принимается. Агент возвращает `job_id` и `test_id` без изменения и не перенумеровывает тесты.

Агент обрабатывает именно переданный список тестов в порядке запроса. Полноту группы, отсутствие пропусков в номерах и их возрастание агент не проверяет; поднаборы и произвольный порядок положительных уникальных номеров допустимы. Агент не добавляет отсутствующие тесты, не сортирует и не перенумеровывает переданные. Например, список `8, 2, 5` обрабатывается в этом порядке с сохранением этих `test_id`. Правила ошибки компиляции и продолжения после ошибки отдельного теста сохраняются.

Один экземпляр агента обслуживает один конкретный компилятор. Поля `language` и `language_version` проверяют совместимость задания с его фиксированным профилем, а не выбирают компилятор внутри агента. Для MVP принимаются только `language = "cpp"` и `language_version = "23"`, с точным сравнением без алиасов и изменения регистра. Пустые и неподдерживаемые значения дают `INVALID_ARGUMENT` до принятия задания. `"23"` обозначает стандарт C++23; конкретная версия g++ определяется образом агента и ещё должна быть выбрана в Q-09. Версия g++ — внутренняя деталь образа агента: мастер не должен её знать или передавать. Отдельное поле версии компилятора в контракт задания не входит; валидация совместимости опирается на `language` и `language_version`.

Отдельные верхние пределы числа тестов и размера gRPC-запроса задания не вводятся: агент не должен отклонять корректный запрос по таким порогам. Настройки транспорта должны соответствовать этому решению. Непустой набор, положительные уникальные номера тестов и остальные согласованные правила валидации сохраняются. Это решение не отменяет resource limits компиляции и исполнения и согласуется с отсутствием отдельных лимитов размеров входных S3-объектов в разделе 5.

Bucket, команды запуска, compiler flags и `version_id` S3 в задании не выбираются. Оставшиеся правила валидации полей уточняются вместе с окончательным `.proto`, контрактом S3 (Q-07) и диапазонами resource limits (Q-05).

###### 3.2. Принятие задания
#### Scenario: AT-39 — ID и непустой набор

- **WHEN** переданы недопустимые ID, дубликаты, пустой набор либо границы типов
- **THEN** Нулевые/отрицательные ID, повторяющиеся `test_id` внутри задания и пустой набор дают `INVALID_ARGUMENT` без принятия; повтор номера теста в другом задании сам по себе не вызывает отказа; допустимые границы типов ID сохраняются без потери значений

Связанные требования: [Раздел 3.1](../job-api/spec.md), REQ-07, REQ-08.

#### Scenario: AT-41 — Валидация языка и версии

- **WHEN** передана точная пара cpp/23 либо пустое, иное или алиасное значение
- **THEN** Для MVP совместима только пара `"cpp"` / `"23"`; пустые значения, другой регистр, алиасы и неподдерживаемые значения дают `INVALID_ARGUMENT` без принятия и смены компилятора

Связанные требования: [Раздел 3.1](../job-api/spec.md), REQ-07, REQ-21.


### Requirement: REQ-08 — Длительный RunJob и единственный слот

RunnerAgent SHALL обрабатывать задание в единственном unary RPC RunJob и немедленно отклонять конкурентные вызовы без очереди.

#### Scenario: REQ-08 — согласованный контракт

- **WHEN** мастер вызывает RunJob
- **THEN** Единственный RPC задания — `RunJob`: один запрос с заданием и один ответ с итоговым структурированным результатом. Вызов остаётся открытым на время подготовки, компиляции, последовательного прогона тестов, публикации и очистки. Промежуточное подтверждение принятия и polling результата не используются. Это логическая занятость раннера; gRPC health и отказ конкурентному запросу обслуживаются без ожидания завершения задания.

В каждый момент обрабатывается не более одного RunJob. Все конкурентные запросы, включая тот же job_id с одинаковым или изменённым содержимым, получают RESOURCE_EXHAUSTED. Очереди, сравнения повторных заданий, дедупликации и истории job_id нет. После освобождения слота запрос с прежним ID может исполнить задание заново. Мастер выдаёт новый job_id и result_prefix для каждого нового запуска.

#### Scenario: AT-02 — Длительность вызова

- **WHEN** начат RunJob с ещё выполняющимся заданием
- **THEN** RPC не возвращает раннее подтверждение; итоговый ответ формируется после обработки, публикации и очистки

Связанные требования: REQ-08, REQ-11.

#### Scenario: AT-03 — Конкурентные вызовы и повторы

- **WHEN** во время активного вызова приходит запрос с другим ID либо с текущим ID и любым содержимым
- **THEN** каждый конкурентный вызов сразу получает RESOURCE_EXHAUSTED без очереди, второго исполнения и изменения активного задания

Связанные требования: REQ-08, REQ-12.

#### Scenario: AT-30 — Повтор после освобождения

- **WHEN** RunJob завершён и мастер повторно передаёт валидное задание с прежним job_id
- **THEN** свободный агент может исполнить его заново; сохранённого результата, дедупликации и истории ID нет

Связанные требования: REQ-08, REQ-13.

#### Scenario: AT-34 — Отсутствие сравнения повторов

- **WHEN** во время работы повторён текущий job_id с теми же или изменёнными полями
- **THEN** возвращается RESOURCE_EXHAUSTED; поля не сравниваются для дедупликации, входы повторного запроса не скачиваются

Связанные требования: REQ-08.

### Requirement: REQ-09 — Итоговый ответ внутри RunJob

RunnerAgent SHALL возвращать структурированный результат в исходном RunJob после очистки без отдельного хранения для последующего чтения.

#### Scenario: REQ-09 — согласованный контракт

- **WHEN** завершается обработка RunJob
- **THEN** Результат возвращается единственным ответом исходного RPC. Ошибки компиляции, исполнения и обработанные инфраструктурные ошибки отражаются в результате по REQ-24/REQ-25 при gRPC OK, если вызов не отменён и ответ ещё может быть отправлен. Состояние результата между вызовами не сохраняется. Отдельных RPC чтения или подтверждения результата нет.

Потеря ответа не даёт возможности получить прежний результат или доказать по job_id, выполнилось ли задание. Автоматический безопасный повтор и exactly-once исполнение не гарантируются. Уже опубликованные артефакты сохраняются. После очистки и завершения серверной обработки слот освобождается; ожидание подтверждения доставки от клиента его не удерживает.

#### Scenario: AT-05 — Нет промежуточного результата

- **WHEN** прогон ещё не завершён
- **THEN** исходный RunJob остаётся открытым; промежуточный ответ и отдельный запрос проверки готовности не предусмотрены

Связанные требования: REQ-09.

#### Scenario: AT-06 — Возврат после очистки

- **WHEN** RunJob завершил прогон без отмены
- **THEN** публикация и попытка очистки завершены до итогового ответа; после успешной очистки и завершения обработчика раннер принимает следующее задание

Связанные требования: REQ-09, REQ-14.

#### Scenario: AT-32 — Отсутствие API чтения результата

- **WHEN** мастер обращается к контракту задания после завершённого вызова
- **THEN** контракт содержит только RunJob; получить ранее выданный или потерянный результат отдельным вызовом нельзя

Связанные требования: REQ-09, REQ-13.

### Requirement: REQ-10 — Допуск, отмена и коды RPC

RunnerAgent SHALL атомарно допускать один вызов, распространять отмену RPC на проверку и очищать среду до повторного использования.

#### Scenario: REQ-10 — согласованный контракт

- **WHEN** запросы конкурируют либо активный RPC отменён
- **THEN** Проверки допуска выполняются без ожидания занятого слота: при остановке агент отвечает UNAVAILABLE; иначе атомарно пытается занять единственный слот и при занятости отвечает RESOURCE_EXHAUSTED. Для получившего слот запроса проверяется корректность; ошибка даёт INVALID_ARGUMENT и освобождает слот без создания workspace или исполнения. В частности, конкурентный запрос не получает особого ответа из-за совпадения job_id или некорректного содержимого. Штатная остановка и захват слота согласованы атомарно: новое задание не может обойти начавшуюся остановку.

Уже отменённый вызов не должен начинать работу. Если отмена происходит после захвата слота, обработчик освобождает только свой слот после необходимой очистки. Отмена отклонённого конкурентного вызова не влияет на активное задание.

Отмена RunJob, истечение deadline или обнаруженный сервером разрыв соединения прекращают обработку задания. Агент останавливает текущую компиляцию или тест, завершает все процессы его песочницы и дожидается их завершения; следующие тесты не запускаются. Мягкость относится к управляемой остановке проверки и обязательной очистке, а не к ожиданию естественного завершения программы участника. Механизм завершения процессов выбирается при реализации так, чтобы не оставлять дочерние процессы.

Скачивания, загрузки, задержки и повторы storage прекращаются; новые публикации и допубликация частичных результатов не выполняются. Уже опубликованные S3-объекты остаются. Отмена клиента не является RuntimeError или превышением лимита решения. Доставка частичного либо итогового структурированного результата отменённого RPC не гарантируется.

Очистка запускается независимо от уже отменённого токена RPC и завершается до освобождения слота. Клиент может получить ошибку отмены раньше окончания серверной очистки; до её успешного завершения новые вызовы отклоняются. Ошибка очистки запрещает повторное использование среды и завершает агент с кодом 1 по REQ-14.

Deadline задаёт мастер, агент не вводит своего значения по умолчанию или отдельного общего лимита длительности задания. В новой модели deadline ограничивает время ожидания RPC и при истечении запускает отмену; лимиты компиляции и каждого теста сохраняются. Разрыв соединения действует как отмена после уведомления сервера транспортом; мгновенное обнаружение сетевой потери не гарантируется.

| Ситуация | Код gRPC | Ответ |
| --- | --- | --- |
| Прогон завершён, включая ошибки кода и обработанные инфраструктурные ошибки | `OK` | Структурированный результат задания |
| Другой вызов занимает раннер, включая отмену и очистку | `RESOURCE_EXHAUSTED` | Агент занят |
| Агент останавливается или выведен из работы после ошибки очистки | `UNAVAILABLE` | Агент не принимает задания |
| Свободный агент получил некорректное задание | `INVALID_ARGUMENT` | Описание ошибки |
| Клиент явно отменил RPC | `CANCELLED` на стороне клиента | Итоговый результат не гарантируется |
| Истёк deadline клиента | `DEADLINE_EXCEEDED` на стороне клиента | Итоговый результат не гарантируется |

Коды соответствуют [стандартным кодам gRPC](https://grpc.io/docs/guides/status-codes/). Правила реакции на отмену и deadline основаны на [cancellation](https://grpc.io/docs/guides/cancellation/) и [deadlines](https://grpc.io/docs/guides/deadlines/). Транспортная ошибка при сетевом сбое определяется gRPC; агент не обещает доставить собственный код или тело по разорванному соединению.

#### Scenario: AT-04 — Атомарный допуск

- **WHEN** два допустимых RunJob поступают одновременно
- **THEN** только один занимает слот; другой получает RESOURCE_EXHAUSTED, двойного исполнения и очереди нет

Связанные требования: REQ-10.

#### Scenario: AT-31 — Потеря соединения или ответа

- **WHEN** соединение потеряно во время работы либо итоговый ответ не дошёл
- **THEN** при уведомлении об отмене незавершённая работа останавливается и очищается; завершённая работа не восстанавливается для чтения; сохранённые S3-объекты остаются, повтор после освобождения может исполнить задание заново

Связанные требования: REQ-09, REQ-10.

#### Scenario: AT-33 — Ответы и коды gRPC

- **WHEN** проверяются завершение, занятость, остановка, валидация, отмена и deadline
- **THEN** применяются коды из таблицы REQ-10; ошибка компиляции/исполнения возвращается внутри результата RunJob с OK при живом вызове

Связанные требования: REQ-08, REQ-09, REQ-10.

#### Scenario: AT-35 — Приоритет допуска

- **WHEN** запрос приходит при остановке, занятости или со свободным слотом
- **THEN** остановка даёт UNAVAILABLE; работающий либо очищающийся раннер даёт RESOURCE_EXHAUSTED даже для некорректного запроса; свободный проверяет задание и возвращает INVALID_ARGUMENT при ошибке; отклонение не меняет текущее задание

Связанные требования: REQ-10, REQ-14.

#### Scenario: AT-36 — Отмена до начала и изоляция вызовов

- **WHEN** запрос отменён до начала обработки либо отменён уже отклонённый конкурентный вызов
- **THEN** новое исполнение не начинается, чужой слот и активное задание не затрагиваются; захваченный собственный слот освобождается после необходимой очистки

Связанные требования: REQ-10, REQ-14.

#### Scenario: AT-38 — Отмена и deadline на стадиях

- **WHEN** активный RunJob отменён клиентом, его deadline истёк или сервер обнаружил разрыв во время подготовки, компиляции, теста либо публикации
- **THEN** текущая работа и все процессы sandbox остановлены, следующие тесты и storage-повторы/допубликация не начинаются; выполняется очистка, занятость сохраняется до её окончания; клиенту не гарантируется результат

Связанные требования: REQ-10, REQ-12, REQ-14.

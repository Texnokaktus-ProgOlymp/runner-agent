# Контракт задания и gRPC

## Purpose

Спецификация определяет согласованное поведение RunnerAgent в области «Контракт задания и gRPC» для первого C++23 MVP и его проверку.

## ADDED Requirements

### Requirement: REQ-07 — Контракт и валидация задания

RunnerAgent SHALL проверять идентификаторы, язык, упорядоченный набор тестов, ссылки и лимиты до принятия задания.

#### Scenario: REQ-07 — согласованный контракт

- **WHEN** мастер передаёт новый запрос задания
- **THEN** соблюдаются следующие условия (предложения и технические детали сохраняют явно указанный статус):

###### 3.1. Данные задания

Задание должно содержать следующие данные. Названия полей, кроме явно согласованных, предварительные; номера protobuf-полей, wire types остальных значений и оставшиеся технические правила валидации определяются при реализации. Согласованные ниже типы, ограничения и семантика сохраняются.

| Данные | Смысл и ограничения |
| --- | --- |
| `job_id` | Положительный `int64`: от `1` до `9223372036854775807`, задаётся мастером и возвращается без изменения |
| `language`, `language_version` | Проверка совместимости задания с единственным профилем агента; для MVP — строго `"cpp"` и `"23"` |
| `source` | Одна ссылка на исходный код: ключ S3 и ожидаемый SHA-256 |
| `tests[]` | Непустой упорядоченный набор тестов; каждый содержит заданный мастером `test_id` типа `int32` — порядковый номер теста в группе — и ссылку на входные данные по ключу и SHA-256 |
| `result_prefix` | Префикс выходных объектов, задаётся мастером |
| Compilation limits | Самостоятельные ограничения компиляции |
| Execution limits | Единый профиль ограничений, применяемый независимо к каждому тесту |

`test_id` должен быть положительным: от `1` до `2147483647`. Номера тестов должны быть уникальны внутри задания; в разных заданиях они могут повторяться. Задание должно содержать хотя бы один тест. Нулевые или отрицательные ID, повторяющиеся `test_id` и пустой набор тестов вызывают `INVALID_ARGUMENT`; задание не принимается. Агент возвращает `job_id` и `test_id` без изменения и не перенумеровывает тесты.

Агент обрабатывает именно переданный список тестов в порядке запроса. Полноту группы, отсутствие пропусков в номерах и их возрастание агент не проверяет; поднаборы и произвольный порядок положительных уникальных номеров допустимы. Агент не добавляет отсутствующие тесты, не сортирует и не перенумеровывает переданные. Например, список `8, 2, 5` обрабатывается в этом порядке с сохранением этих `test_id`. Правила ошибки компиляции и продолжения после ошибки отдельного теста сохраняются.

Один экземпляр агента обслуживает один конкретный компилятор. Поля `language` и `language_version` проверяют совместимость задания с его фиксированным профилем, а не выбирают компилятор внутри агента. Для MVP принимаются только `language = "cpp"` и `language_version = "23"`, с точным сравнением без алиасов и изменения регистра. Пустые и неподдерживаемые значения дают `INVALID_ARGUMENT` до принятия задания. `"23"` обозначает стандарт C++23; конкретная версия g++ определяется образом агента и ещё должна быть выбрана в Q-09. Версия g++ — внутренняя деталь образа агента: мастер не должен её знать или передавать. Отдельное поле версии компилятора в контракт задания не входит; валидация совместимости опирается на `language` и `language_version`.

Отдельные верхние пределы числа тестов и размера gRPC-запроса задания не вводятся: агент не должен отклонять корректный запрос по таким порогам. Настройки транспорта должны соответствовать этому решению. Непустой набор, положительные уникальные номера тестов и остальные согласованные правила валидации сохраняются. Это решение не отменяет resource limits компиляции и исполнения и согласуется с отсутствием отдельных лимитов размеров входных S3-объектов в разделе 5.

Bucket, команды запуска, compiler flags и `version_id` S3 в задании не выбираются. Оставшиеся правила валидации полей уточняются вместе с окончательным `.proto`, контрактом S3 (Q-07) и диапазонами resource limits (Q-05).

###### 3.2. Принятие задания
#### Scenario: AT-39 — ID и непустой набор

- **WHEN** переданы недопустимые ID, дубликаты, пустой набор либо границы типов
- **THEN** Нулевые/отрицательные ID, повторяющиеся `test_id` внутри задания и пустой набор дают `INVALID_ARGUMENT` без принятия; повтор номера теста в другом задании сам по себе не вызывает отказа; допустимые границы типов ID сохраняются без потери значений

Связанные требования: [Раздел 3.1](../job-api/spec.md), REQ-07, REQ-08.

#### Scenario: AT-41 — Валидация языка и версии

- **WHEN** передана точная пара cpp/23 либо пустое, иное или алиасное значение
- **THEN** Для MVP совместима только пара `"cpp"` / `"23"`; пустые значения, другой регистр, алиасы и неподдерживаемые значения дают `INVALID_ARGUMENT` без принятия и смены компилятора

Связанные требования: [Раздел 3.1](../job-api/spec.md), REQ-07, REQ-21.


### Requirement: REQ-08 — Асинхронное принятие и повторы

RunnerAgent SHALL атомарно принимать задание, подтверждать его асинхронно и различать точный повтор, конфликт, занятость и остановку.

#### Scenario: REQ-08 — согласованный контракт

- **WHEN** мастер вызывает StartJob для нового или текущего задания
- **THEN** соблюдаются следующие условия (предложения и технические детали сохраняют явно указанный статус):

API должен быть асинхронным. Имя RPC запуска — `StartJob`. Агент проверяет структуру нового задания, фиксирует его принятие и занятость ресурса и сразу возвращает подтверждение. Подтверждение не означает успешной компиляции или исполнения. После принятия работа продолжается независимо от завершения RPC и разрыва соединения.

Для долгоживущего агента действуют правила:

| Ситуация | Поведение |
| --- | --- |
| Ресурс свободен и новое задание прошло проверку | Принять задание и начать обработку |
| Выполняется задание с тем же `job_id` и одинаковым содержимым | Ответить «задание уже принято», повторно не исполнять |
| Готовый результат того же `job_id` ожидает чтения, содержимое запроса одинаково | Ответить «задание уже принято», повторно не исполнять |
| Тот же текущий `job_id`, но содержимое запроса изменено | Вернуть ошибку конфликта; принятое задание и его результат не изменять |
| Ресурс занят другим `job_id`, включая ожидание чтения | Ответить «ресурс занят» |
| Начата штатная остановка | Не принимать новые задания |

После выдачи результата или перезапуска агент не должен хранить историю ID. Когда ресурс свободен и приём заданий разрешён, запрос с ранее использованным `job_id` проходит обычную проверку и может запустить задание заново. Мастер должен выдавать новый `job_id` для каждого нового запуска. Защита от повторного исполнения действует только пока задание или его непрочитанный результат находятся у агента; постоянного реестра выполненных заданий нет.

Для повторного `StartJob` с текущим `job_id` агент должен сравнивать значения всех полей задания:

- `language` и `language_version`;
- ключ S3 и ожидаемый SHA-256 исходного файла;
- список `tests[]` с учётом количества и порядка тестов, включая `test_id`, ключ S3 и ожидаемый SHA-256 каждого входного файла;
- `result_prefix`;
- все лимиты компиляции и исполнения.

Для запроса, прошедшего проверку корректности согласно [разделу 3.5](../job-api/spec.md), любое различие этих значений означает конфликт (`ALREADY_EXISTS`). Сравниваются разобранные значения полей, а не байты protobuf-сообщения. Для сравнения агент не должен повторно скачивать файлы из S3: используются ссылки и заявленные хеши принятого и повторного запросов. Эти правила действуют как во время выполнения, так и при ожидании чтения готового результата.

Семантика повторов, правила сравнения содержимого и ответы согласованы как часть Q-02; коды gRPC приведены в разделе 3.4. Окончательные типы полей и их представление определяются вместе с `.proto`.

###### 3.3. Получение результата
#### Scenario: AT-02 — Подтверждение и отключение клиента

- **WHEN** клиент отключается после принятия задания
- **THEN** Подтверждение приходит до завершения обработки; принятое задание продолжает работу после завершения RPC/соединения

Связанные требования: REQ-08.

#### Scenario: AT-03 — Повторы `StartJob` во время работы и ожидания чтения

- **WHEN** повторяется StartJob текущего либо другого задания
- **THEN** Текущий ID с одинаковым содержимым получает «задание уже принято» без повторного исполнения; с изменённым содержимым — ошибку конфликта без изменения задания или результата; другой ID получает «ресурс занят»

Связанные требования: REQ-08, REQ-12.

#### Scenario: AT-30 — Отсутствие истории ID

- **WHEN** ранее выданный ID используется после освобождения ресурса или перезапуска
- **THEN** После выдачи результата или перезапуска валидный запрос с ранее использованным ID принимается заново, если ресурс свободен и приём заданий разрешён

Связанные требования: REQ-08, REQ-13.

#### Scenario: AT-34 — Сравнение повторного задания

- **WHEN** повтор текущего задания изменяет одно из полей или protobuf-представление
- **THEN** Для валидного запроса с текущим ID изменение любого поля из [раздела 3.2](../job-api/spec.md), включая порядок тестов, даёт `ALREADY_EXISTS` без изменения принятого задания или результата; одинаковые разобранные значения дают `AlreadyAccepted` независимо от байтового представления protobuf; сравнение не вызывает скачиваний из S3

Связанные требования: [Раздел 3.2](../job-api/spec.md), REQ-08.


### Requirement: REQ-09 — Однократная выдача результата

RunnerAgent SHALL немедленно возвращать NotReady или NOT_FOUND, а готовый результат атомарно извлекать до отправки ответа.

#### Scenario: REQ-09 — согласованный контракт

- **WHEN** мастер вызывает GetResult
- **THEN** соблюдаются следующие условия (предложения и технические детали сохраняют явно указанный статус):

Операция `GetResult` должна выдавать результат соответствующего задания. Если текущее задание с запрошенным ID ещё выполняется, она сразу отвечает «не завершено», не ожидает окончания внутри RPC и не меняет состояние или занятость ресурса. Если запрошенного задания нет, включая чужой ID или уже выданный результат, агент должен отвечать одинаково: «не найдено», не меняя состояние текущего задания.

При выдаче готового результата обработчик `GetResult` должен атомарно забрать результат из состояния агента и освободить ресурс **до отправки RPC-ответа**. Обработчик использует извлечённый результат для формирования ответа; в состоянии агента результата больше нет. Отдельного подтверждения мастера нет; повторное чтение выданного результата невозможно. S3-артефакты остаются. Коды gRPC приведены в разделе 3.4.
#### Scenario: AT-05 — Ранний `GetResult` и запрос другого задания

- **WHEN** GetResult вызван во время работы или с другим ID
- **THEN** Для выполняемого задания — «не завершено», для другого ID — «не найдено»; оба ответа немедленные, состояние и занятость не меняются

Связанные требования: REQ-09.

#### Scenario: AT-06 — Выдача готового результата

- **WHEN** GetResult извлекает готовый результат
- **THEN** До отправки ответа ресурс освобождён, результат удалён из состояния; повторный запрос получает «не найдено», если ID не принят заново; S3-артефакты сохранены

Связанные требования: REQ-09, REQ-10.

#### Scenario: AT-32 — Отсутствующее задание

- **WHEN** GetResult запрашивает неизвестный, чужой или уже выданный ID
- **THEN** Неизвестный, чужой и уже выданный ID дают одинаковый ответ «не найдено», если задание с этим ID отсутствует; состояние текущего задания не меняется

Связанные требования: REQ-09.


### Requirement: REQ-10 — Конкурентные переходы и протокол RPC

RunnerAgent SHALL согласовывать конкурентные переходы и применять установленные коды, приоритеты проверок и семантику отмены RPC.

#### Scenario: REQ-10 — согласованный контракт

- **WHEN** RPC выполняются одновременно, повторяются или завершаются с ошибкой
- **THEN** соблюдаются следующие условия (предложения и технические детали сохраняют явно указанный статус):

Принятие задания и переход при `GetResult` должны быть согласованы при конкурентных запросах: нельзя принять два задания одновременно или повторно выдать один сохранённый результат. При двух одновременных запросах готовый результат забирает только один обработчик; другой получает «не найдено», если задание с этим ID не было принято заново.

Обрыв соединения или потеря ответа после атомарного извлечения не должны восстанавливать результат или занятость ресурса. Повторный `GetResult` отвечает «не найдено», если задание с этим ID не было принято заново. Протокол не гарантирует доставку извлечённого результата мастеру; опубликованные S3-артефакты сохраняются. Это согласованная часть Q-02.

###### 3.4. Имена RPC, ответы и коды gRPC

Согласованы имена `StartJob` и `GetResult` и следующее соответствие ситуаций ответам. Имена состояний в успешных ответах закрепляют семантику; окончательное protobuf-представление и номера полей ещё предстоит определить.

| RPC / ситуация | Код gRPC | Содержимое ответа |
| --- | --- | --- |
| `StartJob`: задание принято | `OK` | `Accepted` |
| `StartJob`: точный повтор текущего задания | `OK` | `AlreadyAccepted` |
| `StartJob`: текущий ID с изменённым содержимым | `ALREADY_EXISTS` | Описание конфликта |
| `StartJob`: агент занят другим заданием | `RESOURCE_EXHAUSTED` | «Агент занят» |
| `StartJob`: новое задание при остановке | `UNAVAILABLE` | «Агент останавливается» |
| Любой RPC: некорректный запрос | `INVALID_ARGUMENT` | Описание ошибки |
| `GetResult`: результат ещё не готов | `OK` | `NotReady` |
| `GetResult`: результат готов | `OK` | `Completed` и результат |
| `GetResult`: запрошенное задание отсутствует | `NOT_FOUND` | «Задание не найдено» |

`Completed` означает завершение обработки задания, включая ошибки компиляции или исполнения. Они отражаются внутри структурированного результата, а не меняют успешный код получения готового результата. `Accepted` и `AlreadyAccepted` также не означают успешности компиляции или тестов.

Соответствие использует [стандартные коды gRPC](https://grpc.io/docs/guides/status-codes/). При нескольких применимых условиях действует порядок из раздела 3.5.

###### 3.5. Приоритет проверок RPC

`StartJob` должен выполнять проверки в следующем порядке, возвращая ответ по первому применимому условию:

1. Проверить корректность запроса; при ошибке вернуть `INVALID_ARGUMENT` независимо от занятости или остановки агента.
2. Если `job_id` совпадает с текущим, сравнить содержимое по [разделу 3.2](../job-api/spec.md): вернуть `OK` с `AlreadyAccepted` либо `ALREADY_EXISTS`. Это правило действует и во время штатной остановки.
3. Если агент останавливается, вернуть `UNAVAILABLE`.
4. Если ресурс занят другим заданием, вернуть `RESOURCE_EXHAUSTED`.
5. Иначе атомарно принять задание и вернуть `OK` с `Accepted`.

Проверки текущего ID, остановки и занятости должны быть согласованы с фиксацией принятия и конкурентными переходами состояния согласно REQ-10. Между проверкой свободного ресурса и принятием нельзя допустить принятие второго задания или обойти начавшуюся штатную остановку.

Для `GetResult` сначала проверяется корректность запроса (`INVALID_ARGUMENT` при ошибке), затем наличие запрошенного задания (`NOT_FOUND` при отсутствии) и готовность результата (`OK` с `NotReady` либо атомарное извлечение и `OK` с `Completed`). Режим остановки не препятствует получению результата, пока gRPC-сервер работает.

Проверка корректности здесь относится к данным RPC-запроса. Скачивание файлов и проверка их содержимого по SHA-256 выполняются после принятия задания согласно REQ-11; правила валидации полей уточняются в Q-03.

###### 3.6. Ответственность за deadlines RPC

Deadline исходящего RPC задаёт мастер. Конкретная длительность и её настройка относятся к мастеру и не задаются этой спецификацией или конфигурацией RunnerAgent. Значение по умолчанию для deadline на стороне агента не устанавливается.

Агент должен сохранять согласованное поведение при отмене RPC или истечении переданного deadline: уже принятое через `StartJob` задание продолжает выполняться, а уже извлечённый через `GetResult` результат не восстанавливается. Deadline RPC не является лимитом длительности задания и не заменяет таймаут ожидания результата при штатной остановке.

#### Scenario: AT-04 — Конкурентное принятие и чтение

- **WHEN** два клиента одновременно принимают задания или читают готовый результат
- **THEN** Два задания одновременно не принимаются; готовый результат забирает один обработчик, второй получает «не найдено», если задание с этим ID не было принято заново

Связанные требования: REQ-10.

#### Scenario: AT-31 — Потеря ответа `GetResult`

- **WHEN** соединение обрывается после извлечения результата
- **THEN** Обрыв соединения после атомарного извлечения не восстанавливает результат или занятость; повторный запрос получает «не найдено», если ID не принят заново; S3-артефакты сохранены

Связанные требования: REQ-09, REQ-10.

#### Scenario: AT-33 — Ответы и коды gRPC

- **WHEN** вызываются RPC во всех согласованных состояниях
- **THEN** Для ситуаций из [раздела 3.4](../job-api/spec.md) проверяется точное соответствие коду и состоянию ответа; получение готового результата с ошибкой компиляции или исполнения возвращает `OK` и `Completed` с соответствующим результатом

Связанные требования: [Раздел 3.4](../job-api/spec.md), REQ-08, REQ-09.

#### Scenario: AT-35 — Приоритет проверок `StartJob`

- **WHEN** условия некорректности, повтора, остановки и занятости применимы одновременно
- **THEN** Некорректный запрос всегда даёт `INVALID_ARGUMENT`, включая повтор текущего ID и остановку; валидный повтор текущего ID при остановке даёт `AlreadyAccepted` или `ALREADY_EXISTS`; валидный другой ID при остановке и занятости даёт `UNAVAILABLE`, а при обычной занятости — `RESOURCE_EXHAUSTED`

Связанные требования: [Раздел 3.5](../job-api/spec.md), REQ-08, REQ-10.

#### Scenario: AT-36 — Приоритет проверок `GetResult`

- **WHEN** GetResult получает некорректный запрос или вызывается во время остановки
- **THEN** Некорректный запрос даёт `INVALID_ARGUMENT` до поиска задания; для валидного запроса проверяются наличие и готовность; при остановке те же ответы доступны до остановки gRPC-сервера

Связанные требования: [Раздел 3.5](../job-api/spec.md), REQ-09, REQ-14.

#### Scenario: AT-38 — Отмена и deadline RPC

- **WHEN** RPC отменён или его deadline истёк после принятия либо извлечения
- **THEN** Отмена RPC или истечение заданного клиентом deadline после принятия задания не прекращают его обработку; после извлечения результата не восстанавливают его или занятость ресурса

Связанные требования: [Раздел 3.6](../job-api/spec.md), REQ-08, REQ-09, REQ-10.

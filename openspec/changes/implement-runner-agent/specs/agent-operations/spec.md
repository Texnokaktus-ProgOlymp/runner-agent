# Конфигурация и эксплуатация

## Purpose

Спецификация определяет согласованное поведение RunnerAgent в области «Конфигурация и эксплуатация» для первого C++23 MVP и его проверку.

## ADDED Requirements

### Requirement: OPS-01 — Конфигурация и workspace

RunnerAgent SHALL фиксировать настройки при запуске с приоритетом окружения и создавать только собственные рабочие области.

#### Scenario: OPS-01 — согласованный контракт

- **WHEN** приложение загружает конфигурацию и готовит workspace
- **THEN** соблюдаются следующие условия (предложения и технические детали сохраняют явно указанный статус):

Обычные параметры задаются в `appsettings.json`; переменные окружения переопределяют значения файла. Credentials читаются только из окружения по REQ-06 и в файл не записываются. Параметры хранилища группируются в секции `S3`, workspace и остановки — в `Runner`; platform/OpenTelemetry сохраняют собственные имена настроек, включая `SERVICE_NAME`. Конфигурация фиксируется при запуске: для её изменения нужен перезапуск, горячая перезагрузка не предусматривается. Точные имена оставшихся параметров внутри секций ещё выбираются.

Корневой каталог workspace задаётся конфигурацией; по умолчанию — `/var/lib/runner-agent`. Агент создаёт внутри собственные рабочие каталоги. S3-ключи не преобразуются в локальные пути. Правила начальной очистки только собственных рабочих областей сохраняются; механизм владения каталогами и isolate boxes уточняется в Q-09.

Из согласованных требований следуют следующие категории настроек:

| Настройка | Зафиксированная семантика |
| --- | --- |
| gRPC endpoint и порт | HTTP/2 без TLS и аутентификации в доверенной внутренней сети; по умолчанию `0.0.0.0:8080` внутри контейнера, адрес и порт настраиваются |
| MinIO endpoint | Задаётся конфигурацией агента; `ForcePathStyle = true` |
| Регион подписи MinIO | По умолчанию `us-east-1`, можно переопределить; сервер без явно заданного региона поддерживается |
| Имя сервиса телеметрии | Имя различает язык и версию языка: для C++23 — `SERVICE_NAME=runner-agent-cpp-23`; другие языковые профили используют другие имена. Экземпляры одного профиля различаются по `service.instance.id` |
| Экспорт телеметрии | Адрес коллектора и параметры экспорта задаются при развёртывании средствами platform/OpenTelemetry |
| Bucket исходного кода | Отдельный от данных тестов и результатов |
| Общий bucket | Входы тестов и выходные артефакты |
| Credential provider | Только окружение агента: `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, необязательный `AWS_SESSION_TOKEN`; без fallback, с изоляцией секретов по REQ-19 |
| Workspace и isolate | Корень workspace настраивается в `Runner`, по умолчанию `/var/lib/runner-agent`; структура собственных каталогов, mounts, box IDs и cgroups требуют выбора |
| Профиль C++23 | Команда и флаги согласованы в REQ-21; версия g++, точный allowlist окружения и доступные файлы уточняются при реализации без изменения профиля |

Resource limits задания поступают от мастера; это не разрешение менять профиль toolchain. Способ задания host/container limits и их согласования с isolate ещё требует проработки.
#### Scenario: AT-72 — Конфигурация

- **WHEN** обычные настройки заданы одновременно в файле и окружении, затем изменены
- **THEN** Переменные окружения переопределяют обычные параметры `appsettings.json`; credentials читаются только из окружения. Секции `S3`/`Runner` и собственные имена platform/OpenTelemetry сохраняются. Изменения настроек применяются после перезапуска, горячая перезагрузка отсутствует

Связанные требования: [Раздел 10](../agent-operations/spec.md), REQ-06.

#### Scenario: AT-73 — Корень workspace

- **WHEN** используется workspace по умолчанию либо переопределённый корень
- **THEN** По умолчанию используется `/var/lib/runner-agent`, корень можно переопределить. Рабочие каталоги агента создаются внутри корня, S3-ключи не преобразуются в локальные пути; очистка затрагивает только собственные области

Связанные требования: [Раздел 10](../agent-operations/spec.md), REQ-19.


### Requirement: REQ-28 — Защита секретов при сборке

RunnerAgent SHALL получать credentials при развёртывании и исключать секреты из Dockerfile, build args и слоёв образа.

#### Scenario: REQ-28 — согласованный контракт

- **WHEN** собирается образ или настраиваются runtime credentials
- **THEN** соблюдаются следующие условия (предложения и технические детали сохраняют явно указанный статус):

Runtime credentials должны задаваться при развёртывании агента. Токены registry и S3 credentials не записываются в Dockerfile, build args или слои образа. При необходимости приватного NuGet используются BuildKit secret mounts; наличие такой зависимости пока не установлено.

### Requirement: OPS-02 — Наблюдаемость, health и завершение

RunnerAgent SHALL предоставлять согласованные логи, трассы, метрики и gRPC health с определёнными кодами управляемого выхода.

#### Scenario: OPS-02 — согласованный контракт

- **WHEN** агент обслуживает задания, экспортирует диагностику или завершает процесс
- **THEN** соблюдаются следующие условия (предложения и технические детали сохраняют явно указанный статус):

Для логирования и OpenTelemetry выбран [Texnokaktus.ProgOlymp.Platform](https://github.com/Texnokaktus-ProgOlymp/platform). Сохраняется его стандартное текстовое логирование в stdout; требование JSON-формата отменено. OpenTelemetry подключается через platform, использующую [Texnokaktus.ProgOlymp.OpenTelemetry](https://github.com/Texnokaktus-ProgOlymp/OpenTelemetry-Library), без повторной независимой регистрации тех же providers/exporters.

По изученному исходному коду platform на 2 октября 2026 года точка подключения — `WebApplicationBuilder.UsePlatform()`, обязательна переменная `SERVICE_NAME`; доступны `ConfigureOpenTelemetry.WithTracerConfiguration`, `WithMeterConfiguration` и `ConfigureSerilog.ConfigureSerilog`. Пакет ориентирован на `net10.0` и настраивает Serilog Console и OpenTelemetry. Это описание API зависимости, а не уже реализованной интеграции RunnerAgent. Версия пакета, источник пакетов и AOT-совместимость проверяются при создании приложения; согласованная семантика наблюдаемости приведена ниже, точные имена инструментов и технические детали инструментации ещё выбираются.

Логи сохраняют контекст `job_id`, для событий конкретного теста — также `test_id`, стадию и причину ошибки, когда они применимы. Секреты, исходники, входные данные и содержимое stdout/stderr, включая потоки компилятора, не включаются в служебные логи и экспортируемую телеметрию. Это ограничение распространяется и на сообщения исключений/библиотек и обогащение логов; публикация потоков как S3-артефактов сохраняется. Стандартный текстовый шаблон не обязан отображать все структурированные свойства контекста.

Стандартный gRPC Health Checking работает на существующем gRPC-порту без отдельного HTTP endpoint. После успешной локальной инициализации API имеет SERVING; обработка RunJob, отмена и очистка, недоступность MinIO сами по себе этот статус не меняют. Health не занимает слот задания. При штатной остановке API остаётся SERVING, пока завершается текущий вызов и очистка; новые RunJob получают UNAVAILABLE. Перед остановкой RPC-сервера выставляется NOT_SERVING. При ошибке очистки новые задания также запрещены, после завершения обработки текущего вызова сервер и процесс останавливаются. Health означает доступность API, а не свободный слот.

Код управляемого завершения — 0 при штатной остановке после текущего вызова и очистки, 1 при ошибке запуска или невозможности очистить sandbox/завершить его процессы. Ошибки компиляции, тестов и отдельные сбои storage сами по себе процесс не завершают. Успешная отмена с очисткой освобождает раннер для следующего задания, если агент не останавливается. При отменённом RPC ожидание доставки результата не требуется. Принудительное внешнее завершение этими кодами не нормализуется.

Ручной деплой предполагает выбор проверенного образа по тегу версии, подготовку Linux judge-host, bucket, конфигурации, credentials и workspace, запуск контейнера с долгоживущим агентом и контрольное задание C++ с получением результата. Точная команда запуска, проверка готовности сервиса, оставшиеся настройки логирования, метрики, эксплуатационные лимиты и аварийная очистка должны быть описаны после выбора среды. Численные требования к пропускной способности, доступности и задержке API в источниках отсутствуют.

Трассировка принятого задания включает отдельную операцию на всю обработку и стадии подготовки, компиляции, тестирования и публикации. Операция обработки связана с RunJob: отмена RPC прекращает рабочие стадии, но трасса включает остановку процессов и обязательную очистку до завершения серверной обработки. `SERVICE_NAME` задаётся при развёртывании и различает язык и версию языка профиля агента: в `runner-agent-cpp-23` суффикс `cpp-23` означает C++23, а не версию g++ или сборки агента. Агенты других языков или версий языка получают другие `SERVICE_NAME`; экземпляры одного профиля различаются по `service.instance.id`. Это правило именования будущих профилей, а не расширение языков текущего MVP. Адрес коллектора и параметры экспорта задаются при развёртывании средствами platform/OpenTelemetry.

Собственные метрики агента: количество заданий по исходу, длительность стадий, ошибки и повторы storage. `job_id` и `test_id` сохраняются в логах и трассах и не используются как метки метрик. Точные имена инструментов, единицы, остальные поля и техническая связь контекстов уточняются при реализации; согласованная семантика не зависит от этих имён.

#### Scenario: AT-67 — Логи и OpenTelemetry

- **WHEN** приложение запускается и экспортирует логи/телеметрию, включая ошибки
- **THEN** Platform сохраняет стандартный текстовый stdout и подключает OpenTelemetry без дублирования регистрации; контекст задания/теста, стадия и причина ошибки доступны, когда применимы. Секреты, исходники, входные данные и stdout/stderr не попадают в логи/телеметрию, в том числе через исключения и обогащение. Отсутствие обязательного `SERVICE_NAME` выявляется при запуске

Связанные требования: [Раздел 10](../agent-operations/spec.md), REQ-19.

#### Scenario: AT-68 — gRPC health

- **WHEN** health запрашивается при обработке RunJob, отмене/очистке, недоступном MinIO и штатной остановке
- **THEN** health обслуживается без занятия слота и остаётся SERVING до остановки RPC-сервера; новые RunJob при обычной занятости получают RESOURCE_EXHAUSTED, при остановке UNAVAILABLE; перед остановкой сервера выставляется NOT_SERVING

Связанные требования: OPS-02, REQ-10, REQ-14.

#### Scenario: AT-69 — Код завершения

- **WHEN** процесс управляемо останавливается либо завершается после ошибки запуска/очистки
- **THEN** штатное завершение после активного вызова и очистки даёт 0; ошибка старта, остановки процессов или очистки даёт 1; успешная отмена сама по себе процесс не завершает

Связанные требования: OPS-02, REQ-14.

#### Scenario: AT-70 — Идентификация и экспорт телеметрии

- **WHEN** развёртываются несколько экземпляров языкового профиля и настраивается экспорт
- **THEN** C++23-профиль развёртывается с `SERVICE_NAME=runner-agent-cpp-23`, где суффикс обозначает язык/версию языка; другие профили получают другие имена. Экземпляры одного профиля различаются по `service.instance.id`. Адрес коллектора/параметры экспорта берутся из конфигурации platform/OpenTelemetry при развёртывании; наличие других языковых профилей не требуется для MVP

Связанные требования: Раздел 10.

#### Scenario: AT-71 — Трассировка и метрики задания

- **WHEN** RunJob выполняется либо отменён с последующей очисткой
- **THEN** трасса охватывает обработку, остановку и очистку до завершения серверной работы; метрики включают количество заданий по исходу, длительности стадий, ошибки/повторы storage; job_id/test_id есть в логах/трассах, но не в метках метрик

Связанные требования: OPS-02, REQ-10.

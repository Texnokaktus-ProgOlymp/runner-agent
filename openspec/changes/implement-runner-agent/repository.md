# Структура репозитория и сборка

Статус: приложение MVP реализовано и проверяется локально. Внешний GitHub/GHCR выпуск и независимая приёмка ещё не выполнены. Требования MVP и платформа linux/amd64 сохраняются.

## Фактический каркас

SDK 10.0.403/`latestPatch` без preview; `net10.0`, C# 14, nullable/implicit usings, deterministic build, встроенные analyzers `10.0-recommended`, warnings as errors. Platform 2026.9.19.2 получает OpenTelemetry 2026.9.19.15 транзитивно. NUnit 4.6.1, NUnit3TestAdapter 6.3.1/MTP 2.4.1, NSubstitute 6.2.0, CodeCoverage 18.11.2, TrxReport 2.4.1 и ReportGenerator 5.5.11 совместно проходят Release build/test. Вложенные props явно импортируют корневой; тестовые пакеты не входят в production. Версии — в CPM/tool manifest, без локальных overrides.

`NuGet.Config` фиксирует package source mapping: `Texnokaktus.ProgOlymp.*` — GitHub Packages, остальные — nuget.org; аудит — nuget.org. При чистом cache нужны credentials чтения двух GitHub Packages, передаваемые через `NuGetPackageSourceCredentials_github` или пользовательскую конфигурацию NuGet. Workflow использует встроенный `GITHUB_TOKEN`, которому репозиторий должен иметь read-доступ к этим пакетам. Credentials не сохраняются в репозитории и доступны только restore/publish шагу.

Реализованы Release/tests/smoke, Docker/MinIO/E2E и публикация проверенных образов без пересборки. Детали workflow и retention приведены в последнем разделе; реальный внешний запуск текущих изменений ещё не выполнен. Локальная AOT публикация со всеми зависимостями успешна с warnings; production остаётся JIT.

Фактическое дерево включает один host и два тестовых проекта, базовый/языковой Dockerfile и тестовые drivers. Проверенные команды находятся в [README](../../../README.md#сборка-и-проверки), требования — в [OpenSpec](./README.md). Docker Desktop использует cgroups v2; обязательные контроллеры и интерфейсы подтверждены реальными sandbox-тестами.
## Согласованные требования

- README с кратким описанием функционала, API, сборки, тестирования и деплоя.
- Solution в формате `.slnx`.
- GitHub Actions для сборки, тестирования, Docker packaging и публикации в GHCR.
- Общие настройки сборки в `Directory.Build.props`, версии NuGet-пакетов в CPM.
- Production-код в `src/`, тестовые проекты в `tests/`.
- Настройки для групп проектов и при необходимости отдельных проектов во вложенных `Directory.Build.props`, включая общие тестовые зависимости и `InternalsVisibleTo`.
- Unit-тестовый проект имеет суффикс `.Tests`; тесты используют NUnit на Microsoft.Testing.Platform.
- Доступ `DynamicProxyGenAssembly2` объявляется в `src/Directory.Build.props` для всех production-проектов.
- Версия образа — `YYYY.M.D.<run_number>`; для выбора образа при деплое достаточно тега версии.
- Автоматический деплой не планируется. Pipeline завершается публикацией в GHCR и фиксацией выпуска Git-тегом.

Dockerfile находятся в docker/base и docker/cpp23; Jobs и Diagnostics дополняют показанные каталоги одного production-проекта. Пустые проекты не создаются.

Для MVP согласован один production-проект: Api/Jobs/Storage/Execution/Languages/Workspace/Diagnostics/Protos остаются каталогами и логическими границами внутри него. Отдельные библиотеки на первом этапе не выделяются. Согласованы два тестовых проекта: `.Tests` и `.IntegrationTests`, с назначением ниже. Выделение библиотек возможно при появлении самостоятельных потребителей или реальной необходимости ограничить зависимости. Solution folders src и tests реализованы в .slnx.

Проект `.Tests` проверяет локальную логику без Docker/S3/isolate. `.IntegrationTests` проверяет реальные границы: gRPC, storage, isolate, разделение compilation/execution, лимиты и очистку. Оба проекта используют NUnit на Microsoft.Testing.Platform. Интеграционные fixtures используют временные данные и тестовые credentials; для sandbox сохраняется запрет на сеть и credentials.

В тестах жизненного цикла проверяются одна компиляция на N тестов, один длительный RunJob до итогового ответа и удержание слота во время обработки и очистки. Конкурентный запрос с любым job_id/содержимым сразу получает RESOURCE_EXHAUSTED без очереди; после освобождения тот же ID может запустить задание заново. Кэша результатов, истории и безопасной от повторного исполнения доставки нет. Тот же процесс/контейнер принимает следующий RunJob после успешной очистки, если не начата остановка.

Проверки набора подтверждают одну компиляцию, последовательный порядок и независимые execution limits каждого теста; при отсутствии отмены ошибки тестов не прерывают набор. RunJob возвращает результат после публикации и попытки очистки; сравнение ответов и AC/WA относятся к мастеру.

Сбои до тестов проверяются отдельно: ошибка скачивания исходника, несовпадение его SHA-256 и невозможность запуска isolate для компиляции должны давать общий `InfrastructureError` со стадией и причиной, без запуска тестов и с пустым списком их результатов. Данные компиляции сохраняются, если появились; неначатая компиляция представляется явным отсутствием результата. Ошибка компиляции кода остаётся `CompilationError`.

Смешанные результаты после успешной компиляции дают общий Completed при обработанном наборе. Ошибки решений, лимитов и инфраструктуры тестов сохраняются раздельно. RunJob возвращает структурированный результат с gRPC OK, если вызов не отменён; отдельного состояния готовности ответа нет.

Совместная ошибка исполнения и публикации проверяется без потери исходного verdict: итоговый статус теста — `InfrastructureError`, отдельно сохраняются результат исполнения с известными метриками/exit code/signal и диагностика сбоя публикации. Возвращаются только ссылки на успешно опубликованные артефакты. Если процесс не запускался, результат исполнения явно отсутствует; в обоих случаях следующие тесты обрабатываются.

Сбой публикации вывода компилятора проверяется для успешной и неуспешной компиляции. В первом случае тесты выполняются, обработанный набор получает общий `Completed`; во втором сохраняются `CompilationError` и пустой список тестов. В обоих случаях сохраняются данные компиляции и инфраструктурная диагностика задания, ссылка на неопубликованный поток отсутствует.

Storage-проверки подтверждают формат SHA-256 как массива 32 байт во входных и выходных ссылках и `INVALID_ARGUMENT` при неверной длине входного хеша. Ключи внутри префикса мастера используют суффиксы `compilation/stdout.txt` и `compilation/stderr.txt`, `tests/{test_id}/stdout.txt` и `tests/{test_id}/stderr.txt`. Мастер отвечает за новый префикс каждого запуска; реестр префиксов у агента не создаётся. Сбой одного артефакта не должен останавливать публикацию остальных или удалять уже опубликованные объекты; повтор использует тот же ключ и содержимое. Хранение и удаление опубликованных артефактов относятся к мастеру или MinIO, а не к агенту.

Проверки контракта также подтверждают возврат заданных мастером положительного `job_id` типа `int64` и положительного `test_id` типа `int32` (номера теста в группе) без потери значений, чтение исходного кода из отдельного bucket и использование общего bucket для входных данных тестов и выходных артефактов. Оба bucket задаются конфигурацией, ключи выходных объектов формируются внутри префикса от мастера. Проверяется SHA-256 входных файлов без требования версий объектов S3. Отдельного RPC отмены нет: отмена RunJob прекращает проверку с последующей обязательной очисткой; штатная остановка агента рассматривается отдельно.

Единственный unary RunJob возвращает итоговый результат с OK при завершённом неотменённом вызове, включая ошибки компиляции и исполнения внутри результата. При остановке новый вызов получает UNAVAILABLE, при обычной занятости RESOURCE_EXHAUSTED независимо от ID и корректности его содержимого. Допущенный к свободному слоту запрос проходит валидацию и при ошибке получает INVALID_ARGUMENT без создания workspace. Проверяются атомарность допуска с остановкой и отсутствие очереди.

Повторный RunJob не имеет специальной семантики по job_id: во время занятости он отклоняется, после освобождения может исполниться заново. Сравнение разобранных полей и байтов protobuf для дедупликации отсутствует, отклонённый запрос не скачивает файлы.

Проверки валидации ID и набора подтверждают `INVALID_ARGUMENT` без принятия задания для нулевых/отрицательных ID, повторяющихся номеров тестов внутри задания и пустого набора. Повтор номера теста в другом задании допустим. Проверяются сохранение допустимых граничных значений `int64` для `job_id` и `int32` для `test_id` без потери значений и отсутствие перенумерации тестов агентом.

Для списка с пропусками и произвольным порядком номеров, например `8, 2, 5`, проверяются принятие валидного задания и исполнение после успешной компиляции в порядке запроса с сохранением номеров. Агент не проверяет полноту группы, не сортирует и не добавляет тесты.

Валидация и настройки gRPC не должны вводить отдельные верхние пределы числа тестов или размера запроса задания. Отдельные лимиты размеров исходника и входов тестов также не вводятся. При создании transport host необходимо согласовать его настройки с этим требованием; resource limits компиляции и исполнения продолжают проверяться отдельно.

Проверки S3-ключей подтверждают отказ пустым `key`/`result_prefix`, одинаковое формирование ключей для префиксов с завершающим `/` и без него и отсутствие использования S3-ключей в качестве локальных путей. Проверки существования выходных объектов перед загрузкой нет; повторное использование префикса мастером может перезаписать объект по прежнему ключу.

Начальная очистка удаляет только собственные workspace/boxes до приёма заданий; её ошибка завершает запуск с кодом 1. Ошибка очистки после обычного или отменённого RunJob запрещает новые задания и завершает процесс с кодом 1. При доступном неотменённом RPC сохраняются известные результаты и диагностика; при отмене ожидания клиента нет. Следующий запуск обязан успешно пройти начальную очистку.

Один экземпляр агента обслуживает фиксированный C++23-профиль с точной парой cpp/23; проверки исключают переключение компилятора, алиасы и произвольные команды. gRPC работает по HTTP/2 без TLS/auth с настраиваемым endpoint 0.0.0.0:8080. Deadline задаёт мастер; его истечение, отмена и обнаруженный разрыв прекращают текущую компиляцию/тест и storage, затем запускают независимую очистку. Следующие тесты и новые публикации не начинаются, опубликованные объекты остаются. Проверки storage используют production IObjectStorage на AWSSDK.S3 и MinIO.

Штатная остановка запрещает новые RunJob, позволяет текущему завершить набор, публикацию, очистку и ответ, затем завершает процесс. Отдельного ожидания чтения и таймаута получения результата нет. При отмене клиентом активного вызова во время остановки выполняются остановка процессов и очистка; незанятый агент выходит сразу.

Сценарии сбоев включают инфраструктурную ошибку одного теста с отдельным статусом и продолжением набора, остановку процесса с `OutputLimitExceeded` при превышении отдельного лимита stdout или stderr и сохранение каждого потока в пределах его лимита, а также отсутствие восстановления текущего задания и кэша ответа после перезапуска агента. Лимиты потоков проверяются независимо, включая случай, когда их сумма превышает каждый отдельный лимит, но сами потоки своих лимитов не превышают. Для MVP состояние хранится в памяти; опубликованные S3-артефакты от него не зависят.

В план тестирования также входят согласованные сценарии:

- Ошибка компиляции возвращает `CompilationError`, данные компиляции и вывод компилятора; коллекция результатов тестов пуста, исполнение тестов не начинается.
- Resilience policy MinIO управляется агентом: максимум три попытки на операцию с задержками 200 мс и 500 мс, автоматические повторы SDK отключены. Проверяются обрывы соединения, сетевые таймауты, HTTP `429`/`500`/`502`/`503`/`504`, `SlowDown`, восстановление и исчерпание попыток, повторное скачивание с начала. Отсутствие объекта/bucket, ошибки доступа/credentials и SHA-256 не повторяются; отмена storage-операции останавливает попытки. Проверка через production SDK должна исключать скрытые дополнительные повторы.
- Credentials читаются только из переменных окружения агента без fallback; отсутствие обязательных значений останавливает запуск. Для компиляции и исполнения тестовые секреты и произвольная посторонняя переменная окружения не должны наследоваться isolate/песочницей или читаться через `/proc` агента, mounts, рабочие файлы и аргументы. Проверяются отсутствие секретов в логах/результатах и path-style запросы к MinIO. Это критерии будущих тестов, а не заявление об уже проверенной изоляции.
- Во время обработки и отмены RunJob слот занят до окончания независимой очистки; клиент может уже получить ошибку, но новый вызов до освобождения получает RESOURCE_EXHAUSTED. Отмена самого RPC не отменяет cleanup; ошибка очистки даёт код 1 без повторного использования среды.

Согласованные проверки ресурсов включают обязательность обоих профилей и всех положительных значений, отсутствие defaults и общего таймаута задания, суммарный CPU/память всех процессов и потоков cgroup, лимит числа процессов/потоков с учётом основного и возврат пика той же метрики памяти cgroup, включая файловый кеш. Stdout/stderr компилятора проверяются раздельно: собственные лимиты, файлы, ключи `compilation/stdout.txt` / `compilation/stderr.txt` и независимая публикация. Превышение лимита stdout или stderr компилятора останавливает компиляцию, сохраняет оба частичных потока в их пределах и даёт `CompilationError` с причиной `OutputLimitExceeded` при отсутствии более приоритетного подтверждённого нарушения; тесты не запускаются.

Дополнительные проверки классификации подтверждают согласованный набор причин завершения и приоритет подтверждённых нарушений: память → вывод → CPU → wall time → процессы → runtime error. Остальные обнаруженные причины сохраняются в диагностике; один сигнал без подтверждения лимита не должен давать verdict превышения. Проверяются типы `int64` для времени/размеров, `int32` для `processes` и отказ `INVALID_ARGUMENT` неприменимым значениям до принятия задания.

Проверки окружения требуют cgroups v2 с доступными контроллерами/метриками; несовместимое окружение завершает запуск до приёма заданий. Интеграционные тесты подтверждают отключённый swap, групповое завершение при OOM, округление лимита памяти вверх до страницы с возвратом фактического значения, чтение пика из memory.peak и учёт pids.events при ограничении pids.max. Обработанный программой отказ созданию процесса с exit code 0 всё равно должен фиксировать ProcessLimitExceeded. Потеря обязательных метрик после запуска отражается как инфраструктурная ошибка без подстановки нулей; доступные данные сохраняются.

Storage-проверки подтверждают регион подписи клиента `us-east-1` по умолчанию на MinIO без явно заданного серверного региона и возможность переопределения. Корректная локальная конфигурация позволяет агенту запуститься при недоступном MinIO без обязательных сетевых проверок; рабочие операции затем применяют согласованные повторы. Bucket подготавливает fixture в роли развёртывания, production-агент их не создаёт и не меняет их настройки. Проверки логирования подтверждают стандартный текстовый stdout через Texnokaktus.ProgOlymp.Platform, подключение OpenTelemetry без повторной регистрации providers/exporters, контекст задания/теста, стадию и причину ошибки, когда они применимы. Секреты, исходники, входные данные и stdout/stderr отсутствуют в логах и экспортируемой телеметрии, включая исключения, сообщения библиотек и enrichment. JSON-формат не требуется.

Для будущего production-проекта выбран [Texnokaktus.ProgOlymp.Platform](https://github.com/Texnokaktus-ProgOlymp/platform) с регистрацией через `WebApplicationBuilder.UsePlatform()`. Пакет подключает Serilog и Texnokaktus.ProgOlymp.OpenTelemetry; требуется `SERVICE_NAME`. Точная версия и источник пакетов фиксируются при создании каркаса в рамках CPM; текущая ветка зависимости не считается выбранной опубликованной версией. AOT-совместимость проверяется отдельно. Собственная инструментация расширяется через `ConfigureOpenTelemetry.WithTracerConfiguration` / `WithMeterConfiguration`, настройка логгера — через `ConfigureSerilog.ConfigureSerilog`.

Интеграционные проверки подтверждают gRPC health на существующем порту без занятия слота: SERVING после инициализации, при обработке/отмене/очистке, недоступном MinIO и завершении активного вызова при остановке; NOT_SERVING перед остановкой сервера. Штатный выход после очистки — 0; ошибка запуска, завершения процессов или очистки — 1. Успешная отмена сама по себе процесс не завершает. Без обязательного SERVICE_NAME запуск отклоняется.

Проверки телеметрии используют SERVICE_NAME=runner-agent-cpp-23, различают экземпляры по service.instance.id и задают экспорт средствами platform/OpenTelemetry. Трасса RunJob охватывает рабочие стадии, остановку и очистку, включая cleanup после отмены. Метрики включают исходы заданий, длительности стадий, ошибки/повторы storage; job_id/test_id доступны в логах/трассах, но отсутствуют в метках метрик.

Проверки конфигурации подтверждают приоритет переменных окружения над обычными параметрами `appsettings.json`, credentials только из окружения, секции `S3`/`Runner` и сохранение имён platform/OpenTelemetry. Настройки фиксируются при запуске и меняются после перезапуска. Проверяются корень workspace `/var/lib/runner-agent` по умолчанию и его переопределение, собственные рабочие каталоги внутри корня без преобразования S3-ключей в локальные пути. В `SERVICE_NAME=runner-agent-cpp-23` суффикс означает язык/версию языка; другие профили получают другие имена, экземпляры одного профиля различаются по `service.instance.id`. Для MVP достаточно проверки C++23; эти правила не требуют реализации других языков.

## Общие настройки сборки

Согласованы общие `TargetFramework=net10.0`, `LangVersion=14.0`, `Nullable=enable`, `ImplicitUsings=enable`. Версии SDK/пакетов и реализованные настройки каркаса зафиксированы в разделе «Фактический каркас»; таблица описывает их распределение. Платформа MVP — `linux/amd64`; arm64 добавляется отдельно после проверки isolate и toolchain.
| Файл | Ответственность |
| --- | --- |
| `global.json` | Версия .NET SDK 10, политика `rollForward` и `test.runner=Microsoft.Testing.Platform`; единые настройки для локальной разработки и CI |
| `Directory.Build.props` | `TargetFramework=net10.0`, `LangVersion=14.0`, `Nullable=enable`, `ImplicitUsings=enable`, deterministic build и настройки анализаторов |
| `Directory.Packages.props` | `ManagePackageVersionsCentrally=true` и версии через `PackageVersion` |
| `src/Directory.Build.props` | Импорт корневых настроек, общие production-настройки и `InternalsVisibleTo` для тестовых assemblies и `DynamicProxyGenAssembly2` |
| `tests/Directory.Build.props` | Импорт корневых настроек, `IsTestProject=true`, `IsPackable=false`, `OutputType=Exe`, `EnableNUnitRunner=true`, общие test packages |
| `.config/dotnet-tools.json` | Зафиксированная версия ReportGenerator; установка через `dotnet tool restore` |
| `.csproj` | Тип SDK проекта, его собственные references, protobuf generation и специфические свойства |

Версия установленного .NET SDK выбирается до вычисления `Directory.Build.props`, поэтому она фиксируется в `global.json`. Атрибут `Sdk` (`Microsoft.NET.Sdk.Web` для gRPC host, `Microsoft.NET.Sdk` для тестов) остаётся в `.csproj`. `TargetFramework` и версия C# задаются отдельно от версии SDK. В каркасе выбран SDK 10.0.403 с rollForward=latestPatch; `latest`/preview для C# не используем.

MSBuild автоматически находит только ближайший `Directory.Build.props`. Поэтому файлы в `src/` и `tests/` начинают с явного импорта:

```xml
<Project>
  <Import Project="$(MSBuildThisFileDirectory)../Directory.Build.props" />
  <!-- Настройки этой группы проектов. -->
</Project>
```

Если отдельному проекту понадобится собственный `Directory.Build.props`, он аналогично импортирует родительский файл своей группы. Для единичного свойства достаточно `.csproj`; отдельный props нужен при полезной группировке настроек. Поздно вычисляемые свойства и build targets при необходимости размещаются в `Directory.Build.targets`.

`PublishAot` не включается глобально: разработка и обычные тесты используют JIT. Проверка AOT выполняется отдельно для production entry point на целевой Linux-платформе. Настройки CI, например `ContinuousIntegrationBuild`, применяются условно, без изменения обычного локального режима.

## CPM, тестовые пакеты и InternalsVisibleTo

Версии всех NuGet-зависимостей централизованно фиксируются в корневом `Directory.Packages.props`, плавающие версии не допускаются. Версии используемых пакетов каркаса уже выбраны и проверены; последующие зависимости добавляются с фиксированными версиями. `PackageReference` в проектах и общих props не содержит `Version`. Дополнительные CPM-файлы в `src/` и `tests/` изначально не нужны.

Для доступа к MinIO production-проект использует `AWSSDK.S3`; версия пакета фиксируется в CPM. Совместимость выбранной версии с целевой Native AOT публикацией проверяется отдельно.

Тестовая платформа — Microsoft.Testing.Platform (MTP), framework — NUnit. Используем нативный MTP-режим `dotnet test` из .NET 10. В `global.json` наряду с настройками SDK добавляется секция:

```json
{
  "test": {
    "runner": "Microsoft.Testing.Platform"
  }
}
```

В `tests/Directory.Build.props` задаются `EnableNUnitRunner=true` и `OutputType=Exe`. NUnit runner поставляется через `NUnit3TestAdapter`; выбираем совместимую версию с поддержкой MTP 1.7 или новее. Свойство `TestingPlatformDotnetTestSupport` для нативного режима .NET 10 не требуется. Основание: [NUnit и MTP](https://docs.nunit.org/articles/vs-test-adapter/NUnit-And-Microsoft-Test-Platform.html), [MTP-режим dotnet test](https://learn.microsoft.com/en-us/dotnet/core/testing/unit-testing-with-dotnet-test#mtp-mode-of-dotnet-test).

Общие зависимости тестов: `NUnit`, `NUnit3TestAdapter`, `NSubstitute`, `Microsoft.Testing.Extensions.CodeCoverage` и `Microsoft.Testing.Extensions.TrxReport`.

Форма общего объявления; фактические версии находятся в Directory.Packages.props:

```xml
<ItemGroup>
  <PackageReference Include="NUnit" PrivateAssets="all" />
  <PackageReference Include="NUnit3TestAdapter" PrivateAssets="all" />
  <PackageReference Include="NSubstitute" PrivateAssets="all" />
  <PackageReference Include="Microsoft.Testing.Extensions.CodeCoverage" PrivateAssets="all" />
  <PackageReference Include="Microsoft.Testing.Extensions.TrxReport" PrivateAssets="all" />
</ItemGroup>
```

Для конкретного проекта команда использует `dotnet test --project <path>`, для всего solution — `dotnet test --solution <path>`. Покрытие в Cobertura включается через `--coverage --coverage-output-format cobertura`, TRX — через `--report-trx`. В CI оба тестовых проекта запускаются отдельно на соответствующих этапах; ReportGenerator обрабатывает полученные Cobertura-файлы. См. [покрытие MTP](https://learn.microsoft.com/en-us/dotnet/core/testing/microsoft-testing-platform-code-coverage) и [отчёты MTP](https://learn.microsoft.com/en-us/dotnet/core/testing/microsoft-testing-platform-test-reports).

Тестовые зависимости не попадают в корневые или production props. Пакеты, нужные только интеграционным fixtures, подключаются в IntegrationTests, с версиями в общем CPM. Конкретные версии фиксируются при создании проектов и проверяются совместным restore/build/test.

`InternalsVisibleTo` задаётся на стороне production assembly. Для предложенных имён проектов в `src/Directory.Build.props` подходит:

```xml
<ItemGroup>
  <InternalsVisibleTo Include="$(MSBuildProjectName).Tests" />
</ItemGroup>
```

Здесь предполагается, что `AssemblyName` совпадает с именем проекта. IntegrationTests по умолчанию проверяет публичные границы. Доступ для прокси NSubstitute также объявляется в `src/Directory.Build.props` и наследуется всеми production-проектами:

```xml
<ItemGroup>
  <InternalsVisibleTo Include="DynamicProxyGenAssembly2" />
</ItemGroup>
```

Согласованы проверки команды `g++ -std=c++23 -O2 -pipe -DONLINE_JUDGE` с явными входным/выходным файлами, динамической линковки и runtime-библиотек только для чтения. Интеграционные тесты подтверждают работу compiler/solution без root, запись только в рабочие/временные каталоги стадии, отсутствие утечек через дескрипторы/mounts и непересекающиеся workspace/box IDs/cgroups экземпляров. Проверяются монотонное wall time, CPU всей cgroup, подтверждённые причины превышений и отсутствие переполнения при преобразованиях лимитов.

## Docker

Dockerfile находятся в docker/base и docker/cpp23. Агент публикуется SDK вне Docker; build context допускает только artifacts/host, Docker-конфигурацию и bootstrap. База multi-stage собирает pinned isolate отдельно, final содержит Ubuntu/.NET runtime/isolate/agent без SDK и компилятора. Производный образ добавляет g++ 13.3.0 и фиксированный профиль. Мастер задаёт только язык/версию стандарта, без команд и compiler version.

NuGet credentials доступны restore/publish на host/CI и не входят в Docker context. Registry token и S3 credentials не передаются в build args или слои. Runtime credentials задаются env при запуске.
Для MVP выбран долгоживущий агент с единственным RunJob: контейнер используется для последовательных заданий, слот занят до завершения обработчика и очистки. Отмена RPC останавливает текущую песочницу и storage, после успешной очистки разрешает следующий вызов. Штатная остановка позволяет активному вызову закончить набор и ответ; отдельного ожидания чтения результата нет. Host/container должны позволять завершить обработку и очистку. Автоматический деплой не планируется.

## GitHub Actions

Путь workflow: `.github/workflows/dotnet.yml`. Согласован запуск на push в `master` публичного GitHub-репозитория. Pull request в рабочем процессе отсутствуют; PR-триггеры и отдельные PR-проверки не предусматриваются. Обязательный результат — сборка, тесты, проверенный Docker image и публикация в GHCR только после успешных обязательных проверок.

Для интеграционных тестов согласован стандартный одноразовый GitHub-hosted Linux runner на виртуальной машине при условии бесплатного использования. Для публичного репозитория стандартные runners бесплатны согласно [условиям GitHub Actions](https://docs.github.com/en/billing/concepts/product-billing/github-actions), проверенным 2 октября 2026 года. Платные larger runners не выбираются; постоянный judge-host не используется. Выбран стандартный VM image `ubuntu-24.04`; работоспособность privileged Docker/cgroups v2/isolate подтверждается пробным запуском при создании CI. Контейнерный `ubuntu-slim` для этой задачи не подходит: он не поддерживает необходимые привилегированные операции ([справка runners](https://docs.github.com/en/actions/reference/runners/github-hosted-runners)).

Бесплатность вычислений не означает неограниченное хранение artifacts. Docker-архив для передачи между jobs и TRX/coverage занимают artifact storage; размер, срок хранения и удаление временного архива нужно подобрать в пределах бесплатной квоты. Переход на платные ресурсы этим решением не разрешён. GitHub выбран основным репозиторием кода, CI и выпусков. Пользователь самостоятельно переносит репозиторий, обновляет origin и пересоздаёт Gitea как независимое зеркало. Зеркалирование настраивается только в Gitea: в GitHub нет связанных с ним workflow, secrets или проверок; недоступность зеркала не влияет на выпуск. После переноса фактический адрес GitHub определяется обновлённым origin.

### Выводы из изученного pipeline

Изученный workflow запускается на push в `master`. Job сборки устанавливает .NET 10, выполняет restore/build/test, собирает Cobertura coverage и публикует Markdown summary. Зависимый Docker job формирует версию из даты коммита в часовом поясе Europe/Moscow и номера workflow run, собирает образы для amd64/arm64, отправляет их в GHCR и создаёт Git-тег. Также предусмотрены submodules и приватный NuGet source.

Для RunnerAgent полезны разделение проверки и публикации, отчёт покрытия, Buildx, OCI metadata и связь версии образа с исходным коммитом. Особенности, которые требуют адаптации:

- Согласованный триггер RunnerAgent — push в `master`, без pull request. Публикация зависит от успешных проверок этого запуска.
- Использовать SDK из `global.json` и одну конфигурацию `Release` на этапах restore/build/test/publish.
- Зафиксировать ReportGenerator как local tool и сохранять TRX/coverage artifacts, включая результаты неуспешных тестовых запусков, когда файлы созданы.
- Платформа MVP согласована: `linux/amd64`. Поддержка arm64 добавляется отдельно после проверки isolate и toolchain на этой архитектуре; использование QEMU пока не утверждено.
- Submodules и приватный NuGet source подключать только при появлении соответствующих зависимостей.
- `contents: write` нужен для Git-тега, но не для отправки образа в GHCR. Для публикации достаточно `contents: read` и `packages: write`.
- В summary публикации возвращать полное имя образа с тегом версии для ручного деплоя.
- Не считать успешную сборку образа доказательством работоспособности isolate: перед публикацией проверить реальный запуск C++ в этом образе.

### Согласованные этапы и оставшиеся детали

1. **Build/test.** На push в `master` выполнить сборку и `.Tests`. Сохранить TRX и coverage, включая неуспешные тестовые запуски, если файлы сформированы. Checkout, SDK/MTP по `global.json`, tool restore, Release build и конкретные команды остаются предлагаемыми деталями реализации.
2. **Docker/integration.** Собрать `linux/amd64` image и выполнить `.IntegrationTests` против него на стандартном одноразовом GitHub-hosted Linux VM runner с проверенной поддержкой privileged Docker/cgroups. Использовать тестовые данные и credentials. Buildx с `push: false`, `load: true` — предлагаемый способ сборки. Постоянный judge-host не применяется.
3. **Publish.** Только после успешных обязательных проверок push в `master` опубликовать тот же проверенный образ без пересборки. Между jobs образ передаётся через `docker save/load`; временный artifact учитывается в бесплатной квоте хранения. В summary вывести полное имя образа с тегом версии для ручного деплоя. Login через `GITHUB_TOKEN`, конкретные permissions и передача revision — предлагаемые детали реализации.
4. **AOT compatibility.** При появлении production-проекта отдельная информационная CI-проверка `PublishAot=true` для целевого Linux RID. Неуспех виден в результатах, но не блокирует рабочий JIT-образ. Переход production на AOT допускается после успешной сборки и полного набора интеграционных тестов AOT-варианта, включая platform/OpenTelemetry.

Publishing job не запускается при пропущенных или неуспешных обязательных проверках. Устаревшие проверки от push можно отменять до публикации; начатую публикацию новым push не прерывают. Настройка concurrency должна учитывать эту границу, а не отменять весь workflow вместе с publishing job. Конкретная реализация выбирается при создании workflow; PR-сценариев нет.

### Registry, версии и теги

Согласованный runner — стандартный `ubuntu-24.04` (Linux VM); перед интеграционными тестами проверяются необходимые возможности privileged Docker/cgroups v2/isolate. Имя образа — `ghcr.io/texnokaktus-progolymp/runner-agent-cpp-23`. Для истории выпусков после успешной публикации образа создаётся Git-тег `vYYYY.M.D.<run_number>` на коммите, из которого собран образ. Тег Docker-образа сохраняет формат `YYYY.M.D.<run_number>` без `v`. При повторном запуске существующий Git-тег на том же коммите считается нормальным; тег на другом коммите вызывает ошибку без перезаписи. Сбой создания Git-тега делает этап выпуска неуспешным, опубликованный образ сохраняется. Устаревшие проверки от push можно отменять до публикации, но уже начатая публикация новым push не прерывается.

Согласованный image: `ghcr.io/texnokaktus-progolymp/runner-agent-cpp-23`. Namespace `texnokaktus-progolymp` зафиксирован явно; текущий Git origin не определяет namespace registry. Обозначение `judge-cpp` в архитектуре описывает состав первого образа, а не отдельный registry package.

Формат тега Docker-образа: `YYYY.M.D.<run_number>`, где дата берётся из исходного коммита в Europe/Moscow. Повторный запуск того же workflow сохраняет версию. Revision коммита включается в OCI labels. Версия передаётся в Docker build и metadata агента согласованно; точное отображение в .NET version properties определяется при реализации.

Для ручного деплоя образ выбирается по тегу версии: `image:<version>`.

Pipeline выпуска сначала публикует образ в GHCR, затем создаёт Git-тег с префиксом `v` для истории по согласованным правилам повторов. Автоматический деплой не планируется; развёртывание на judge-host выполняется вручную.

## Реализованные команды и ручной деплой

Актуальные restore/build/test/publish/Docker команды находятся в [README](../../../README.md#сборка-и-проверки). Выполнены локальные .NET/NUnit, SDK HTTP fault tests, MinIO и production gRPC/S3 проверки в privileged Linux amd64 Docker с cgroups v2. Тестовые fixtures не используют production secrets.

Физические Dockerfile расположены в docker/base и docker/cpp23; код — в одном production-проекте, каталоги Api, Jobs, Protos, Diagnostics, Storage, Execution, Languages, Workspace. IntegrationTests содержит Tools/CustomWebApplicationFactory, SetupBase/SetupGlobal и сценарии реальных внешних границ. Категории Sandbox, MinIO, EndToEnd требуют соответствующей среды; обычный прогон явно исключает их.

Workflow .github/workflows/dotnet.yml выполняет Release/tests/smoke и Docker-наборы, передаёт оба проверенных образа через docker save/gzip/load, проверяет image IDs. Publish без пересборки отправляет ghcr.io/texnokaktus-progolymp/runner-agent-base и runner-agent-cpp-23, затем создаёт Git-тег версии. Конфликт чужого тега обнаруживается до registry mutations. Начатый publish не отменяется новым push, проверки отменяемы. Shell fixtures проверяют дату коммита Europe/Moscow, повтор, конфликт и ошибку registry без внешней публикации.

Архив ограничен 200 МиБ (локально около 174 МиБ), хранится 1 день, удаляется из Actions после успешной публикации. Отчёты хранятся 3 дня. При сбое load/publish архив остаётся до retention для диагностики и повторного запуска publish. Общая свободная квота организации не проверена: перед первым workflow оператор должен обеспечить доступный бесплатный бюджет. Две текущие копии архива занимают около 349 МиБ без отчётов; неограниченное число неудачных выпусков не обещается.

Информационная AOT job публикует тот же production-проект со всеми зависимостями, сохраняет warnings/log и не блокирует JIT. Локальная linux-x64 AOT сборка на SDK 10.0.403 завершилась с exit 0 и trimming/AOT warnings; полноценный запуск AOT через integration-набор не выполнялся. Production остаётся JIT.

Ручной запуск образа с --privileged --cgroupns=private, S3 env и volume workspace описан в README. Внешний GitHub/GHCR выпуск текущей версии и деплой опубликованного тега ещё не выполнялись. Пользователь самостоятельно меняет origin и настраивает Gitea-зеркало; workflow не зависит от зеркала.
